## A.0 设计原则
承接 v1 AHF 架构的不变量——**每一步的"判断"由模型做出，每一步的"事实"由 harness 记录**——v2 在此之上新增五条工程原则：
1. **契约先行**：所有跨包协作只通过 `packages/core` 中定义的纯类型契约进行，契约层零运行时依赖，可独立发版与测试。
2. **策略可替换**：Goal-Plan-Execute-Observe-Reflect 闭环不是硬编码流程，而是**一种 HarnessStrategy 实现**。简单任务用 `PlanExecuteStrategy`，复杂任务用 `FullLoopStrategy`，运行时按目标契约选择。
3. **Provider 可替换**：所有模型调用经由 `packages/provider-llm`（pi-ai 适配）进行，上层只面向 `Provider` 契约编程，永不直连厂商 SDK。
4. **开关即架构**：每一个流程节点（Observe/Reflect/审批门/校准回路等）都是带 FeatureFlag 的可插拔模块。**Flag 关闭 ≠ 数据不产生**——观测点持续 emit，仅 sink 不消费；这保证 A/B 测试与事后回放的完整性。
5. **观测三层对齐执行三层**：Session-Turn-Step 与真实执行结构一一映射，任何 span 都能定位到"哪次输入、哪个子任务、哪个最小动作"。
---
## A.1 分层架构总览
v2 采用五层结构，自上而下依赖严格单向，禁止反向依赖与跨层依赖。
```
┌───────────────────────────────────────────────────────────────────┐
│  L4 应用层 apps/*                                                 │
│      cli / server / worker — 装配、启动、HTTP/SSE 暴露            │
├───────────────────────────────────────────────────────────────────┤
│  L3 策略层 packages/strategy-*                                    │
│      HarnessStrategy 实现：full-loop / plan-execute / react       │
│      按目标契约选择策略、编排五阶段                                │
├───────────────────────────────────────────────────────────────────┤
│  L2 能力层 packages/{planner,executor,observer,reflector,memory}  │
│      五阶段的独立实现，可被任何策略复用                            │
│      planner 负责 Provider 池选择 + Capacity 组装                 │
├───────────────────────────────────────────────────────────────────┤
│  L1 基础设施层 packages/{provider-llm,observability,flags,policy} │
│      provider-llm：基于 pi-ai 的 LLM 适配（独立包）               │
│      observability：Session-Turn-Step span + 事件总线             │
│      flags：Feature Flag 求值与 A/B 分流                          │
│      policy：权限策略、审批门、沙箱策略                           │
├───────────────────────────────────────────────────────────────────┤
│  L0 契约层 packages/core                                          │
│      全部 TypeScript 类型与接口契约（零运行时依赖）               │
└───────────────────────────────────────────────────────────────────┘
```
**依赖规则**：上层依赖下层；L0 被所有层依赖但不依赖任何层；L1 之间禁止相互依赖（仅通过 L0 协作）；L2 通过依赖注入消费 L1；L3 编排 L2；L4 装配一切。

## A.2 核心契约定义
### A.2.1 执行三层：Session / Turn / Step
三层数据模型与观测层一一映射，是整个架构的**时空坐标系**。
```ts
// packages/core/src/session.ts
/** 用户的一次输入 = 一个 Session（最外层容器） */
export interface Session {
  sessionId: string;             // ULID
  userId?: string;
  /** 用户原始输入（自然语言意图） */
  rawIntent: string;
  /** 由 Goal 层产出的结构化目标契约 */
  goal: GoalContract;
  /** 本次会话选中的策略 */
  strategyId: string;
  /** 会话级上下文（跨 Turn 持久化） */
  state: SessionState;
  /** 会话级 Feature Flag 快照（求值一次，全程不变） */
  flagSnapshot: FlagSnapshot;
  createdAt: number;
  endedAt?: number;
  outcome?: 'success' | 'failed' | 'aborted' | 'timeout';
}
/** 目标拆解出的一个子任务 = 一个 Turn */
export interface Turn {
  turnId: string;
  sessionId: string;
  /** 子任务的自然语言描述 */
  title: string;
  /** 子目标的可验证完成标准（来自 Plan 层） */
  acceptance: AcceptanceSpec;
  /** 该 Turn 所需的 Capacity（由 Plan 层组装） */
  capacity: Capacity;
  /** 该 Turn 内的 Step 列表（执行序） */
  stepIds: string[];
  status: 'pending' | 'running' | 'succeeded' | 'failed' | 'rolled_back';
  attempt: number;               // 重试次数
  parentPlanNodeId?: string;     // 关联到 Plan 图
}
/** 最小执行单元 = 一个 Step（thinking 或 tool_call） */
export type StepKind = 'thinking' | 'tool_call' | 'observation';
export interface Step {
  stepId: string;
  turnId: string;
  sessionId: string;
  seq: number;                   // 在 Turn 内的序号
  kind: StepKind;
  /** thinking：LLM 推理产出；tool_call：一次工具调用 */
  payload: ThinkingPayload | ToolCallPayload | ObservationPayload;
  /** 该 Step 使用的 Provider 与模型（可追溯） */
  model?: ModelRef;
  usage?: Usage;                 // tokens / cost / latency
  status: 'pending' | 'running' | 'ok' | 'error' | 'skipped' | 'blocked';
  error?: HarnessError;
  startedAt: number;
  endedAt?: number;
  /** 决策依据快照（审计用）：当时的上下文摘要 + prompt 版本 */
  decisionContext?: DecisionContext;
}
```
**映射规则**：`Step` 对应观测层的最小 span；`Turn` 对应 Plan 图中的一个节点；`Session` 对应一次用户输入的完整轨迹。**任何日志、指标、审计记录都必须携带这三层 ID**，缺一不可。
### A.2.2 Provider 契约（pi-ai 适配）
Provider 适配层基于 [`pi-ai`](https://github.com/earendil-works/pi) 的统一多 Provider API——其暴露 `getModel(provider, model)`、`stream(model, context)`、`complete(model, context)`、`Context`/`Tool`/`toolResult` 等核心类型，原生支持 TypeBox 校验的工具调用、跨 Provider 模型切换与统一 usage/cost 统计。`packages/core` 不直接依赖 pi-ai，而是定义**等价契约**，由 `packages/provider-llm` 完成契约与 pi-ai 的桥接，保证契约层稳定、适配层可替换。
```ts
// packages/core/src/provider.ts
/** 模型引用：定位池中的一个具体模型 */
export interface ModelRef {
  providerId: string;            // e.g. 'anthropic-primary'
  vendor: string;                // 'anthropic' | 'openai' | ...
  modelId: string;               // 'claude-opus-4' | 'gpt-5' | ...
}
/** Provider 实例：一个带凭证、限流、标签的模型端点 */
export interface Provider {
  id: string;
  vendor: string;
  models: ModelDescriptor[];
  /** 能力标签，供 Plan 层路由决策 */
  tags: ProviderTag[];           // ['cheap','fast','long-context','tools','vision']
  /** 运行时约束 */
  limits: { rpm?: number; tpm?: number; concurrency?: number };
  /** 成本系数（相对值，用于路由权衡） */
  costWeight: number;
  /** 健康度由运行时反馈，供故障转移 */
  health: { score: number; lastErrorAt?: number };
}
export interface ModelDescriptor {
  id: string;
  contextWindow: number;
  supportsTools: boolean;
  supportsThinking: boolean;
  supportsVision: boolean;
  inputCostPerMTok: number;
  outputCostPerMTok: number;
}
/** 与 pi-ai Context 对齐的统一上下文（可序列化，可跨 Provider 迁移） */
export interface LLMContext {
  systemPrompt?: string;
  messages: LLMMessage[];
  tools: ToolSpec[];
}
/** LLM 调用统一入口，由 provider-llm 包实现 */
export interface LLMDriver {
  /** 流式调用：返回 Step 事件流，由 Executor 消费 */
  stream(req: LLMRequest): AsyncIterable<LLMStreamEvent>;
  /** 非流式调用 */
  complete(req: LLMRequest): Promise<LLMResponse>;
}
export interface LLMRequest {
  model: ModelRef;
  context: LLMContext;
  thinking?: { budgetTokens?: number };
  maxTokens?: number;
  signal?: AbortSignal;
}
```
### A.2.3 Capacity 契约（Plan 层组装产物）
Capacity 是 Plan 层输出给执行层的**资源包**：一次执行需要什么模型、哪些工具、什么权限、多少预算。
```ts
// packages/core/src/capacity.ts
/** Plan 层为每个子任务组装的执行资源包 */
export interface Capacity {
  /** 路由决策选中的模型 */
  model: ModelRef;
  /** 本次允许调用的工具白名单（schema 已校验） */
  tools: ToolSpec[];
  /** 本次允许的权限级别（最小权限） */
  permission: PermissionLevel;
  /** 预算上限（在目标契约内进一步收紧） */
  budget: { maxSteps?: number; maxTokens?: number; maxCostUsd?: number; timeoutMs?: number };
  /** 执行上下文（沙箱配置、网络白名单、文件挂载） */
  sandbox: SandboxSpec;
  /** 本次执行的 Feature Flag 子集（已求值） */
  flags: FlagSnapshot;
}
export type PermissionLevel =
  | 'text'        // 仅生成文本
  | 'read-only'   // 可读不可写
  | 'draft'       // 写入暂存区
  | 'approved'    // 经审批可对外
  | 'autonomous'; // 受限自主
export interface ToolSpec {
  name: string;
  description: string;
  /** TypeBox schema，与 pi-ai Tool.parameters 对齐 */
  parameters: unknown;
  /** 工具声明的最小权限级别 */
  minPermission: PermissionLevel;
  /** 不可逆标记，触发审批门 */
  irreversible?: boolean;
  /** 副作用域（'fs' | 'net' | 'process' | 'external-api'） */
  sideEffects: SideEffectScope[];
}
```
### A.2.4 HarnessStrategy 契约（闭环策略化）
闭环不再是硬编码流程，而是可插拔策略。`packages/core` 只定义接口，`packages/strategy-*` 提供实现。
```ts
// packages/core/src/strategy.ts
/** 策略能力声明：告知运行时本策略需要哪些阶段参与 */
export interface StrategyCapabilities {
  needsGoal: boolean;
  needsPlan: boolean;
  needsExecute: boolean;
  needsObserve: boolean;         // false 时 observer 模块不被实例化
  needsReflect: boolean;
  /** 是否需要跨 Turn 持久化状态 */
  needsPersistentState: boolean;
}
/** Harness 策略：可替换的执行编排方案 */
export interface HarnessStrategy {
  id: string;                    // 'full-loop' | 'plan-execute' | 'react-only'
  version: string;
  capabilities: StrategyCapabilities;
  /** 策略选择评分：根据目标契约评估适配度，得分高者胜出 */
  score(goal: GoalContract): number;
  /** 主入口：接收已装配的依赖，产出 Step 事件流 */
  run(ctx: StrategyContext): AsyncIterable<StrategyEvent>;
}
export interface StrategyContext {
  session: Session;
  /** L2 各阶段模块（按 capabilities 注入，未启用的为 undefined） */
  planner?: Planner;
  executor?: Executor;
  observer?: Observer;
  reflector?: Reflector;
  memory: MemoryStore;
  driver: LLMDriver;             // 来自 provider-llm 包
  flags: FlagSnapshot;
  emit: (event: HarnessEvent) => void;   // 统一观测出口
}
```
**内置策略**：
| 策略 ID | 编排 | 适用场景 |
|---|---|---|
| `full-loop` | Goal → Plan → Execute → Observe → Reflect | 复杂多步任务、长视野、含不可逆动作 |
| `plan-execute` | Plan → Execute（无独立 Observe/Reflect，观察结果直接回注 Executor） | 简单线性任务、低风险 |
| `react-only` | 单层 Think-Act-Observe 循环 | 实时问答、单工具调用 |

## A.3 Feature Flag 与 A/B 测试系统
### A.3.1 设计要点
- **静态声明 + 运行时求值**：所有 flag 在代码中以常量声明（名称、默认值、类型、作用域），运行时根据 `sessionId`、`userId`、`goal tags` 等上下文求值，**求值结果作为快照冻结在 Session 中**，保证一次会话内行为一致、可追溯。
- **Flag 关闭 ≠ 数据不产生**：观测点 emit 不受 flag 控制；flag 只控制 sink 是否消费。这保证关闭 Observe 层时，数据仍流向事件总线，事后可回放。
- **A/B 分流**：flag 支持按 hash 分桶，可在同一时间窗内对同一改进点做对照实验。
```ts
// packages/core/src/flags.ts
export interface FeatureFlagDefinition<T = boolean | number | string> {
  key: string;                            // 'observe.enabled' | 'plan.strategy' | 'ab.provider-router-v2'
  description: string;
  type: 'boolean' | 'number' | 'string';
  defaultValue: T;
  /** 求值规则：按优先级依次尝试 */
  rules?: FlagRule<T>[];
}
export interface FlagRule<T> {
  /** 命中条件（所有条件 AND） */
  match?: {
    userIdIn?: string[];
    goalTagIn?: string[];
    /** 按 sessionId 哈希分桶（A/B 用） */
    bucketRange?: [number, number];       // 0-99
  };
  value: T;
  /** 规则来源标识（审计） */
  source: string;
}
export interface FlagSnapshot {
  values: Record<string, unknown>;
  /** 求值时使用的规则 trace，便于复盘 */
  trace: { key: string; matchedRule?: string; resolvedValue: unknown }[];
  /** 便捷 API */
  isEnabled(key: string): boolean;
  getNumber(key: string): number | undefined;
  getString(key: string): string | undefined;
}
```
### A.3.2 A/B 测试路径
```ts
// 示例：对比两个 Provider 路由算法的 cost 与成功率
const flags: FeatureFlagDefinition[] = [
  {
    key: 'ab.planner.route-v2',
    description: 'Plan 层路由算法 v2（含 cost-aware 加权）',
    type: 'boolean',
    defaultValue: false,
    rules: [
      { match: { bucketRange: [0, 49] }, value: true, source: 'ab-experiment-2026-09' },
      { match: { bucketRange: [50, 99] }, value: false, source: 'ab-experiment-2026-09' },
    ],
  },
];
```
实验结果通过观测层的 Session/Turn 聚合指标自动对齐：`flagSnapshot.trace` 中含 `ab.planner.route-v2=true` 的 Session 与 false 的 Session 在成本、成功率、Turn 数上分别聚合对比。**A/B 不需要旁路系统，复用观测层即可**。

## A.4 关键模块设计
### A.4.1 Plan 层：Provider 池选择与 Capacity 组装
Plan 层是 v2 架构的核心增量。它接收目标契约，做三件事：**分解子任务 → 选择 Provider → 组装 Capacity**。
```ts
// packages/core/src/planner.ts
export interface Planner {
  /** 输入目标契约，输出 Plan 图（节点间可有依赖） */
  plan(goal: GoalContract, ctx: PlanContext): Promise<PlanGraph>;
  /** 为单个 Turn 重新组装 Capacity（重试/升级场景） */
  assembleCapacity(turn: Turn, ctx: PlanContext): Promise<Capacity>;
}
export interface PlanGraph {
  sessionId: string;
  nodes: PlanNode[];
  edges: { from: string; to: string; kind: 'sequence' | 'parallel' | 'rollback' }[];
}
export interface PlanNode {
  nodeId: string;
  title: string;
  acceptance: AcceptanceSpec;
  /** 该节点的 Provider 路由意向（执行时由 Planner.assembleCapacity 最终确定） */
  preferredModelTags: ProviderTag[];
  estimatedCost?: number;
  estimatedSteps?: number;
}
```
**Provider 池选择算法**（v2 默认实现）：
```
1. 候选过滤：从 ProviderPool 中筛出满足硬性要求者
   - 支持 goal.tags 中要求的全部能力（tools/vision/long-context）
   - health.score ≥ threshold
2. 软性评分：
   score = w1 * capability_match
         + w2 * (1 / costWeight)
         + w3 * latency_p50
         + w4 * (1 - recent_error_rate)
   权重由 flag 'planner.route-weights' 注入，可 A/B
3. 取 score 最高者；同分按成本优先
4. 失败时降级到次优（带退避），事件广播至观测层
```
**Capacity 组装流程**：
```
Turn 创建
  ├─ 1. 从 PlanNode 取 preferredModelTags
  ├─ 2. 调用 ProviderRouter.select() → ModelRef
  ├─ 3. 根据 PlanNode.acceptance 推导所需工具 → ToolSpec[]（schema 已校验）
  ├─ 4. 根据 ToolSpec[].sideEffects 推导 PermissionLevel
  │      - 全部只读 → 'read-only'
  │      - 含写 → 'draft'
  │      - 含 irreversible → 触发审批门，未通过前维持 'draft'
  ├─ 5. 从 GoalContract.budget 收紧出 Turn 级 budget
  ├─ 6. 构造 SandboxSpec（按策略要求选择沙箱配置）
  └─ 7. 求值 flag 子集 → Capacity 完成，交付 Executor
```
### A.4.2 观测层：Session-Turn-Step 三层埋点
观测层与 OTel GenAI 语义约定对齐——GenAI semconv 已定义 `invoke_agent`、`execute_tool` 等 span 类型及 `gen_ai.*` 属性族，v2 在此之上叠加 Session-Turn-Step 三层 ID 作为一等属性。
```ts
// packages/core/src/observability.ts
/** 三层 ID 是所有事件的必备字段 */
export interface TraceIdentifiers {
  sessionId: string;
  turnId?: string;
  stepId?: string;
}
export type HarnessEventType =
  | 'session.started' | 'session.ended'
  | 'turn.started' | 'turn.ended'
  | 'step.started' | 'step.ended'
  | 'llm.request' | 'llm.stream_event' | 'llm.response'
  | 'tool.invoke' | 'tool.result' | 'tool.blocked'
  | 'policy.check' | 'policy.denied' | 'approval.requested' | 'approval.granted'
  | 'provider.selected' | 'provider.fallback'
  | 'flag.evaluated'
  | 'reflection.verdict' | 'rollback.executed';
export interface HarnessEvent extends TraceIdentifiers {
  eventId: string;
  type: HarnessEventType;
  timestamp: number;
  /** 关键属性，与 OTel GenAI semconv 对齐 */
  attributes: {
    'gen_ai.operation.name'?: string;
    'gen_ai.request.model'?: string;
    'gen_ai.provider.name'?: string;
    'gen_ai.usage.input_tokens'?: number;
    'gen_ai.usage.output_tokens'?: number;
    'harness.step_kind'?: StepKind;
    'harness.permission_level'?: PermissionLevel;
    'harness.flag_overrides'?: Record<string, unknown>;
    'harness.strategy_id'?: string;
    [k: string]: unknown;
  };
  payload?: unknown;
}
/** 事件总线：emit 永不被 flag 阻断，仅 sink 受 flag 控制 */
export interface EventBus {
  emit(event: HarnessEvent): void;
  subscribe(filter: EventFilter, sink: EventSink): Unsubscribe;
}
export interface EventFilter {
  types?: HarnessEventType[];
  minLevel?: 'debug' | 'info' | 'warn' | 'error';
  /** 仅消费 flag 命中时的数据 */
  requireFlag?: { key: string; equals?: unknown };
}
export interface EventSink {
  id: string;
  /** 消费到事件，可能异步（写库、转发 OTLP 等） */
  handle(event: HarnessEvent): Promise<void> | void;
}
```
**关键设计**：emit 与 consume 解耦。`observe.enabled=false` 时，`Observer` 模块不消费事件（不做规则判断、不注入反馈），但 `llm.request`/`tool.invoke` 等事件仍持续 emit 到总线，可被审计 sink、回放 sink 消费。这使 Observe 层成为纯消费者而非数据通路的一部分。
### A.4.3 三层聚合视图
观测层在三层 ID 之上提供聚合查询，直接支撑四层级评估：
| 层级 | 聚合键 | 典型指标 |
|---|---|---|
| Step | `sessionId + turnId + stepId` | 单次调用延迟、token、错误类型 |
| Turn | `sessionId + turnId` | 子任务完成率、平均步数、重试次数、回滚率 |
| Session | `sessionId` | 整体成功率、总成本、总时长、策略 ID、flag 覆盖 |
| 跨 Session | `userId / strategyId / flag 值` | A/B 对照、模型成本分布、失败分类分布 |

**关键依赖关系**：
```
apps/* → harness-runtime → strategy-* → planner/executor/observer/reflector
```

## A.6 执行流程（以 `full-loop` 策略为例）
```
用户输入
  │
  ▼
[Runtime] 创建 Session（求值 FlagSnapshot，冻结到 session.flagSnapshot）
  │
  ▼
[Goal 层] 生成 GoalContract（落盘 goal.md，含 success/failure/budget/终止条件）
  │
  ▼
[Strategy 选择器] 按 strategy.score(goal) 选出 FullLoopStrategy
  │
  ▼
[Planner.plan()]
  ├─ 分解为 PlanGraph（N 个 PlanNode）
  ├─ 对每个 node：调用 ProviderRouter.select() → ModelRef
  └─ 对每个 node：组装 Capacity（tools/permission/budget/sandbox）
  │
  ▼
[Executor 循环] 对每个 Turn：
  ├─ step.started (emit)
  ├─ LLM 调用（PiAiDriver.stream）→ thinking / tool_call
  ├─ tool_call 命中 hook → policy.check（emit）
  │     ├─ 通过 → tool.invoke → tool.result
  │     ├─ 需审批 → approval.requested → 等待 → approval.granted
  │     └─ 拒绝 → tool.blocked → 反思层介入
  ├─ step.ended (emit, 含 usage)
  └─ 若 observe.enabled → Observer 消费 tool.result，结构化回注上下文
  │
  ▼
[Reflector] 对照 GoalContract 判定
  ├─ 通过 → Turn 完成，进入下一个 Turn
  └─ 失败 → 注入错误细节，重试或回滚（rollback.executed）
  │
  ▼
[Session.ended] + 聚合指标上报
```
**Flag 影响点**：
| Flag | 影响范围 | 关闭后行为 |
|---|---|---|
| `observe.enabled` | Observer 模块 | Observer 不消费事件，但事件仍 emit（审计可取） |
| `reflect.enabled` | Reflector 模块 | 跳过独立评估，由 Executor 简单判断完成 |
| `approval.gate` | 审批门 | 仍记录 policy.check，但直接放行（仅限低风险环境） |
| `ab.planner.route-v2` | Planner 路由算法 | 使用 v1 评分公式 |
| `memory.persistent` | MemoryStore | 仅内存模式，落盘跳过 |
| `sandbox.enabled` | SandboxSpec | 仅开发模式允许关闭；生产强制 true |

## A.7 验收标准（v2 总体）
| # | 验收项 | 标准 |
|---|---|---|
| 1 | 三层观测完整性 | 任意 Step 都能通过 `sessionId/turnId/stepId` 三元组定位；任何事件缺任一必填 ID 即报错 |
| 2 | 策略可替换 | 新增一个 HarnessStrategy 实现无需修改 runtime 代码；通过策略 ID 切换 |
| 3 | Provider 可替换 | 替换 provider-llm 实现不影响上层；pi-ai 仅存在于 provider-llm 包内 |
| 4 | Flag 关闭 ≠ 数据丢失 | 关闭 `observe.enabled` 后，事件总线仍能查到完整 llm.request/tool.invoke 流水 |
| 5 | A/B 对照 | 同一 flag 不同 bucket 的 Session 在聚合指标上可自动分组对比 |
| 6 | Capacity 可追溯 | 每次工具调用都能回溯到当时的 Capacity 快照（model/tools/permission/budget） |
| 7 | 契约稳定 | packages/core 不依赖任何运行时包，可独立编译发布 |
| 8 | 审计可重建 | 凭事件日志可离线重放任意 Session 的完整决策链（模型看到什么、决定什么、执行什么） |
