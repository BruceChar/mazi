**Harness = 目标闭环 + 状态记忆 + 权限边界 + 审计反馈**

目标闭环负责“做对事”，权限边界负责“不越界”，状态记忆负责“在长程任务中保持一致”，审计反馈负责“持续可纠错”。

# AI Agent Harness 架构设计文档
> **文档定位**：面向复杂真实任务的 AI Agent 执行框架设计。在假设模型能力持续提升乃至 AGI 实现的前提下，从第一性原理推导 harness 的存在依据、能力边界与模块设计，供架构评审与工程实现参考。
---
## 0. 总纲
**Harness 定义**：在环境不可逆的约束下，将模型的概率性推理转化为**可验证、可回滚、可审计**的行动序列的全部确定性工程结构。
**总体结构**：**一个核心执行闭环 + 三个支柱 + 两条治理回路**。
```
用户意图
  └─► 核心执行闭环（模块一）：Goal ─► Plan ─► Execute ─► Observe ─► Reflect ─►（回到 Plan/Goal）
        │
        ├── 支柱一（模块二）记忆与状态管理 ──── 让闭环在时间维度上可延续
        ├── 支柱二（模块三）工具接地与权限安全边界 ─ 让闭环在真实世界上可安全落地
        ├── 支柱三（模块四）可观测、审计与持续校准 ─ 让闭环在事后可验证、可复盘
        │
        └─► 治理回路一（校准回路）：评估 → 策略/约束更新 → 再评估
            治理回路二（进化回路）：失败账本 → Harness 迭代
                └─► 反馈回核心闭环与三大支柱（并上行至训练管线）
```
**根本分工**：模型负责生成假设，harness 负责让假设变得可证伪。模型输出 token 不是行动——模型提出“我认为应该执行 A”，harness 回答“A 是否被允许、以什么权限、在什么隔离环境、执行后如何验证、失败如何回滚、全过程如何记录”。
**分工判断标准**（贯穿全文）：
> 凡是“输出是概率分布、错误可由单步推理纠正”的能力，交给模型；凡是“涉及真实世界状态变更、错误代价不可逆、需要跨时间维度保持一致性”的能力，交给 harness。
---
## 1. 第一性原理：为什么必须有 Harness
### 1.1 环境侧：复杂真实任务的四条硬约束
1. **环境部分可观测**——行动前无法获得完整信息；
2. **动作不可逆**——错误代价无法通过重新推理消除；
3. **时间跨度超越单次上下文**——任务状态无法天然驻留；
4. **目标在执行中可能漂移**——“完成”的定义需要外部锚点。
### 1.2 模型侧：三条内生局限
模型本质是“给定上下文输出下一个 token 分布”的函数，它是**无状态、无副作用、无权限概念**的：
1. 输出是概率性的（能力提升不改变这一属性）；
2. 自我评估带系统性乐观偏差（RLHF 使其倾向自信且讨好的答案，自报置信度与真实准确率有显著鸿沟）；
3. 对真实世界状态的掌握完全依赖上下文注入。
### 1.3 推论
- 四条环境约束是**环境的属性**，不随模型能力提升而消失。即使 AGI 实现，只要动作仍对真实世界产生不可逆影响，harness 就必须存在。
- Harness 的核心不是让模型更聪明，而是把模型能力放进**可控制、可恢复、可审计**的闭环。
- 生产数据显示，同一模型在不同 harness 中表现差异可达数十个百分点——系统瓶颈往往不在模型，而在驾驭它的脚手架。
---
## 2. 能力分工：模型内生 vs Harness 承担
### 2.1 能力矩阵
| 能力维度 | 模型内生提供（即使 AGI 后仍不完全可靠） | Harness 必须承担（不可外包给模型） |
|---|---|---|
| 任务理解 | 解析自然语言目标、识别隐含约束 | 将目标翻译为显式、可验证的完成准则 |
| 规划 | 生成候选分解路径、提出子目标、动态重规划 | 计划落盘、状态检查点、重规划触发条件、子目标失败标准 |
| 工具使用 | 提议“应调用哪个工具”、生成调用意图 | 工具注册表、schema 校验、权限检查、真实执行、超时/重试/降级、事务回滚 |
| 记忆与状态 | 仅在上下文窗口内推理 | 持久化、checkpoint/resume、跨会话记忆、检索/压缩/遗忘 |
| 反思/自评 | 生成对自身输出的批评文本 | 独立评估器、规则化反馈、错误注入回环 |
| 置信度 | 自报置信度（常过度自信） | 基于频率/多采样/外部校准的真实置信度 |
| 安全判断 | 识别“这类操作通常危险” | 确定性策略、硬性权限边界、沙箱、审批门（不可绕过） |
| 审计 | 解释“我为什么这么做” | 全链路 trace、不可篡改日志、可重放证据 |
### 2.2 动态边界
模型能力升级后，harness 中属于**“认知”**的部分（复杂规划、反思、长程状态维护）会被逐步吸收；属于**“治理”**的部分（权限、审计、状态持久化）不会消失，反而更重要。今天由 harness 补上的，明天模型能做到就移除对应脚手架——harness 应从“补智商”演进为“管行为”。

## 3. 总体架构
### 3.1 组件与职责一览
| 组件 | 核心职责 | 关键属性 |
|---|---|---|
| 核心执行闭环 | 目标→计划→执行→观察→反思的可靠推进 | 可中断、可恢复、可异步 |
| 记忆与状态管理 | 跨时间维度保持任务一致性 | 持久化、分层、可重建 |
| 工具接地与权限边界 | 将模型意图安全接地为真实动作 | 确定性、最小权限、不可绕过 |
| 可观测、审计与校准 | 让系统事后可验证、可改进 | 全链路、可重放、外部校准 |
| 校准回路 | 评估结果约束 agent 行为 | 外部评估、多层级 |
| 进化回路 | 生产失败驱动 harness 自身迭代 | 失败可追溯、规则可增删 |
### 3.2 设计不变量
> **每一步的“判断”由模型做出，每一步的“事实”由 harness 记录。**
任何时刻停下，都能从日志重建“模型当时看到了什么、决定了什么、harness 执行了什么、环境发生了什么”。这是全部可信性的来源。

## 4. 模块一：核心执行闭环
### 4.1 为什么简单 ReAct 循环不够
- **乘积律**：多步任务整体成功率近似各步成功率的乘积——单步 95%，20 步任务成功率掉到 36%。可靠性必须来自结构，而非单步智能。
- **上下文腐烂（context rot）**：窗口越满，推理质量越差。
- **自我确认偏差**：单 agent 同时承担行动与评价，无法发现自身真正的错误。
因此闭环各环节必须由 harness 提供结构性保障：
### 4.2 目标层
- **做什么**：接收用户意图后，强制生成结构化**目标契约**：成功条件、失败条件、不允许触碰的资源、预算上限（时间/token/金钱）、终止条件。
- **为什么**：模型对“完成”的判断天然偏乐观，必须有外部锚点；事先写下 done 条件能显著减少 scope drift。
- **怎么做**：契约落盘（如 `goal.md`），作为后续所有反思与终止判断的引用源；每次注入上下文时重新加载，防止长任务“漂移遗忘”。
- **验收标准**：能否用一段代码或一个测试用例**机械地**判断“任务是否完成”？不能，说明目标定义还不够。
### 4.3 计划层
- **做什么**：将目标分解为可独立验证的子目标，每个子目标附带：预期可观察副作用、所需工具与权限级别、失败信号、回滚方法。
- **为什么**：纯文本计划无法支撑长时间执行，必须结构化落盘，使会话恢复可从计划文件重建状态。
- **怎么做**：Plan-and-Execute 处理长视野任务，ReAct 处理实时性强的子任务，混合是生产主流；计划文件由 harness 维护，模型只读或经审批后写入。
- **验收标准**：任一子任务失败时，能否**不丢弃已完成工作**、从该子任务回滚并重试？
### 4.4 执行层
- **做什么**：所有副作用操作经由 harness 执行器，禁止模型直触底层 API；harness 负责调度、超时、重试、降级、原子性保证与事务回滚。
- **为什么**：动作不可逆是复杂任务的核心风险，必须由外部机制而非模型自觉兜底。
- **怎么做**：动作前记录状态快照；写操作进入**暂存区**（分支/draft/staging/事务），验证或审批后才合并；破坏性命令（`rm -rf`、`DROP TABLE`、`git push --force`）由 hook 硬拦截。
- **验收标准**：随机中断执行，系统能否**在任意点恢复并继续**？
### 4.5 观察层
- **做什么**：工具结果以结构化形式回注上下文（状态码、关键数值、错误类型、diff）；大体积输出只保留头尾，全文转储文件系统供按需读取。
- **为什么**：上下文是稀缺资源，噪声降低推理质量；结构化观察便于反思层做规则化判断。
- **怎么做**：hook 拦截所有工具返回值 → schema 校验 → 敏感信息脱敏 → 大小裁剪 → 注入。
- **验收标准**：每次观察后，模型能否**不依赖长尾记忆**理解当前状态？
### 4.6 反思层
- **做什么**：使用**独立评估器**（另一模型实例、规则引擎或确定性测试）对照目标契约判断执行质量；失败信息以自然语言反馈回模型，作为下一轮尝试的提示。
- **为什么**：行动者与评价者分离，缓解确认偏差；多个反思实例可显著提高纠错率。
- **怎么做**：遵循**“成功静默、失败冗长”**——通过时不注入任何信息，失败时注入错误细节；所有反思锚定到目标契约的具体条款，避免泛泛评价。
- **验收标准**：评估器与生成器是否由不同 prompt、不同实例或不同工具集构成？评估结果能否被人工复核？

## 5. 模块二：记忆与状态管理
### 5.1 状态分层
模型权重无法在单次会话中可靠保存细粒度事实；即使 AGI 内部推理更强，外部持久状态仍需 harness 维护。
| 层级 | 内容 | 生命周期 | 归属 |
|---|---|---|---|
| 工作记忆 | 当前上下文窗口内容 | 单次推理 | 模型 |
| 任务状态 | 目标契约、计划、子目标进度、中间产物 | 任务全程、跨会话 | harness 持久化 |
| 环境事实 | 工具返回、文件/外部系统当前状态 | 环境拥有，harness 记录快照 | 环境 + harness |
| 长期记忆 | 用户偏好、历史任务、领域知识 | 跨任务 | harness（检索库） |
### 5.2 持久化与恢复
- checkpoint/resume：状态写入磁盘，与执行层“任意点恢复”验收标准共用同一机制；
- 计划文件是会话恢复的锚点（见 4.3）；
- 跨会话记忆按任务/用户隔离，防止状态串扰。
### 5.3 上下文管理
四类操作对抗 context rot：**压缩**（摘要历史）、**检索**（按相关性注入）、**裁剪**（丢弃低价值内容）、**转储**（大输出进文件系统，上下文只留指针）。
- **验收标准**：任务进行到后期，模型上下文中是否仍只包含与当前决策相关的信息？能否从持久化状态完整重建一个中断多日的任务？

## 6. 模块三：工具接地与权限安全边界
### 6.1 威胁模型与设计立场
三种风险叠加：模型从混乱输入中解析指令（网页、文档、邮件中的对抗性内容）、以自信姿态犯错、能调用影响真实系统的工具。**“提示模型不要做危险的事”是必要但不充分的**——边界必须由 harness 强制执行。
设计立场：**策略与目标分离**，类似操作系统的用户态/内核态边界。模型可以提议，harness 根据策略执行或拒绝——即使模型出错或被提示注入，也不会直接造成不可逆后果。
### 6.2 工具注册表与执行器
- **注册表**：每个工具声明式描述 schema、前置条件、副作用、幂等性、耗时/成本、所需权限级别；
- **执行器**：标准化调用、超时、重试、降级、回滚；运行时校验调用是否越级。
- **验收标准**：不符合 schema 的调用是否在触达真实系统**之前**被拦截？
### 6.3 最小权限与权限阶梯
- 默认最低权限启动：**文本级 → 只读 → 草稿级 → 审批后执行 → 受限自主**，仅在观察到具体需求且具备对应控制手段时逐级上升；
- 权限令牌与会话绑定，任务结束即失效。
- **验收标准**：能否一句话说清“这个 agent 能读什么、能写什么、能花多少钱、能发什么”？说不清就不应上线。
### 6.4 动作分级与审批门
按不可逆程度分级，审批成本精准投放在真正高风险的动作上：
| 级别 | 示例 | 处理方式 |
|---|---|---|
| 读操作 | 查询、检索 | 自动放行，记录 trace |
| 可撤销写 | 文件编辑、本地提交 | 进入暂存区 |
| 外部可见 | 发邮件、提 PR、调支付 API | 人工审批门 |
| 高风险 | 生产写入、超阈值金额、删除 | 强制双人确认 |
- 审批规则以策略文件定义（threshold、scope、approver），版本化管理，每次审批决策记录到 trace。
- **验收标准**：审批拒绝后，系统能否优雅终止或转向备选方案，而不是反复尝试绕过？
### 6.5 沙箱与执行隔离
- 容器/VM 级隔离 + 每任务独立工作区 + 资源配额（CPU/内存/时长/网络）；文件系统只暴露工作目录，网络出口走代理白名单，不允许访问宿主机凭证。
- **原理**：沙箱不是让 agent 更聪明，而是**让错误更便宜**——越界 agent 在沙箱内外的损失差几个数量级。
- **验收标准**：假设 agent 完全被恶意操控，它能造成的最大损失是多少？这个上限是否可接受？
### 6.6 预算与速率限制
时间/token/金钱预算在目标契约中定义、由 harness 执行，杜绝无人干预下耗尽预算或陷入死循环的可能。
### 6.7 扩展点的注入面审查
MCP 服务器、浏览器插件等扩展点的描述文本会注入 prompt，构成潜在的 prompt injection 通道——必须经独立审查后接入，并维护扩展点清单与审查记录。
### 6.8 全链路审计日志
- 每个 trace 记录：prompt 版本与上下文、模型决策、harness 执行的动作、工具返回、策略判定、审批记录、最终结果；使用 OpenTelemetry 或类似标准统一格式。
- **被拦截的尝试也必须留痕**——“agent 想做什么但被挡了”是安全分析的重要信号。
- **验收标准**：审计员能否仅凭日志重建完整决策链？答案必须是“能”。

## 7. 模块四：可观测性、评估与持续校准
### 7.1 为什么必须外部评估
模型自评有结构性偏差（倾向自信且讨好），且模型只能“评价输出长什么样”，无法评价“输出是否在真实世界产生了预期效果”——后者只有 harness 与环境交互后才能知道。指标覆盖：任务成功率、过程质量、成本、延迟、安全事件；失败案例固化为回归测试集，防止能力漂移。
### 7.2 四层级评估
| 层级 | 评估问题 | 典型失败 |
|---|---|---|
| span | 单次工具调用是否正确 | 参数错误、schema 违例 |
| trace | 单次端到端任务是否完成 | 步骤遗漏、工具误用 |
| trajectory | 决策路径是否高效合理 | 绕路、重复尝试、过度操作 |
| session | 跨轮会话是否保持一致 | 上下文遗忘、目标漂移 |
单一层级无法定位失败原因：trace 失败可能源于 span 参数错误，span 全部通过也可能因规划不当导致 trajectory 失败。评估结果须与 trace 中具体 span 关联。
- **验收标准**：评估体系能否区分**“模型错了 / 工具错了 / 上下文给了错的 / 策略错了”**四种情况？
### 7.3 可验证奖励优先于主观判断
- 能用确定性代码判断的绝不交给 LLM judge：schema 合规、transaction ID、测试通过、数值范围；
- LLM judge 仅用于语义类问题（是否基于检索证据、是否切合用户意图），且 judge 本身需用人工标注样本校准；
- **原理**：确定性检查便宜、可重复、可解释；judge 引入二次不确定性，必须严格限定使用范围。
### 7.4 置信度的频率校准
- 不依赖模型自报置信度，通过多采样一致性、语义熵、logprob 聚合估计不确定性；
- 用 held-out 数据集拟合校准器（Platt scaling / isotonic regression）映射为真实概率；
- 校准数据集随分布漂移定期重校；高不确定性动作自动降级到人工审批。
- **验收标准**：confidence ≥ 0.9 的样本子集，实际准确率是否接近 0.9？
### 7.5 治理回路一：校准的三向反馈
评估结果流向三处：
1. **反馈给模型**——通过反思层注入；
2. **反馈给 harness 自身**——通过失败账本（见 7.6）；
3. **反馈给训练管线**——通过可验证奖励用于 post-training。
最可靠的 agent 不是模型最强的，而是**“模型—harness—评估”三者耦合度最高**的。
### 7.6 治理回路二：失败驱动的 Harness 迭代
- 把每次生产失败当作永久性输入。例：“agent 注释掉了测试且被合并” → 下个版本 AGENTS.md 增加“禁止注释测试”规则 + pre-commit hook 检查 `.skip(` + reviewer subagent 将该问题列为 blocker。
- 维护**失败分类账**：每类失败映射到四类修复之一——prompt 修订 / 工具 schema 调整 / hook 增加 / 评估指标新增；每条规则可追溯到一个具体过往失败。
- 同时警惕过度工程：模型能力升级后，旧脚手架要敢于删除。
- **验收标准**：每个 harness 组件能否说清“它是因为哪个具体失败而存在的”？说不清就是冗余。

## 8. 设计哲学与演进纪律
1. **Harness 的存在依据是环境属性，而非模型缺陷。** 不可逆性与可观测性不足不随模型能力提升而消失，即使 AGI 实现 harness 依然必要——只是边界动态移动：认知部分被模型逐步吸收，治理部分（权限、审计、状态持久化）愈发重要。
2. **模型越强，harness 越从“补智商”转向“管行为”。** AGI 时代评估重心从“输出对不对”转向“过程是否可接受、边界是否被遵守”。
3. **好 harness 的标志不是复杂，而是“每一行都可被删除”**——每一行都因为过去一次具体失败而存在，也将因为未来模型能力的一次提升而优雅退场。这是面向 AGI 时代构建 agent 的真正工程纪律。
**凝练公式**：
> **Harness = 目标闭环 + 状态记忆 + 权限边界 + 审计反馈**
>
> 目标闭环负责“做对事”，权限边界负责“不越界”，状态记忆负责“在长程任务中保持一致”，审计反馈负责“持续可纠错”。
