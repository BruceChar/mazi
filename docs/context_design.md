
# AI Agent Context 管理器设计方案

> **版本**：v1.0（正式版）
> **文档定位**：面向生产实现的 Context Manager 工程规范。设计前提承接 Harness 架构文档：模型是“给定上下文输出下一个 token 分布”的函数——**无状态、无副作用、无权限概念**。Context Manager 的职责不是让模型记住更多，而是作为**无状态模型与持久世界之间的桥**，在每一轮决策时刻注入最小且充分的相关信息。
>
> **凝练公式**：
> **Context 管理 = 状态外置 + 决策相关注入 + 可重建锚点**
> 状态外置解决“信息不丢”，决策相关注入解决“推理不被稀释”，可重建锚点解决“任意时刻可恢复”。

---

## 1. 设计依据

### 1.1 三条不随 AGI 消失的事实

| 事实                                         | 后果                 | 设计对策                                            |
| -------------------------------------------- | -------------------- | --------------------------------------------------- |
| 模型无状态，上下文只是易失工作记忆           | 状态必须住在模型之外 | 存储层外置（§5），模型不可直写                     |
| 上下文是稀缺资源，窗口越满推理越差           | 注入必须“最小充分” | 三区缓存模型 + 分区预算 + 注意力租金按需支付（§3） |
| 环境部分可观测，上下文是模型看世界的唯一窗口 | **注入即权限** | 信任分级 + 注入面治理 + 脱敏前置（§4）             |

### 1.2 根本分工

> **凡是“判断”交给模型，凡是“事实与执行”交给 harness。**
> 归属判断、相关性兜底排序、摘要生成由模型承担；存储、注入、切换、晋升、仲裁、合并、删除级联全部由 harness 确定性执行。

### 1.3 注意力租金原则

注入的价值 = 信息增益 + 注意力增益，二者可分离。多数注入买的是**位置**（把已有信息拉回决策点旁），不是新颖性。推论：

1. 快照与注入物必须是**摘要 + 指针**，不重复全文；
2. 租金按依赖度支付：低依赖轮次少注或不注，不固定每轮交。

## 2. 总体架构

```
┌────────────────── 存储层（确定性，harness 持有，模型不可直写）──────────────────┐
│  用户级档案（Fact，分档激活）   话题线（TopicLine，一等实体）   会话 transcript   │
│  检索索引 / 转储全文 / vault（明文） / ContextEpoch 版本链 / Trace（指针化）      │
└──────────────────────────────┬───────────────────────────────────┬────────────┘
                        快照 out/in                          压缩/裁剪/转储+指针
┌──────────────────────────────▼───────────────────────────────────▼────────────┐
│ 激活层（模型窗口）：静态前缀区 / 追加历史区 / 动态尾部区（§3）                    │
└──────────────────────────────┬────────────────────────────────────────────────┘
┌──────────────────────────────▼──────────────── 治理层 ────────────────────────┐
│  hook 管线（校验→脱敏→裁剪，对所有注入生效） · 信任分级（T0–T3）与仲裁           │
│  写租约 / 合并策略 / 删除级联 · 全链路指针化 trace · 策略参数版本化 + 回归门禁    │
│  红线双轨（自然语言 context + 确定性 hook） · 失败账本驱动的策略迭代             │
└───────────────────────────────────────────────────────────────────────────────┘
```

## 3. 三区缓存模型

### 3.1 设计原理

前缀缓存逐字节匹配：前缀内任意字节变化，其后全部失效。由此，窗口内容按变更性质分为三区——**可变改写、确定性追加、每轮重建**，各自适用不同的缓存纪律：

```
┌─ 静态前缀区（epoch 内字节冻结，diff = 0）────────────────────┐
│ 系统提示+策略(T0, ≤2000) │ resident事实(≤500) │ 契约摘要(≤150) │
│ 背景线程条(≤150)                                              │
├─ 追加历史区（append-only，旧前缀永不改写）────────────────────┤
│ [U₁][A₁][U₂][A₂]...[Uₙ]                                      │
│   第 n 轮命中至第 n-1 轮末尾；增量 miss = 本轮新增             │
├─ 动态尾部区（每轮重建，全价 = 注意力租金）────────────────────┤
│ 检索外围(≤500, T3≤300) │ 跨话题合成(≤400, 瞬态) │ 轮内state(≤300) │
│ 当前输入(≤4000)                                               │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 Epoch（缓存纪元）

> **Epoch = 相邻两次显式状态变更事件之间的静态前缀区间。epoch 内静态前缀区字节不可变；一切可变内容（档案、契约、背景条、焦点快照）只在 epoch 边界变更。**

```yaml
ContextEpoch {
  epoch_id,
  prefix_version,                  # 单调递增，写入前缀首行
  composed_of: { system_ver, profile_ver, bg_strip_ver,
                 contract_ver, focus_snapshot_ver },   # 版本向量（§10）
  started_at, ended_at,
  end_reason: session_boundary | topic_switch | contract_revision
            | profile_promotion | privacy_deletion | forced_strip_consolidation
            | history_compression
}
```

**四条纪律**：

1. **epoch 内静态前缀区 diff 为零**，由 CI 断言（作用于冻结区，非全窗）；
2. **epoch 切换必须携带前缀 diff 记录**，写 trace；
3. **prefix_version 写入前缀自身**——任一 trace 经五元组即可还原模型当时看到的前缀的确切身份；
4. **旧版本不可变留存**；回滚 = 钉住旧版本开启新 epoch。
   **两类泄漏独立告警**：静态前缀区在 epoch 内被改写 = **epoch 泄漏**；历史区被回写改 = **append 泄漏**。健康基线：每轮未命中 ≈ 动态尾部区（≤1500）+ 本轮新增历史，偏差 >±10% 触发排查。

### 3.3 两个交点规则

1. **历史区压缩 = epoch 边界事件**。压缩即重写历史，从压缩点起全价——压缩点必须同时是新 epoch 起点，成本一次付清；
2. **静态前缀区变更只允许 epoch bump**，无例外。背景条的惰性失效（§6.3）是此规则的执行机制。

### 3.4 全局预算总表

| 区       | 槽位              | 信任等级 | 预算                                        | 缓存状态            | 变更时机                 |
| -------- | ----------------- | -------- | ------------------------------------------- | ------------------- | ------------------------ |
| 静态前缀 | 系统提示 + 策略   | T0       | ≤2000                                      | 0.1x（epoch 内）    | epoch bump               |
| 静态前缀 | resident 用户事实 | T0/T1    | ≤500                                       | 同上                | epoch bump（仅会话边界） |
| 静态前缀 | 焦点契约摘要      | T2       | ≤150                                       | 同上                | epoch bump               |
| 静态前缀 | 背景线程条        | T2       | ≤150                                       | 同上                | epoch bump（惰性失效）   |
| 追加历史 | transcript        | T1/T2    | 历史区 > 0.6·W 触发压缩，压缩后 ≤ 0.25·W | 前缀命中，增量 miss | append-only              |
| 动态尾部 | 检索外围          | T2/T3    | ≤500（其中 T3 ≤300）                      | 全价                | 每轮                     |
| 动态尾部 | 跨话题合成        | T2       | ≤400，瞬态                                 | 全价                | 按需单轮                 |
| 动态尾部 | 轮内 state        | T2       | ≤300                                       | 全价                | 每轮                     |
| 动态尾部 | 当前输入          | T1/T3    | ≤4000                                      | 全价                | 每轮                     |

**动态尾部合计**  **≤1500（不含当前输入）**  预算参数均随策略参数版本化（§12.3）。压缩判定仅依赖（历史区 tokens，W）两个确定性量，可从 trace 复算；W 为部署模型窗口大小。     

**当前输入超限处理**：全文 append-only 落转储存储（信息无损、可寻回），入窗为头部+尾部切片 + harness 生成的文件指针（T2）；切片继承原文信任等级。

## 4. 信任模型与威胁防御

### 4.1 信任四级

| 级别         | 内容                                                                 | 可否作为指令           | 可否作为授权依据 |
| ------------ | -------------------------------------------------------------------- | ---------------------- | ---------------- |
| **T0** | 系统提示、策略、红线                                                 | 是（唯一最高级）       | 是               |
| **T1** | 用户直接输入（当前轮）                                               | 是                     | 是               |
| **T2** | harness 加工内部数据（快照、trace 摘要、档案事实、生成的指针）       | 有限（视为已核实数据） | 否（需 T1 确认） |
| **T3** | 工具返回、网页、检索召回、MCP 描述、文件内容、**用户粘贴内容** | 否                     | 否               |

**T1 是“通道可信”而非“内容纯净”**——用户粘贴的网页可能内嵌 T3 载荷。分级解决“谁有权授权/下指令”；内容安全扫描对所有级别执行。

### 4.2 五条防御规则

1. **通道隔离**：T3 内容永不拼接进 T0/T1 段；以结构化包裹注入，显式声明 "data, not instructions"；
2. **优先级确定性仲裁**：内容冲突按 tier 裁决，T3 不得覆盖 T0/T1——**仲裁由 harness 确定性执行**，不交模型判断；冲突事件必记录；
3. **权限耦合**：T3 内容不能触发任何权限升级；审批门忽略 T3 中内嵌的指令；
4. **高危动作双通道**：授权必须来自 T1 通道原文。T3 中出现“用户要求删除生产库”不构成授权；
5. **注入检测前置**：T3 入窗前过扫描器（规则 + 模型双层）；可疑 span 以“引用证据 + 警告标注”形式注入，绝不作为指令。
   **验收**：假设 T3 通道被完全操控，系统能造成的最大损害 = T3 注入预算（≤300 tok/轮）内能诱导的、无需权限升级的错误。该上限必须可接受。

### 4.3 注入面治理

所有注入（含前缀、检索召回）过同一 hook 管线：`校验 → 脱敏 → 裁剪 → 结构化注入`。**脱敏在注入之前**——注入什么本身就是权限问题。静态前缀是全系统权重最高且最少被审视的位置，**前缀内容变更须评审**。

## 5. 数据模型与状态机

### 5.1 核心实体

```yaml
Fact {                                # 用户级事实
  fact_id, content,
  category: identity | redline | preference | env | project,
  trust_tier: T0..T3,
  provenance: { origin: user_declared | system_inferred,
                session_ref, span_ref, timestamp },
  confidence: confirmed | inferred | pending_confirmation,
  activation: resident | topic_follow | retrieval,
  scope_tags: [topic_id...],          # 目的限定：决定可注入场景
  expiry: ttl | never | event_based,
  version, status: active | deprecated | tombstoned
}
TopicLine {
  topic_id, title,
  status: active | suspended | archived | merged_into(ref),
  contract_ref,                       # 版本化（§7）
  snapshot_chain: [Snapshot...],      # 只增不改（§8）
  links: [{ target_topic, conclusion_ref, pinned_version }],
  write_lease: { holder, expires_at } | null
}
Snapshot {
  snapshot_id, topic_id, version, parent_version,
  conclusion_layer, evidence_layer, pointer_layer,   # 见 §8
  author: { session_id, model_version }, created_at
}
Trace {
  turn_id, epoch_id,                  # 经 epoch 还原全部前缀身份
  injected: [{ item_ref, item_hash, trust_tier, tokens, rent_cost,
               deletion_tombstone }],
  decision_hashes, structured_action_summaries,      # 模型输出指针化
  security_events, switch_events, contract_events, merge_events
}
```

### 5.2 状态机

**Fact**：`pending_confirmation →（用户确认 / 多采样验证）→ confirmed →（矛盾 / 过期）→ re-verify →（失败）→ deprecated → tombstoned`。**任何跳过确认的转移都是违规**，trace 可查。
**TopicLine**：`active ⇄ suspended → archived | merged_into`。合并与复活均为显式事件（§10）。

### 5.3 用户级事实：五类三分档

| 类别            | 量级           | 激活档位                           | 准入判据                             |
| --------------- | -------------- | ---------------------------------- | ------------------------------------ |
| 身份与账号      | 20–50 tok     | **resident**                 | 缺席则每类决策都错                   |
| 红线约束        | 30–80 tok     | **resident + hook 双轨**     | 属权限策略，版本化                   |
| 全局输出偏好    | 50–150 tok    | **resident**                 | 每次输出都参与                       |
| 环境事实        | 100–300 tok   | **topic_follow**             | 仅相关话题参与；验证跨话题通用后晋升 |
| 项目/领域上下文 | 200–2000+ tok | **topic_follow / retrieval** | 高度局部化，禁止常驻                 |

**resident 层硬约束 ≤500 tok**：每条事实必须能回答“缺席时哪类决策会受损”，回答不了即降级。**窗口内用户事实相关比例**为核心可观测指标，不得随档案增长恶化。   

**写路径门控**：用户显式声明直写（高置信）；系统行为提炼**必须经用户确认或多采样验证**，禁止静默固化。每条事实带元数据（来源、置信度、最后验证时间、关联话题）。会话中新声明的事实本轮经尾部生效；**档案落盘与前缀变更只发生在会话边界**。

## 6. 焦点模型

### 6.1 不变量

> **主焦点任一时刻唯一。一个话题拥有完整上下文，其余话题以指针形态存在、不参与推理。**
> 窗口布局见 §3.1。焦点快照（契约摘要 + 结论层）位于静态前缀区，仅在 epoch 边界变更（切换本身即边界事件）。

### 6.2 焦点事件

| 事件               | 触发                             | 语义                                                                                         |
| ------------------ | -------------------------------- | -------------------------------------------------------------------------------------------- |
| **switch**   | 模型识别话题转移，或用户显式指令 | 替换主焦点：写回旧话题增量 → 取回目标话题快照 → 注入 → 留痕                               |
| **push**     | 嵌套子问题且预期返回             | 焦点入栈；**栈深 ≤3**，超出则栈底降级为背景线程。无返回预期的切题走 switch，不走 push |
| **pop**      | “回到刚才的问题”               | 栈顶出栈恢复                                                                                 |
| **合成注入** | 跨话题比较请求                   | 两个话题结论层摘要各 ≤200 tok 瞬态注入尾部，仅本轮有效，**不产生焦点切换**            |
| **元讨论**   | “你为什么刚才这么说”           | transcript 自身已含答案，无需任何切换                                                        |

被动兜底：未被识别的话题回切，由检索层按相关性召回该话题关键结论作为观察注入。**主动切换与被动召回两层都要有，缺一层就有漏网场景。**切换频率异常升高 = 话题切分粒度或任务定义问题的信号。

### 6.3 背景线程条与惰性失效

- 背景条位于静态前缀区（≤150 tok），每线程一行：标题 + 状态 + 最后活跃；
- **惰性失效**：线程闲置超 **N=10 轮** → 仅打 `pending_consolidate` 标记并写 trace（零缓存影响）；实际移除发生在**下一个 epoch 边界**。设最大滞留 **M=24 轮**，届时无自然边界则强制 epoch bump 兜底；
- 并行任务在 **harness 层**执行（异步 subagent），窗口始终渲染单一叙事，结果以带话题标签的结构化观察回注；用户显式双线并行时，第二线获得 strip 加大型槽位（≤100 tok 摘要）。

## 7. 契约生命周期与修订协议

### 7.1 契约定义

每个话题线持有落盘契约（goal contract）：目标、约束、done 条件、失败条件、预算上限、终止条件。契约是恢复锚点与终止判断的唯一引用源。

### 7.2 风险分级（字段定级，与措辞无关）

> **修改边界的动作，本身就是边界的一部分。** 契约的 H 级字段正是 harness 的治理对象——对它们的修改权放在审批门内，无论请求者是谁、措辞多干净。
>
> | 级          | 字段                                              | 路径                                                                         | 确认形态                                                         |
> | ----------- | ------------------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------- |
> | **L** | 输出格式、语言、详略、称呼、代码风格              | 快路径守卫（7.3）+ 累计防御                                                  | 即时生效 + trace                                                 |
> | **M** | 子目标增删、验收标准调整、期限变更                | 内容扫描 + 影响简述                                                          | 用户轻确认                                                       |
> | **H** | 目标变更、权限范围、预算（时间/token/金钱）、红线 | 内容扫描 +**强制影响分析**（受影响子目标 / 已完成工作处置 / 预算余量） | **读回确认**：harness 复述变更与影响，用户确认后落盘新版本 |
>
> 规则：L 级守卫不过 → 降级按 M 级处理，不拒绝；**T1 直述的 H 级字段同样走读回确认**；分级表随策略参数版本化。

### 7.3 快路径守卫（仅 L 级适用，四条全过才即时生效）

1. 长度 ≤ 200 tok；
2. 结构检查：无代码块 / 引用块 / URL / markdown 链接 / 外语插入段；
3. 指令扫描（规则 + 轻量模型双层）通过：无“新目标 / 新权限 / 忽略此前”类嵌入模式；
4. 语义单一：单一目标陈述，非复合指令包。
   **累计防御**：滚动 20 轮内 L 级快路径变更 ≥3 次 → 后续契约变更一律慢路径，且下一 epoch 边界强制契约复核。分级是硬封顶（L 级任意累积改不出权限/预算变更），累计防御是软漂移控制；守卫误拦截率受监控，持续偏高进失败账本校准。

### 7.4 修订协议状态机

```
ACTIVE ──[模型提请修订]──────► PENDING_REVISION
ACTIVE ──[用户直接陈述（L/M级）]──► ACTIVE（按分级路径，+trace）
PENDING_REVISION ──[用户批准/修改后批准]──► ACTIVE（新版本 vN+1，旧版留存）
PENDING_REVISION ──[用户拒绝]─────────► ACTIVE（拒绝记录；冷却期）
PENDING_REVISION ──[超时]────────────► ACTIVE（默认拒绝，防"挂起漂移"）
```

- 提请必须附影响分析，否则退回；
- PENDING_REVISION 期间执行照常按现行契约，除非用户暂停；
- **拒绝冷却**：同一修订被拒后不得重复提请相同内容超过 1 次；再次出现 → 升级 blocker（防“磨垮用户”式绕过）；
- **回滚 = 新事件**：钉住历史版本开启新 epoch，永不覆盖；契约版本链与快照版本链同构；
- 预算与权限类修订与高危动作同级，走审批门。

## 8. 多粒度快照与摘要偏差防护

### 8.1 三层结构

```yaml
Snapshot:
  conclusion_layer:      # 注意力层：结论、决策、待办（压缩态，可注入）
    - { claim_id, text, evidence_refs: [eid...] }
  evidence_layer:        # 验证层：每条结论的证据
    - eid: e_042
      verbatim_excerpt: "……原文逐字引用（限长）……"
      span_ref: transcript:session_17#turn_23
      content_hash: sha256(...)          # 哈希链：H(excerpt + span + prev_hash)
      source_trust: T1, timestamp
  pointer_layer:         # 全文指针层
    - { type: transcript_span | file | artifact, uri }
```

### 8.2 核心原则与硬规则

> **摘要是缓存，不是真相源。结论层负责注意力，证据层负责验证。**

1. **不可逆动作前强制回源**：任何结论即将驱动不可逆操作时，executor 向证据层取原文逐字核对——`content_hash` 验证未被篡改，以原文而非摘要作为决策依据。摘要偏差在造成损害之前被拦截；
2. **关键决策必须有 evidence 条目**：无证据引用的“决策”降级为“假设”，**不参与恢复锚点**；
3. 哈希链提供篡改检测：证据被事后修改 → 链断裂 → 审计告警。

## 9. 检索管线与依赖度评分

### 9.1 管线

```
触发 → 召回（外部、廉价）→ [条件触发] 重排（模型、限额）→ 信任标注 → 预算门 → 注入
```

| 环节     | 设计                                                                      | 成本控制           |
| -------- | ------------------------------------------------------------------------- | ------------------ |
| 召回     | 混合 ANN + BM25；embedding 以 content_hash 为键缓存；索引增量更新         | 毫秒级、确定性     |
| 重排     | 仅在召回 top-k 分数平坦/歧义时触发；小模型；**硬限额 ≤1 次/10 轮** | 例外路径而非默认   |
| 预取     | 事件驱动：topic switch 预取目标话题快照；里程碑预取相关结论；异步执行     | 零在线延迟         |
| 信任标注 | 每条召回物入窗前打`trust_tier + provenance 链`                          | hook 管线内        |
| 预算门   | T3 ≤300 tok/轮；按 tier 分配注入预算                                     | harness 确定性执行 |

### 9.2 依赖度评分规格

```
score = 0.4·affinity + 0.3·explicit_ref + 0.2·recency + 0.1·phase_match
affinity     scope_tags ∩ 焦点话题 的 Jaccard；无 scope_tags 取 0.5（中性）
explicit_ref 检测到显式引用信号（"上次说的X"、指代消解）= 1，否则 0
recency      exp(−Δturns/τ)，τ = 20 轮
phase_match  当前任务阶段 ∈ 该事实适用阶段集合（布尔）
θ_auto = 0.7（≥ 直接注入，不消耗模型注意力）
θ_low  = 0.4（< 不注入；两者之间交重排 judge，限额内）
```

| 问题       | 方案                                                                                                         |
| ---------- | ------------------------------------------------------------------------------------------------------------ |
| 冷启动     | 上表先验默认值；**方向保守**（θ 偏高，宁可少注），靠漏召回率在线校准                                  |
| 先验→学习 | 积累 ≥500 标注轮次（回归集 + 在线采样）后转学习校准                                                         |
| 调参流程   | 离线网格扫描 → 目标函数 max(Δ成功率 − λ·token成本) → 参数新版本 → 回归门禁 → 上线（λ 由回归集标定） |
| 回退路径   | 评分器故障/超时 → 降级为“仅显式引用信号注入”（最保守通路）                                                |
| 在线校准   | auto-inject 子集 precision < 0.8 → θ_auto 上调；漏召回率超阈值 → θ_auto 下调                             |

**漏召回兜底**：低置信场景降级为宽召回；用户重述了我们应有的信息 → 记为漏召回事件，进失败账本。

## 10. 并发与版本控制

| 机制                             | 规则                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **不可变版本链**           | Snapshot 只增不改 → 并发读天然安全；TopicLine 状态字段是唯一可变项                                     |
| **写租约**                 | 同一话题同一时刻至多一个活跃写者（soft lease + TTL）；并发写第二者进冲突队列，绝不静默覆盖              |
| **版本向量**               | `ContextEpoch.composed_of` 五元组即坐标——任意时刻窗口状态可完整重建，任意两时刻可精确 diff          |
| **引用钉版**               | 话题 A 引用 B 的结论 → pin 具体版本；B 修订后 A 的引用标记“过期”并通知依赖方——**引用不悬空** |
| **合并策略**：             |                                                                                                         |
| 冲突类型                         | 策略                                                                                                    |
| ----------                       | ------                                                                                                  |
| 加性字段（decisions/todos 追加） | 自动合并                                                                                                |
| 叙事/结论矛盾                    | 三方合并 + 模型辅助 diff +**用户裁决**；矛盾进冲突队列，写审计                                    |
| 话题合并（A 并入 B）             | 显式事件：B 增量写回、A 转`merged_into`、A 的引用重定向并通知                                         |
| 变体复活                         | 以新 TopicLine 挂接原话题 link 的方式复活，不复活原线本体——保持历史不可变                             |
| 全部合并事件写`merge_events`。 |                                                                                                         |

## 11. 隐私合规与记忆管理

### 11.1 六项用户操作

| 操作 | 系统效果                                         |
| ---- | ------------------------------------------------ |
| 查看 | 全量事实 + 话题线，逐条展示 provenance           |
| 编辑 | 产生新版本，旧版留痕，永不覆盖                   |
| 删除 | 硬删 +**墓碑**（防从残留再学习）+ 级联清理 |
| 导出 | 可携带格式（JSON bundle 含 provenance）          |
| 暂停 | 本会话临时排除注入，不删数据                     |
| 纠错 | 标记事实错误 → 触发 re-verify，非静默修正       |

### 11.2 删除级联（GDPR 删除权）

删除覆盖：**档案 → 检索索引/向量 → 前缀旧版本退役（epoch bump）→ 快照 tombstone → trace 回写 tombstone**。embedding 必须可删；transcript 原文与删除权的张力显式交用户选择（删除 vs 留存），默认从紧。

### 11.3 其余合规要点

- **目的限定**：`scope_tags` 即用途约束；resident ≤500 预算同时是数据最小化的工程体现；
- **可逆令牌化**：脱敏层输出 token 入窗，明文存 vault；vault 访问需权限 + 全审计；高敏类别（证件号等）不可逆哈希剔除，永不入 vault；
- **权限分层**：用户级事实与组织共享事实分离读写权限。

### 11.4 Trace 指针化

trace **只存引用，不存明文**：`item_ref + item_hash + trust_tier + tokens + rent_cost`；模型输出同样指针化（决策哈希 + 结构化动作摘要），完整输出入可删存储。审计重建的诚实降级：明文已删条目显示 tombstone（“已于 X 时被用户删除，指纹 h=…”）——**结构完整性永存，内容完整性随删除权合法降级，且降级本身可审计**。

## 12. 评估、指标与可观测性

### 12.1 ROI 归因：抽样审计而非账目

| 层           | 内容                                                                                                                               |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| 在线（永远） | 只记 proxy：注入物采用率、下游引用信号。不做回放，不宣称因果                                                                       |
| 离线（抽样） | 失败账本 episode**抽样** → with/without 双配置回放 → 每配置 k≥5 次采样 → 报告 **mean ± 95% CI**，采样种子入 trace |
| 声明         | “边际成功率”是**统计相关，非严格因果**；ROI 用于排序注入类型的相对价值，不用于精确记账                                     |

低 ROI 自动降频的触发条件：**CI 上界仍低于成本线**（保守决策）；样本量不足的 cell 标注“证据不足”，不得驱动降频/移除决策。

### 12.2 指标体系

| 指标              | 定义 / 健康信号                                                 |
| ----------------- | --------------------------------------------------------------- |
| 任务成功率        | episode 级，对照回归集基线                                      |
| 重建成功率        | 会话级（P0）/ 话题级（P2），任意中断点恢复完整性                |
| 漏召回率          | 用户重述我们应有的信息的事件占比                                |
| 冗余冲突率        | 窗口内检测到的矛盾注入对数                                      |
| 每轮未命中基线    | ≈ 尾部区 ≤1500 + 历史增量；两类泄漏（epoch / append）独立告警 |
| 缓存节省          | read_tokens × 价差，按 epoch 分解                              |
| 租金 ROI          | §12.1，按注入类型分解，带 CI                                   |
| 切换 / epoch 频率 | 异常升高 = 粒度或任务定义问题                                   |
| T3 安全事件数     | 含被拦截的注入尝试（留痕本身即信号）                            |
| 依赖度判断器质量  | auto-inject precision/recall vs 事后归因真值                    |
| 守卫误拦截率      | 正常修订请求被降级的比例                                        |

### 12.3 策略参数版本化

全部策略参数（θ、注入预算、信任规则、焦点栈深、strip N/M、压缩阈值、输入上限、分级表）版本化管理；**变更必须在回归集过门槛后上线**，与代码相同的评审流程。每个策略/组件可追溯至一次具体失败，说不清即为冗余。

## 13. MVP 路线图

**原则：每阶段独立可上线、独立可回滚，后一阶段不阻塞前一阶段的价值兑现。**
**纪律：任何门禁只能引用当期交付清单中存在的机制。**（评审时逐条断言；引用未来机制的门禁视为文档错误。）

### P0 —— 最小闭环

| 交付     | 三区布局落地；epoch 版本号；append-only 纪律；尾部 state 注入；三计数监控 + 两类泄漏告警                                                                                                        |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 默认参数 | resident ≤500；尾部 ≤800（仅 state + 输入）；压缩阈值 0.6/0.25·W；输入 ≤4000                                                                                                                |
| 门禁     | ①**会话级恢复**：同一会话任意点中断后跨日续跑，窗口由 checkpoint + transcript + 尾部 state 重建，模型不依赖丢失的工作记忆继续任务；② 每轮未命中 ≈ 预测值（±10%）；③ 前缀泄漏告警为零 |

### P1 —— 安全底座

| 交付 | T0–T3 标注贯通全链路；hook 管线（校验→脱敏→裁剪）；契约风险分级表 + 快路径守卫；trace 指针化 + vault  |
| ---- | -------------------------------------------------------------------------------------------------------- |
| 门禁 | ① T3 全操控损害上限演练通过；② 高危授权 100% 溯源至 T1 原文；③ 删除级联演练通过（含 trace tombstone） |

### P2 —— 记忆完整形态

| 交付 | 话题线 + 三层快照 + 哈希链；不可逆动作回源校验；检索管线（召回 + 预算门，重排限额接口预留）；依赖度评分 v0（仅确定性项，先验参数）；契约修订协议全状态机                                     |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 门禁 | ① 回放集中“未回源即执行不可逆动作”为零；② auto-inject precision ≥ 0.8（先验参数下）；③ 漏召回率不高于 P1 基线；④**话题级重建**：跨会话中断多日的任务从话题线快照 + 契约完整重建 |

### P3 —— 治理完备

| 交付                                                                                     | 写租约 + 合并策略 + 引用钉版；焦点栈 + strip 惰性失效；UX 六操作 + GDPR 级联；ROI 离线抽样审计；策略参数版本化上线流程 + 回归门禁 |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 门禁                                                                                     | 验收表全绿；每个策略参数有版本号与回归记录                                                                                        |
| **刻意延后**：模型重排（P2 只留限额接口）、ROI 驱动的自动降频（P3 才有可信数据）。 |                                                                                                                                   |

## 16. AGI 动态边界与设计哲学

| 部件                                                                                    | 属性 | AGI 后                                       |
| --------------------------------------------------------------------------------------- | ---- | -------------------------------------------- |
| 压缩/摘要策略、检索排序、话题归属判定、依赖度评分的学习化                               | 认知 | 被模型吸收，**策略可插拔、可优雅退场** |
| 分层持久化、话题隔离、信任分级与注入权限、脱敏、版本链、哈希链、trace、删除级联、写租约 | 治理 | **永存，且更重要**                     |
| 预算数值、θ 阈值、栈深等参数                                                           | 策略 | 随模型能力重标定                             |
| **设计不变量**：                                                                  |      |                                              |

> **每一步的“判断”由模型做出，每一步的“事实”由 harness 记录。**
> 任何时刻停下，都能从存储层与 trace 重建“模型当时看到了什么、决定了什么、harness 执行了什么、环境发生了什么”。
> 好 harness 的标志不是复杂，而是**每一行都可被删除**——策略因具体失败而存在，骨架因环境属性而永存。Context Manager 的全部工作，是把轮内、会话内、跨会话三个时间尺度的“写回”与“取回”收敛为同一条确定性管线；它不需要让模型更聪明，它负责让模型在每一轮、每个话题、每次恢复时，窗口里恰好只有“如果缺席就会错”的那一小块信息——其余一切住在外部，可检索、可重建、可审计、可删除。
