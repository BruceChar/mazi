
# 用户行为流与认知画像设计

> 版本：v2.0 · 状态：设计定稿
> v2.0：新增「用户行为指令」分类（授权独立于反馈）、审批发起锚点，以及行为流 → Step 时间线的只读投影（§10）。

## 1. 目标与原则

**目标**：把用户的全部行为记录为一条追加式的 JSONL 事件流，作为可携带的用户资产；任意分析器消费该流产出画像报告。换框架、换模型，流与画像随用户迁移。
**核心原则**：

1. **只记用户行为**：不记模型推理、不记执行轨迹。用户是什么样的人，体现在输入的问法、反馈的时机与内容、授权决策、中断点、设置调整——这些全部是流中的行。唯一例外是审批发起锚点（`approval`）：它只记录「用户看到的审批请求」这一必要摘要，用于定位授权与计算延迟，不含执行轨迹（§10.3）。
2. **事实与解释分离**：流只存可机械观测的事实；所有“用户是什么样”的判断在分析层生成，且必须附证据。
3. **追加不可变**：流 append-only，历史行永不修改。结构信号（会话归属、位置、间隔、节律）由流顺序派生，不显式存储。
4. **ts 即 id**：时间戳就是事件的唯一标识，也是证据引用与 ref 指向的依据。不引入任何 ID 体系。
5. **有数据补数据**：所有可选字段缺失即缺失，分析器不臆测。这是采集端与版本演进的共同约定。
6. **投影只读**：用户行为与 Step 时间线的合并是派生视图，纯函数、确定性、不写库、不改 GTS StepKind（§10.4）。

## 2. 数据模型

### 2.1 统一信封

```ts
interface StreamEvent {
  ts: number;              // 事件 id（规则见 §3）
  type: 'input' | 'feedback' | 'authorization' | 'approval' | 'setting' | 'session';
  ref?: Ref;               // 子行为/关联指向；独立事件无 ref
  data: object;            // 按 type 定义，见 2.3
}
```

### 2.2 Ref 对象

```ts
interface Ref {
  ts: number;              // 指向目标事件的 ts
  /** 有数据补数据：被指向对象的输出侧机械事实，捕获时盖章，全字段可选 */
  anchor?: {
    tokens?: number;       // 产出规模
    durationMs?: number;   // 产出耗时
    hadError?: boolean;    // 是否包含错误
  };
}
```

anchor 解决的问题：数值评分只有 ref 时退化为“不满频率计数”——不知道评的是啰嗦还是错误。anchor 是**被评价物的客观事实**（多长、有没有错），不是模型解释，几个字节，有则盖、无则空。

### 2.3 事件类型

| type（记录）      | ref                              | data                                                      | 说明                                                                                                             |
| ----------------- | -------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `input`           | 可选，指向被重问的上一条 input     | `{ text, drafts?: string[] }`                             | 用户问题/一次提交。**草稿修改不独立成行**，作为 `drafts` 并入——草稿先于提交存在，独立成行会导致 ref 指向未来事件 |
| `feedback`        | 指向所属 input，含 anchor         | `{ kind, ... }`（见下表）                                 | 用户反馈                                                                                                         |
| `authorization`   | 指向配对的 `approval`，含 anchor  | `{ decision: 'granted'\|'denied', scope?, latencyMs? }`   | 用户授权行为（原 `feedback.kind=approval`）；latencyMs 由两侧服务器时刻计算，可靠                                 |
| `approval`        | 无                               | `{ summary, approvalKey?, capability?, allowedScopes? }`  | **审批发起锚点**：用户看到什么由此记录；流中唯一 `harness` 来源记录                                             |
| `setting`         | 无                               | `{ key, value }`                                          | 换模型、调权限、改偏好——用户在流上打的独立标记                                                                 |
| `session`         | 无                               | `{ action: 'open'\|'switch', title? }`                    | 会话边界行                                                                                                       |

`approval` 是流中唯一 `harness` 来源记录，其余均为用户行为。

`feedback.kind`：

| kind        | 字段                            | 语义                                                                 |
| ----------- | ------------------------------- | -------------------------------------------------------------------- |
| `rating`    | `rating: 1-5`                   | 输出评价。anchor 的主要服务对象                                      |
| `text`      | `text`                          | 文本反馈（含“别用××”类决策更改的口头形式；做出来的更改走 setting） |
| `interrupt` | `at: number`（0-1，中断时进度） | 主动中断                                                             |

### 2.4 结构信号派生规则（不存储）

- **会话归属**：session 行与下一个 session 行之间的所有事件属于该会话；
- **位置/间隔**：input 的会话内序号、相邻 ts 差；
- **重问对比**：input.ref 指向的两条 input 直接 diff；
- **节律**：全流 ts 的时段直方图。

### 2.5 流示例

```jsonl
{"ts":1725678900000,"type":"session","data":{"action":"open"}}
{"ts":1725678940123,"type":"input","data":{"text":"这个设计有什么根本问题？","drafts":["这个设计有什么问题？"]}}
{"ts":1725679012345,"type":"feedback","ref":{"ts":1725678940123,"anchor":{"tokens":8200,"durationMs":43000}},"data":{"kind":"rating","rating":2}}
{"ts":1725679020000,"type":"feedback","ref":{"ts":1725678940123},"data":{"kind":"text","text":"太啰嗦，直接说结论"}}
{"ts":1725679110456,"type":"input","ref":{"ts":1725678940123},"data":{"text":"用三句话回答这个设计有什么根本问题"}}
{"ts":1725680000000,"type":"setting","data":{"key":"model","value":"gpt-x"}}
{"ts":1725680100000,"type":"approval","data":{"summary":"shell.run: rm -rf build","capability":"shell.run","allowedScopes":["once"]}}
{"ts":1725680104500,"type":"authorization","ref":{"ts":1725680100000},"data":{"decision":"granted","scope":"once","latencyMs":4500}}
```

## 3. 时间戳规则

1. **ts = 服务器接收时刻**，不用客户端时钟（防回拨、多设备漂移）；
2. **全局单调**：写入端强制 `ts = max(now, lastTs + 1)`——同一次表单提交产生多条事件（评分+评论）、历史数据回填、批量导入都是机器速度写入，此守卫使“ts 即 id”永远成立，不再依赖任何行为速度假设；
3. 语义上 ts 表示“服务器记录时刻”而非行为物理时刻，对画像分析无影响；
4. **证据引用、ref 指向，一律是 ts**。

---

## 4. 存储

- 单一 JSONL 文件（按用户分文件或按时间滚动），追加写入；
- 历史行永不修改、永不删除（删除是治理操作，见 §6 导出与假名）；
- 存储格式 = 导出格式（§6），无转换层。

## 5. 画像报告

```ts
interface ProfileReport {
  schemaVersion: string;              // 'profile-report/1.0'
  subjectId: string;
  strategy: {                         // 生成本报告的分析策略标识
    analyzerId: string;
    analyzerVersion: string;
    model: string;
    promptVersion: string;
  };
  generatedAt: number;
  streamRange: [firstTs, lastTs];     // 消费的流范围
  dimensions: {
    id: string;                       // 'cognitive.verification-habit'
    status: 'established' | 'insufficient';
    value: string | number | object | null;   // insufficient 时必须 null
    confidence: number;               // 0-1：证据量 × 一致性 × 时效
    evidence: number[];               // 流中真实存在的 ts 列表
  }[];
  features: MechanicalFeatures;       // §5.2，确定性计算，不依赖 LLM
  contentHash: string;                // sha256(规范化序列化)
}
```

### 5.1 生成规则

1. **机械验收门**：报告落盘前校验每个 evidence ts 在流中真实存在——防分析器编造证据，这是可信度地基；
2. **可复现**：同流（同 streamRange）+ 同 strategy → 同 contentHash。画像结论可被第三方独立审计；
3. **换分析器**：不比对 hash，产出逐维度差异对照，由用户/下游决定采纳；
4. **宁缺毋滥**：证据量低于阈值（默认 8 条）→ `insufficient`、`value: null`，不出结论。

### 5.2 机械特征层

从流确定性可算，零 LLM 成本，独立于任何分析器存在：
输入长度分布、问句率、结构化格式使用率、草稿修改率、评分均值与走势、文本反馈语义信号、中断进度分布、授权决策延迟分布、拒绝率、重问率与改写幅度、会话间隔分布、活跃时段直方图、setting 变更频率与类别分布。
用途：分析器的输入底座；LLM 分析不可用/被禁用/匿名降级时的存活层。

### 5.3 维度起步集

| 维度                                                         | 值类型      | 主要证据                                   |
| ------------------------------------------------------------ | ----------- | ------------------------------------------ |
| `cognitive.planning-style`                                 | categorical | 重问模式、草稿行为、输入结构               |
| `cognitive.abstraction-level`                              | ordinal     | input 语言特征                             |
| `cognitive.verification-habit`                             | categorical | 授权延迟/拒绝、中断点、反馈时机            |
| `temperament.patience`                                     | ordinal     | interrupt.at 分布、间隔                    |
| `temperament.cost-sensitivity`                             | ordinal     | rating × anchor(tokens/duration) 相关性   |
| `values.quality-signals`                                   | signal-set  | text feedback 内容、低分场景的 anchor 对比 |
| `values.priority-ordering`                                 | ranking     | rating 与规模/耗时/正确性的相关性结构      |
| 分类法可扩展（`id` 开放），注册表随 schemaVersion 版本化。 |             |                                            |

## 6. 导出与携带

导出 = **文件头 + 流切片（原样逐行拷贝）**，零转换：

```jsonc
{"format":"user-behavior-stream","schemaVersion":"1.0",
 "subject":{"id":"...","identity":"real"|"pseudonymous"},
 "range":[firstTs,lastTs]}
{"ts":...,"type":"input","data":{...}}
...
```

- 假名导出：替换 subject.id；可选剥离文本（保留结构信号与机械特征，匿名画像好过没画像）；
- 新环境消费流程：读文件头 → 迁移（§7）→ 逐行消费 → 机械特征立即可用 → 重算或沿用画像报告。

## 7. 版本与迁移

三层版本，各管各的：

| 层         | 载体                         | 规则                                                   |
| ---------- | ---------------------------- | ------------------------------------------------------ |
| 数据格式   | 文件头`schemaVersion`      | semver；加可选字段、加枚举值 = minor；破坏兼容 = major |
| 报告内容   | 报告内 dimensions + 重新生成 | 派生物，随时可重算                                     |
| 分析方法   | 报告`strategy`             | 换策略 → 不比 hash，比维度差异（§5.1-3）             |
| 迁移机制： |                              |                                                        |

1. 读取器接受所有 ≤ 自身 schemaVersion 的导出；
2. 按版本链执行迁移函数（`migrate_1_to_2 → migrate_2_to_3`），行为同数据库 migration；回填数据逐条过单调守卫（§3）；
3. 每个历史版本留存 fixture 导出，CI 回归：**三年前导出的流今天仍可读可分析**。

## 8. 验收标准

| # | 验收项       | 标准                                                    |
| - | ------------ | ------------------------------------------------------- |
| 1 | ts 唯一性    | 全流无重复 ts，含批量导入与回填之后                     |
| 2 | ref 完整性   | 所有`ref.ts` 可解析到流中真实事件                     |
| 3 | 证据真实性   | 报告 evidence 全部存在于流，机械校验拒绝编造            |
| 4 | 可复现       | 同流 + 同 strategy → 同 contentHash                    |
| 5 | 旧版可读     | CI fixture 回归：各历史版本导出可被当前读取器迁移并消费 |
| 6 | 追加不变     | 流文件历史字节永不重写（文件级校验）                    |
| 7 | 机械特征独立 | 关闭 LLM 分析后 features 层可完整计算                   |
| 8 | 纯用户行为   | 流中不出现模型推理、执行轨迹、框架内部 ID               |
| 9 | 行为单独成条 | 问题/反馈/授权/审批发起各自一条；`rating` 与 `text` 不合并 |
| 10 | 投影只读确定 | `projectBehaviorTimeline` 同输入同输出；不修改 Step、不新增 StepKind |
| 11 | 时间线顺序   | 用户问题在首个 Step 前；授权行紧跟其审批发起行；反馈按 ts 插入 |

## 9. 定稿的设计决定及其理由（备查）

| 决定                              | 理由                                                                  |
| --------------------------------- | --------------------------------------------------------------------- |
| 砍协作证据、砍 inputMeta          | 画像对象是用户；打字时长被上厕所污染，不可信                          |
| ts 即 id（服务器时刻 + 单调守卫） | 表单多事件同毫秒、导入回填是设计内生场景，守卫 5 行代码使假设永久成立 |
| 草稿并入 input.drafts             | 草稿先于提交，独立成行会 ref 指向未来事件                             |
| ref 为对象（ts + anchor）         | 定位与“被评价物事实”分离；anchor 有则补，兼容演进                   |
| decision_change 不设独立 kind     | 说出来的 → text feedback；做出来的 → setting。两种形态已覆盖        |
| 导出 = 文件头 + 切片              | 存储即资产，无独立 Bundle 概念                                        |
| 机械特征层独立于 LLM              | 冷启动、审计、匿名降级三重用途                                        |
| `authorization` 独立于 feedback | 授权是用户决策资产，独立成条才能重建授权行为链与延迟分布              |
| 用户行为不写入 Step               | GTS 二分为归因原子、行为流为可携带用户资产，生命周期与消费者不同      |
| 投影是只读纯函数                  | client/server 同输入同输出可对拍；删除投影不伤行为流与 Step 原始事实  |

## 10. 用户行为指令与 Step 投影（v2.0）

### 10.1 术语

- **用户行为指令（UserBehaviorInstruction）**：用户行为流中的一条记录，代表一次可机械观测的用户行为；三类——问题（`input`）、反馈（`feedback`）、授权（`authorization`）。
- **审批发起锚点（`approval`）**：与用户授权成对的系统事实，记录「用户看到了什么审批请求」；流中唯一非用户行为记录，仅用于授权定位与延迟计算。
- **Step 投影（Behavior Step Projection）**：把用户行为流与 Goal/Task/Step 快照按时间合并为一条只读时间线的纯函数；**不新增 StepKind、不写入 `goal_steps`**。

### 10.2 为什么独立成流而不写入 Step

- GTS 的 Step 是**归因原子**，`kind` 严格二分（`deliberation | invocation`）；用户行为既非模型内在，也非 harness 对外部世界的一次调用，塞入 Step 会破坏 `step.kind → step.payload` 的唯一判别式（AHF_CORE_GTS §3.3）。
- 用户行为流面向**可携带的用户资产**（跨框架迁移、画像分析）；Step 面向**单次运行的执行归因**。二者生命周期与消费者不同，硬合并会让删除任一方都伤及另一方。
- 投影是只读派生物：删掉投影，行为流与 Step 两边的原始事实都不受损。

### 10.3 线协议视图

```ts
/** 一条用户行为指令（api/webui 共享视图） */
export interface UserBehaviorView {
  ts: number;                       // 事件 id = 排序依据与证据引用
  type: 'input' | 'feedback' | 'authorization' | 'approval' | 'setting' | 'session';
  ref?: { ts: number; anchor?: { tokens?: number; durationMs?: number; hadError?: boolean } };
  data: Record<string, unknown>;    // 按 type 收窄，见 §2.3
}
```

记录来源与对齐现有事件：

| 记录            | 来源    | 对齐现有事件                            | 说明                                                   |
| --------------- | ------- | --------------------------------------- | ------------------------------------------------------ |
| `input`         | user    | `user.input.recorded`                   | 用户问题/一次提交                                      |
| `feedback`      | user    | `user.feedback.captured`                | 用户反馈（rating/text/interrupt）                      |
| `authorization` | user    | `approval.granted`/`approval.cancelled` | 用户授权行为；`ref` 指向配对的 `approval`              |
| `approval`      | harness | `approval.requested`                    | 审批发起锚点；**流中唯一 `harness` 来源记录**          |

> v2.0 变更：原 `feedback.kind=approval` 提升为独立 `authorization` 类型；新增 `approval` 锚点类型。v1 未落地，无历史迁移负担；若已有 v1 数据，按 `feedback.kind=approval → authorization` 迁移（§7）。

### 10.4 Step 投影契约

```ts
/** 时间线条目：Step 与用户行为指令的只读合并视图 */
export type TimelineEntry =
  | { source: 'step'; at: number; step: StepView }
  | { source: 'behavior'; at: number; behavior: UserBehaviorView };

/** 纯函数：会话内 Step（按 startedAt 升序）+ 用户行为流 → 按时间合并的只读时间线 */
export function projectBehaviorTimeline(
  steps: readonly StepView[],
  behaviors: readonly UserBehaviorView[],
): TimelineEntry[];
```

规则：

1. `at`：Step 取 `startedAt`；行为取记录 `ts`（`approval` 锚点取其自身 `ts`）。
2. 按 `at` 升序；同 `at` 时**行为在前、Step 在后**，保证用户问题渲染在首个模型 Step 之上。
3. 同 `at` 同源按 `ts` 稳定排序，结果确定：同输入 → 同输出，可缓存、可 client/server 对拍。
4. 投影只读输入，**不修改 Step、不落库、不新增 StepKind/Step**。
5. 顺序完全由 `ts`/`startedAt` 决定；`ref` 只服务画像与证据引用，不参与定位。

### 10.5 写入点与存储

| 行为          | 写入点                                                 | 记录                                                   |
| ------------- | ------------------------------------------------------ | ------------------------------------------------------ |
| 用户问题      | `HarnessRuntime.createGoalSession`（会话创建/首次执行） | `input`                                                |
| 用户反馈      | `HarnessRuntime.recordFeedback`                        | `feedback`                                             |
| 审批发起      | `ApprovalBroker.decide`（创建 waiter 时）              | `approval`                                             |
| 用户授权      | `ApprovalBroker.settle(..., by:'user')`                | `authorization`（含 `latencyMs = now − requestedAt`）  |
| 审批超时/停机 | `ApprovalBroker.settle(..., by:'timeout'\|'shutdown')`  | 只发 `approval.cancelled` 事件，**不记 `authorization`**（非用户行为） |

> 决策值映射：用户结算 `granted` → `authorization.decision='granted'`；`rejected` → `'denied'`；`cancelled`（TTL 超时/停机关闭）不是用户行为，不记 `authorization`。若未来 UI 支持用户主动取消待审，按 `'denied'` 记并在 `data.reason` 标注。

存储沿用 §4：append-only JSONL，按运行会话分文件 `~/.mazi/behavior/<rootGoalId>.jsonl`，文件头见 §6；写入端沿用 §3 的全局单调守卫。事件总线与行为流双写：事件是实时通道，行为流是用户资产（与 AHF_CORE_OBSERVATION 的 append-only、双写原则同构）。记录失败必须留系统日志，不静默吞掉（AGENT.md §7）。

### 10.6 接口与 UI

- `GET /api/sessions/:id/timeline`：`GoalTreeSnapshot` **加法**增加可选 `behaviors: UserBehaviorView[]`；旧消费端忽略即可。
- WebUI 对话流/轨迹：对 `projectBehaviorTimeline` 的输出渲染——Step 行沿用现有卡片；**行为行**按类型区分样式：问题（用户气泡）、反馈（👍/👎/文本）、授权（`granted`/`denied` + scope + latencyMs）、审批发起（警示卡片 + 摘要）。**审批发起与用户反馈都必须出现在 Step 时间线中**（本条款的直接要求）。
- 审计面板（观测看板）**不纳入**行为行：行为没有 vendor/runtime/cost 事实，避免用零值污染用量口径；行为详情就地展示（摘要 / 决策 / 延迟）。
- 实时：`approval.requested` → `approval` 行；`approval.granted/cancelled` → `authorization` 行；`user.feedback.captured` → `feedback` 行；SSE 增量刷新。
