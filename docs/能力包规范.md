# 能力包（Capability Package）规范与个人助理功能接入设计

> 版本：v0.1 · 状态：设计草案
> 范围：packages/skills（新增 monorepo 包）、packages/core（能力包契约类型）、packages/runtime（注册表 / 激活 / 调度 / 通道适配）、apps/api（只读查询）。
> 关系：复用 docs/用户问题标签与分类设计.md 的意图标签作为激活判据；复用 docs/core/AHF_CORE_TOOL-GATEWAY.md 的工具契约与权限/审批机制；对齐 docs/ProviderAdapter设计.md 的适配器注册模式；**与 docs/模型目录与计费实施设计.md 的 catalog（模型目录）命名区分**，能力注册表是新建模块，不复用 catalog。

---

## 1. 目标与范围

个人助理类功能（成功日记、身材管理、财务理财，以及后续的通知提醒系统、微信/飞书等消息通道）以**什么样的存在形态**进入 mazi，是本文要回答的问题。

**结论先行**：

1. **领域功能**（成功日记 / 身材管理 / 财务理财 …）= **能力包（Capability Package）**，落在新增的 `packages/skills/`，每个功能一个包，**意图路由指令激活**，任务结束即卸载，不常驻。
2. **平台能力**（通知/提醒调度、消息通道适配、记忆、权限、审计）= **进 harness 核心/运行时**，领域无关，任何能力包不得感知或实现。
3. 能力包是「**manifest + 工具集 + 记忆 schema + 模板/校验规则**」的声明式组合，不是独立 Agent，也不是写进核心的函数库。

**目标**：新增任何个人助理功能 = 新增一个能力包目录 + 注册表自动发现，核心代码零改动；权限、审批、记忆、审计、事件全部自动继承 harness 既有机制。

**非目标（本期）**：多能力包组合编排；能力包远程分发/市场；多用户鉴权；微信/飞书真实接入（外部授权与风控成本高，独立排期）；复杂 cron 语义调度。

## 2. 形态决策：为什么是能力包

| # | 候选形态 | 与 mazi 架构的冲突 | 结论 |
| --- | --- | --- | --- |
| CP-1 | **独立 Agent 库**（每个功能一个 Agent） | 破坏法律 1「归因链闭合」：独立 Agent 的 Goal 无法回溯到 human/system 根，产生孤儿动作；每个 Agent 重复实现 harness 职责（权限/记忆/审计）；权限治理组合爆炸。需要多角色协作时，用 Goal 树既有的委托边（权限上限递减）即可 | 否 |
| CP-2 | **功能函数库**（领域代码进 core/runtime） | 违反 OCP：每加一个功能改一次核心；领域需要的是「数据结构 + 规则 + 工具」的声明式组合，不是函数集合；领域逻辑会泄漏进 harness 事实层 | 否 |
| CP-3 | **指令激活的内置功能**（路由 if/else 写死在运行时） | 与 CP-2 同源问题：新增功能必须改路由代码；分类法与能力列表无法数据驱动 | 否 |
| CP-4 | **能力包**（manifest + 工具 + 记忆 schema + 模板/校验，注册表驱动，意图路由激活） | 复用 ToolGateway / EventBus / 记忆支柱 / authz / ledger；新增 = 加包；核心只做一次性的通用扩展（handler 型工具注册口、能力事件类型） | **是** |

### 2.1 判定逻辑

- 能力包不是「模型判断」：它声明**事实与边界**（工具能做什么、数据长什么样、什么规则必须遵守）——这正是 harness 的职责，交给包；模型在其边界内做概率性判断。
- 能力包挂载 = 一次**委托**：沿用法律 2「治理上限单调递减」，包内工具的权限天花板由 manifest 声明，不得突破当前 Goal 的 ceiling。

## 3. 总体架构：平台横向 vs 领域纵向

```
用户入口（WebUI / 微信 / 飞书 / …）
   │  平台层：ChannelAdapter 归一化为统一消息
   ▼
意图路由（复用 question taxonomy：speech_act + domain/category + 关键词）
   │  命中
能力注册表 CapabilityRegistry ──── 读取 manifest（启动时扫描 packages/skills/*）
   │
   ├──────────────┬──────────────────────────────┐
   ▼              ▼                              ▼
领域能力包（纵向）  平台横向能力（harness，领域无关）  执行闭环（不动）
packages/skills/   · event-bus + 提醒调度器        Goal → Plan → Execute
success-diary      · ChannelAdapter（微信/飞书/…）  → Observe → Reflect
body-management    · 记忆支柱（命名空间隔离）        两法律自动约束每个能力包
finance            · authz / 审批 / ledger
```

- **纵向**：能力包只声明「自己的领域」；横向：平台能力只提供「通用机制」。纵向可增可减，横向稳定演进。
- 能力包通过挂载点（ToolGateway 注册 + 记忆命名空间 + 模板注入 + 事件订阅）进入执行闭环，闭环本身不感知任何具体领域。

## 4. 能力包目录结构

```
packages/skills/
├── success-diary/                 # 能力包 id（kebab-case，全局唯一）
│   ├── manifest.json              # 能力包元数据（规范见 §5）
│   ├── tools/
│   │   ├── diary.append.json      # ToolConfig 声明（JSON Schema）
│   │   └── diary.summary.json
│   ├── handlers/
│   │   ├── diary.append.ts        # 工具实现（导出注册函数，见 §6.1）
│   │   └── diary.summary.ts
│   ├── memory/
│   │   └── schemas.json           # 状态模型（entries / streaks 集合的 JSON Schema）
│   ├── templates/
│   │   ├── append-prompt.md       # 提示模板（可含 {{变量}}）
│   │   └── summary-prompt.md
│   ├── validators/
│   │   └── entry.ts               # 纯函数校验器
│   ├── events.ts                  # 领域事件声明与发射助手
│   └── README.md                  # 领域边界、术语、数据语义、提醒规则示例
├── body-management/
└── finance/
```

约定：

- 包内文件一律**声明式优先**（JSON Schema / markdown / 纯函数），不依赖包级运行状态。
- 包与包之间**零依赖**（本期）；公共能力只允许引用平台层。
- 每包自带 `README.md` 说明领域语义，作为包内模板/校验规则的唯一权威解释。

## 5. Manifest 规范

`manifest.json` 是能力包的唯一入口，注册表启动时扫描并校验。

```jsonc
{
  "id": "success-diary",                 // 必填：kebab-case，全局唯一
  "version": "0.1.0",                    // 必填：semver；记忆 schema 演进时递增
  "name": "成功日记",                      // 必填：展示名
  "description": "记录每日成就、维护连续天数、周期性复盘",   // 必填
  "intents": {                           // 必填：路由判据
    "domains": ["personal", "growth"],   // 复用 taxonomy 的 domain 枚举
    "categories": ["habit", "mindset"],  // 复用 taxonomy 的 category 枚举
    "keywords": ["成功日记", "日记", "成就", "复盘"]  // 兜底关键词命中
  },
  "permissionCeiling": "draft",          // 必填：PermissionLevel，包内工具上限
  "tools": ["diary.append", "diary.summary"],   // 引用 tools/ 下声明文件
  "memory": {
    "collections": [
      { "name": "entries", "sensitivity": "sensitive" },
      { "name": "streaks", "sensitivity": "normal" }
    ]
  },
  "templates": ["append-prompt", "summary-prompt"],  // 引用 templates/
  "validators": ["entry"],               // 引用 validators/
  "events": {
    "emits": ["diary.entry.created", "diary.reminder.due"],
    "subscribes": ["diary.reminder.tick"]
  },
  "privacy": {
    "note": "日记内容属敏感数据，默认只写不读回 LLM 上下文"
  }
}
```

字段校验规则（注册表机械校验，不通过则拒绝加载并报错）：

1. `id` 全局唯一，与目录名一致；
2. `domains` / `categories` 必须存在于 question-taxonomy 注册表（域-子类兼容）；
3. `tools` / `memory.collections` / `templates` / `validators` 引用必须可解析；
4. `permissionCeiling` 必须是合法 `PermissionLevel`；
5. `events.emits/subscribes` 遵循 `skill.<id>.<name>` 命名约定，避免跨包事件命名冲突；
6. 敏感度取值 `normal | sensitive | secret`，默认 `normal`。

## 6. 能力包四要素

### 6.1 工具集（tools）

- 声明复用既有 `ToolConfig` 契约：`{ name, description, parameters(JSON Schema), minPermission, sideEffects, irreversible? }`。
- 实现以 **handler 注册函数**挂进 ToolGateway（与 CLI builtin 工具并列的第二种工具形态）；`minPermission` 不得超过 `manifest.permissionCeiling`，越界声明 → 注册失败。
- 副作用标注复用 `SideEffectScope`（fs/net/process/db/pay/external-api）：财务类写操作标 `pay`/`db` 并默认 `minPermission: 'approved'`。
- 能力包工具的每次调用自动落入现有审计（tool.invoke / tool.result / tool.blocked 事件）。

### 6.2 记忆 schema（memory）

- 每个集合是独立 JSON Schema；运行时以命名空间 `skills.<skillId>.<collection>` 存储，**默认包间不可见**。
- `sensitivity: 'sensitive' | 'secret'` 的集合：`secret` 只写不读回（不注入 LLM 上下文）；`sensitive` 注入前需脱敏声明（manifest 声明策略，默认不注入）。
- 包版本升级 = schema 版本递增；旧数据迁移策略由包自身在 `README.md` 声明，平台只提供版本号与快照，不做隐式迁移。

### 6.3 模板（templates）

- Markdown 提示模板，占位变量用 `{{var}}`（如 `{{date}}`、`{{recentEntries}}`）。
- 模板约束「模型怎么组织输出」，不写死业务规则；业务规则归 validators。

### 6.4 校验器（validators）

- 纯函数：输入 = 模型输出或工具结果，输出 = `{ ok, reason? }`。
- 失败处理：校验失败不阻断主流程（MVP），结果进审计；`irreversible` 工具的前置校验失败必须触发审批或中止。
- 校验器为确定性事实，属于 harness 侧，不允许调用 LLM。

## 7. 注册表与激活生命周期

### 7.1 CapabilityRegistry（新模块 `packages/runtime/src/capabilities/`）

- 启动时扫描 `packages/skills/*/manifest.json`，机械校验（§5），构建**不可变快照**；
- 查询：`list()` / `get(id)` / `resolveByIntent(domain, categories, keywords) -> SkillId | null`；
- 命名区分：`apps/api` 的 catalog 是**模型目录与计费**，能力注册表是独立模块，接口前缀 `/api/capabilities`，不复用 catalog。

### 7.2 激活生命周期

```
输入到达 → 意图路由（taxonomy 标签命中）→ registry.resolveByIntent
  → 命中单包（多包命中取最高置信度；并列时询问用户，MVP 不做组合）
  → 挂载：
      · 包工具注册进 ToolGateway（minPermission 生效，ceiling 校验）
      · memory 命名空间打开
      · templates 注入当前 Goal 上下文
      · events 订阅/发射挂上 event-bus
      · 发事件 capability.activated
  → 执行：在 Goal 树上正常跑，全程审计
  → 卸载（Goal 结束 / 用户切换意图 / 错误终止）：
      · 移除工具注册、退订事件
      · 保留记忆（append-only）
      · 发事件 capability.deactivated
```

- 激活是运行时内部动作，**不暴露为 REST 写接口**（本期）；
- 事件类型扩展：新增 `capability.activated / capability.deactivated`（task 级，携带 `skillId`）到 core 事件枚举——这是一次性通用扩展点（§16 R1）。

### 7.3 多包命中消解

- 路由按 `speech_act ∈ {task, question}` 且 domain/category 命中优先；关键词命中为兜底；
- 多个包并列命中：取路由置信度最高者；无法区分时在会话中询问用户（`decision`），不静默选择。

## 8. 平台能力：通知/提醒与消息通道

### 8.1 原则

> 领域包只发**领域事件**，不感知调度与通道；调度与投递是平台职责。

### 8.2 提醒调度器（Scheduler）

- 平台订阅领域事件（如 `diary.reminder.due`），按用户配置的提醒规则（如「每晚 21:00 提醒写日记」）触发，生成提醒任务投递到当前会话/通道；
- 提醒规则存为用户数据（行为流 `setting` 行记录配置），不写进能力包；
- MVP：最小调度器（事件总线 + 定时触发），不实现完整 cron 语义；后续可平滑替换。

### 8.3 消息通道（ChannelAdapter）

```ts
interface ChannelAdapter {
    id: string;   // 'console' | 'webui-sse' | 'wechat' | 'feishu' | ...
    deliver(message: ChannelMessage): Promise<DeliveryReceipt>;
}
```

- 对齐 ProviderAdapter 的注册/发现模式：`DefaultChannelRegistry` 按 id 分派；未知通道立即失败；
- 通道适配在平台层注册，任何能力包不感知通道差异（同一条提醒可投递到任意已注册通道）；
- 本期实现：`console` + `webui-sse`；微信/飞书为后续 adapter（需外部授权与风控，独立排期）。

## 9. 权限与治理

1. **天花板语义**：挂载能力包 = 一次委托。包内生效权限 = `min(当前 Goal ceiling, manifest.permissionCeiling, 工具 minPermission 派生值)`；越权调用由 authz 拦截，走既有审批流（approval）。
2. **审批复用**：`pay`/`external-api` 副作用工具默认 `approved`；审批锚点照常落行为流（`approval` 行）。
3. **敏感数据**：成功日记/身材/财务均属隐私面；`secret` 集合只写不读回；导出时按 sensitivity 剥离；标签系统的 `sensitivity` 轴复用，命中 `sensitive` 的问题原文不入 LLM 精标。
4. **审计**：能力包的激活/卸载/工具调用/校验失败全部落 event 流与 ledger，可按 `skillId` 回放。
5. **卸载即失权**：Goal 结束后工具注册与订阅必须移除；残留注册视为 bug（验收 CP-6 强制）。

## 12. 非目标与 YAGNI 护栏

- **不做**：多能力包组合编排、能力包市场/远程分发、微信/飞书实际接入（独立排期）、完整 cron 调度、可视化工作流编排、多 Agent 拆分（Goal 树委托已覆盖）。
- **护栏**：manifest 字段只定义本期必要的；新增字段 = manifest schema 升版本；禁止为「将来可能」预留接口；能力包规范变更必须先改本文档再改代码（AGENT.md 文档优先）。

## 13. 验收标准

| # | 验收项 | 标准 |
| --- | --- | --- |
| CP-1 | 注册表加载 | 启动时扫描 packages/skills/*，非法 manifest（缺字段/引用不可解析/越界 ceiling）被拒绝并报错 |
| CP-2 | 意图激活 | 命中意图后包工具出现在 ToolGateway，模板/记忆/事件挂载成功；未命中不加载 |
| CP-3 | 卸载无残留 | Goal 结束后 ToolGateway 无该包工具、事件订阅清空；进程内反复激活/卸载 3 次无泄漏 |
| CP-4 | 权限天花板 | 包工具越过 manifest.permissionCeiling 的调用被 authz 拦截并触发审批 |
| CP-5 | 记忆隔离 | `skills.<id>.*` 命名空间互不可见；`secret` 集合不进入 LLM 上下文 |
| CP-6 | 核心零领域代码 | core/runtime 不含 success-diary 等任何领域标识；新增第二个包无需改动注册表代码 |
| CP-7 | 提醒闭环 | 领域事件 → 调度器 → 通道投递全链路（console adapter）可验证；投递记录可审计 |
| CP-8 | 全链路审计 | 激活/卸载/工具调用/校验失败在 event 流与 ledger 可回放，含 skillId |
| CP-9 | 敏感数据治理 | 导出可剥离 sensitive/secret 字段；命中 sensitivity 的问题原文不入 LLM 精标 |

## 16. 风险与开放问题

- **R1 · ToolGateway 扩展口**：handler 型工具注册是本期唯一允许的 runtime 扩展；与 AGENT.md「核心最小原则」的权衡：该扩展是通用机制（与 CLI builtin 并列），非领域代码。需在 CP-A 定稿时确认。
- **R2 · 事件类型扩展**：`capability.activated/deactivated` 入 core 事件枚举，属一次性通用扩展，同上。
- **R3 · 多包命中消解**：MVP 取最高置信度、并列询问；若未来出现复合意图（「记一下今天身材和财务」），需要组合挂载策略，本期不做。
- **R4 · 记忆 schema 演进**：包版本升级时旧数据迁移由包自声明；平台只提供版本号与快照，不做隐式迁移（防数据损坏）。
- **R5 · 财务/身材数据安全**：财务涉及真实资金（pay 副作用），身材涉及健康隐私；REST 写接口开放前需先补加密存储与通道授权设计（独立文档）。
- **R6 · 通道风控**：微信/飞书 adapter 涉及外部平台授权、消息频率与合规，独立排期，不阻塞能力包规范落地。
