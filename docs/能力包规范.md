# Skill（SKILL.md）规范与实现

> 版本：v1.0 · 状态：设计定稿（取代 v0.x "能力包" 设计）
> 范围：packages/core（Skill 契约类型）、packages/runtime（发现 / 解析 / 挂载 / 目录注入）、apps/api（发现与挂载接口）、apps/webui（Skills 面板）。
> 依据：Agent Skills 开放标准（agentskills.io，Anthropic 提出，Claude Code / API 等实现），见文末「参考」。

---

## 1. 业界共识：Skill 就是一个 SKILL.md

**结论**：一个 Skill 的最小完整形态 = **一个目录 + 一个 `SKILL.md`**。`SKILL.md` 由

1. **YAML frontmatter**（`---` 包裹）承载元数据，标准要求的字段是 `name` 与 `description`；
2. **Markdown 正文**承载指令（什么时候用、按什么步骤做、输出什么格式）；
3. 可选：随包文件（脚本 / 参考资料 / 资源），由正文按相对路径引用。

机制叫 **渐进式披露（progressive disclosure）**，分三层：

| 层 | 内容 | 何时进入上下文 | 成本 |
| --- | --- | --- | --- |
| L1 | `name` + `description` 目录（catalog） | 会话启动 / 每次请求前常驻 | 每个 Skill 一行 |
| L2 | `SKILL.md` 正文 | 模型判断相关后读取整个文件 | 只在用到时付 |
| L3 | 随包文件（references/scripts/assets） | 正文里指名后按需读取 | 按需 |

关键点：**Skill 不注册新工具**。它教模型用**已有工具**（读文件、跑命令）完成特定任务；因此它是**可移植的文本资产**，不是插件。Claude Code 的原话是 "Bundled skills are prompt-based: they give Claude detailed instructions and let it orchestrate the work using its tools."

## 2. 为什么 v0.x 的 manifest.json / tools / memory / templates / validators / events 是类别错误

v0.x 把 Skill 设计成"能力包"：`manifest.json` 声明工具、权限天花板、记忆 schema、模板、校验器、事件订阅，运行时再把 handler 注入 ToolGateway。那是**插件 / MCP 的职责**，不是 Skill 的：

| v0.x 要素 | 真实归属 | 结论 |
| --- | --- | --- |
| `tools` + `handlers`（注册新工具） | 插件 / MCP server（扩展 action surface） | 移出 Skill |
| `permissionCeiling`（权限天花板） | 判权属于 harness；新副作用面才需要它 | 移出 Skill |
| `memory/schemas.json`（私有数据集合） | 插件的数据面 | 移出 Skill |
| `templates/*.md`（提示模板） | 就是 `SKILL.md` 正文本身 | 取消 |
| `validators/*.ts`（确定性校验） | 平台/插件的机械约束 | 移出 Skill |
| `events.emits/subscribes` | 平台调度（提醒）由用户配置驱动 | 移出 Skill |
| `intents.domains/categories` | 标准靠 `description` 让模型自判；硬编码分类法与可移植性冲突 | 取消：路由完全由 description 驱动 |

代价是显性的：一个只想写"记录成功日记"的人，被迫写 manifest + 工具 JSON + TS handler + schemas + 模板 + 校验器，而且产物**无法跨工具移植**。这正是"业界一个 md 就够、我们却要一堆文件"的根因。

## 3. 格式规范

```
<skills 根>/<skill-id>/
├── SKILL.md            # 必需：frontmatter + 正文
└── …                   # 可选：references/ scripts/ assets/ 等随包文件
```

`SKILL.md`：

```markdown
---
name: success-diary
description: 记录每日成就并做周期性复盘。当用户想写成功日记、记录今天做到的事、或要求复盘时使用。
when_to_use: 用户说「成功日记 / 今天做到了什么 / 帮我复盘这周」
allowed-tools: fs.read rg
license: MIT
---

# 成功日记

## 何时使用
…

## 步骤
1. 读 `references/format.md` 确认结构；
2. 向用户追问事实—感受—下一步；
3. 把结果写入用户指定的文件。
```

字段表（除特别说明外都可选；标准要求 `name` + `description`）：

| 字段 | 说明 |
| --- | --- |
| `name` | Skill 名；缺省 = 目录名 |
| `description` | **核心**：做什么 + 什么时候用（模型据此决定是否加载）；缺省回退正文首行 |
| `when_to_use` | 触发语/示例请求（行业实现里的扩展字段） |
| `allowed-tools` | Claude Code 扩展：允许的工具；mazi **解析并展示，暂不参与判权**（见 §6） |
| `license` / `metadata` | 附加元数据，原样保留展示 |

机械校验（不合格即拒绝加载并报错）：`SKILL.md` 存在且可读；frontmatter 以首行 `---` 开始且闭合；`description`（或正文首行）非空；正文非空。

**主体分栏 ↔ 正文映射**（面板「新建技能」按分栏填写，服务端拼装；任一分栏填写即写入正文，全空则落占位骨架）：

| 分栏 | 正文 |
| --- | --- |
| description | frontmatter `description`（模型路由用，非正文） |
| 何时使用（trigger） | `## 何时使用`（多行转列表） |
| 步骤 | `## 步骤`（自动编号 `1. 2. …`） |
| 输出 | `## 输出`（项目符号） |
| 注意事项（可选） | `## 注意事项`（项目符号） |

## 4. 目录与优先级（三级根）

| 级别 | 位置 | 说明 |
| --- | --- | --- |
| 项目 | `<workspace>/skills/<id>/SKILL.md` | 随仓库共享（对应 Claude Code 的 project skills） |
| 用户 | `$MAZI_HOME/skills/<id>/SKILL.md` | 用户资产；面板「新建」默认落点 |
| 内置 | `<runtime 包>/builtin-skills/<id>/SKILL.md`，`MAZI_BUILTIN_SKILLS_DIR` 可覆盖 | 随应用只读分发 |

同名 id 只保留最高优先级，其余进 `shadowed()`。仓库只承载**管理机制**与内置只读落点，不承载任何领域 Skill。

## 5. 生命周期

```
发现（扫描三级根 → 解析 SKILL.md → 快照）
  → 挂载（用户开关，持久化 $MAZI_HOME/skills.json）
  → 运行期 L1：把已挂载 Skill 的 name/description/path 注入系统提示（catalog）
  → 运行期 L2：模型判断相关 → 用已有 fs 工具读 SKILL.md 正文
  → 运行期 L3：正文提到的随包文件按需读取
  → 卸载：从 catalog 移除（工具面不受影响）
```

- 挂载状态是用户设置，重启保持；每次运行把 catalog 计入该 Skill 的 `usage.injections`（进程内累计）。
- 运行边界发 `capability.activated / capability.deactivated`（携 `harness.skill_id`），可回放"这次运行带上了哪些 Skill"。
- **不改变工具面、不改变权限**：挂载 Skill 不授予任何新能力。

## 6. 接口契约

| 端点 | 方法 | 说明 |
| --- | --- | --- |
| `/api/capabilities` | GET | 列表：id / name / description / scope / dir / path / mounted / mountedAt / allowedTools / resources / usage(注入次数·最近注入) + 装载错误 + 覆盖来源 + 汇总 |
| `/api/capabilities` | POST | 新建：`{ id, name, description?, scope: user\|project, whenToUse?, steps?, output?, notes? }` → 按主体分栏写 `SKILL.md` 并立即发现；内置根只读 |
| `/api/capabilities/:id` | GET | 详情：frontmatter 全量 + 正文 + 随包文件清单 + 绝对路径 |
| `/api/capabilities/:id/mount` | POST | 挂载（幂等） |
| `/api/capabilities/:id/unmount` | POST | 卸载（幂等） |
| `/api/capabilities/reload` | POST | 重新扫描三级根 |

`allowed-tools` 暂只解析展示：mazi 的工具面与判权由 Goal ceiling + authz 决定，Skill 不得放宽；真正需要新工具/新副作用的场景按下节处理。

## 7. 非目标（明确边界）

- **不做**：Skill 内注册工具、handler、私有记忆 schema、校验器、事件订阅、权限天花板（v0.x 已删除）。
- 需要**新工具 / 新副作用面 / 私有数据** → 属于**插件或 MCP server**，用另一套设计（独立文档），不塞进 `SKILL.md`。
- 不做远程 Skill 市场 / 签名分发（后续按需）。

## 8. 验收标准

| # | 验收项 | 标准 |
| --- | --- | --- |
| SK-1 | 解析与校验 | 只有 `SKILL.md` 的目录可被发现；缺 frontmatter / description / 空正文被拒绝并报错 |
| SK-2 | 三级根 | project > user > builtin；同名覆盖记入 shadowed；内置只读 |
| SK-3 | 渐进披露 | 未挂载不进 catalog；挂载后 catalog 只含 name/description/path；正文只在模型读取时进入上下文 |
| SK-4 | 挂载治理 | 挂载持久化、卸载立即生效、重复操作幂等；进程内反复挂载/卸载无残留 |
| SK-5 | 核心零领域 | 仓库不含任何领域 Skill；新增 Skill = 新增目录，零代码改动 |
| SK-6 | 面板闭环 | UI 发现 / 新建 / 挂载 / 卸载 / 查看使用情况与正文 |

## 9. 实现映射

| 位置 | 内容 |
| --- | --- |
| `packages/core/src/capabilities.ts` | Skill 契约类型（frontmatter / 文档 / 校验 issue） |

| `packages/runtime/src/capabilities/skill-md.ts` | `SKILL.md` 解析（frontmatter 子集 + 正文）与机械校验 |
| `packages/runtime/src/capabilities/source.ts` | 三级 skills 根装配 + 文件读取 |
| `packages/runtime/src/capabilities/registry.ts` | `SkillRegistry`：扫描 / 快照 / 查询 / description 关键词兜底路由 |
| `packages/runtime/src/capabilities/runtime.ts` | `SkillRuntime`：挂载状态、catalog 注入、usage、详情 |
| `packages/runtime/src/capabilities/scaffold.ts` | 新建 `SKILL.md` 脚手架 |
| `packages/runtime/src/harness/runtime.ts` | 运行期把已挂载 Skill 的 catalog 追加进系统提示 + 运行边界事件 |
| `apps/api/src/capabilities/` | §6 的 REST 端点 |
| `apps/webui` Settings → Skills | 发现 / 新建 / 挂载 / 卸载 / 正文与使用情况 |
| `packages/runtime/builtin-skills/` | 内置只读落点（仓库不含领域 Skill） |
