
# 模型目录与计费数据架构设计文档

**版本**：v1.0

**状态**：定稿

**范围**：多厂商多渠道模型接入的目录管理、定价版本化、动态更新机制、长期凭证与运行时依赖的分层存储设计

**基线说明**：本版直接采用五层概念模型（vendor → model → provider → offering → driver 协议），Offering 为定价/健康/路由的一等挂靠点，不设“先简化后演进”的过渡形态

## 1. 设计总纲

本系统管理的是一组**外部世界拥有、我们无法控制**的事实：厂商会发布模型、下架模型、调整价格、变更能力；渠道会接入新型号、淘汰旧型号、单独定价。设计由此推导出三条总原则：
**原则一：状态可下线，事实不可撤销。**
目录（谁存在、什么价）是可变的锚点；账本（何时用了多少、当时什么价）是不可变的事实。下架任何一个实体，不能导致它的历史定价和历史账单失去解释依据。
**原则二：我们落库的不是“世界的现状”，而是“我们何时得知了什么”。**
厂商与渠道随时变更，我们无法阻止；能做的是把每次得知记录为有出处（source）、有时刻（effectiveAt / observedAt）的事实。
**原则三：运行时层可任意丢弃，凭证层永不可丢。**
所有凭证都在持久事实层；缓存陈旧只影响可用性，永远不影响账务正确性。丢失任何运行时状态不构成事故，丢失任何一行凭证才是。
系统整体分层：

```
外部世界（厂商公告 / 渠道定价页 / API）          运维操作 / 用户配置
        │                                             │
        ▼                                             ▼
┌──────────────────┐   ┌──────────────────┐
│ Sync 管线（写路径）│   │ Health 探测器      │
│ 拉取→diff→校验     │   │ 周期探测→追加样本   │
└───────┬──────────┘   └────────┬─────────┘
        ▼ 事务：目录变更 + change 事件 + epoch++      ▼ 追加（不触发 epoch）
┌─────────────────────────────────────────────────────┐
│  事实层 · Postgres（权威存储 = 长期凭证）              │
│  vendors / providers / models(软删)                  │
│  offerings(软删) / pricing_plans(追加，挂 offering)   │
│  health_samples(时序，挂 offering) / model_aliases    │
│  catalog_changes(审计) / driver_configs              │
│  usage_records(账本，挂 offering)                    │
└───────┬─────────────────────────────────────────────┘
        ▼ epoch 通知（进程内事件 / Redis pub-sub）
┌──────────────────┐
│ 快照构建器         │
│ 按 epoch 重建视图  │
└───────┬──────────┘
        ▼ 原子指针交换（双缓冲）
┌─────────────────────────────────────────────────────┐
│  运行时层 · 易失内存（重启即重建 = 运行时依赖）         │
│  CatalogSnapshot · 当前健康聚合 · 路由器 · 驱动实例     │
└───────┬─────────────────────────────────────────────┘
        ▼ 请求派发时钉死 (offeringId, pricingPlanId, epoch)
     UsageRecord 追加回事实库 ──→ 凭证闭环
```

**原始 JSON 的定位**：不是权威存储，而是快照的序列化产物（seed 导入格式 / 导出格式）。首次启动 bootstrap 入库（见 §12），此后数据库是唯一事实源。

## 2. 术语表（五层概念模型）

```
vendor     谁开发的？         deepseek / anthropic / openai
   │       厂商命名
model      什么型号？         deepseek-v4-flash / deepseek-v4-pro
   │       同一型号可从多个渠道买到
provider   从哪个渠道接？      deepseek官方API / openrouter / bedrock
   │       渠道 = 端点 + 密钥 + 计费账户 + 限流 + 协议
offering   该渠道下的该型号    (deepseek × deepseek-v4-flash) 这份"供给"
   │       价格、健康、能力偏差都长在这层
driver     用什么协议说话？    pi-ai / openai-compat / anthropic-native
```

| 概念                     | 回答的问题               | 本质                               | 稳定性          | 关键属性                     |
| ------------------------ | ------------------------ | ---------------------------------- | --------------- | ---------------------------- |
| **vendor**         | 谁开发的                 | 开发商：造模型（权重、训练、命名） | 极稳定          | 身份                         |
| **model**          | 什么型号                 | 厂商命名的型号，id 由厂商给定      | 厂商换代即换 id | 厂商规格（capabilities）     |
| **provider**       | 从哪个渠道接、账算谁的   | 接入渠道：端点、密钥、限额         | 可增删          | 协议（driverType）、限额     |
| **offering**       | 该渠道下该型号的具体供给 | model × provider 交叉点           | 价格健康随时变  | 定价、健康、能力偏差         |
| **driver 协议**    | 用什么协议通信           | 技术适配器                         | 纯技术选型      | 序列化/流解析/tool call 表达 |
| **几组关键关系**： |                          |                                    |                 |                              |

- **vendor ≠ provider**：源数据中 `"id": "deepseek", "vendor": "deepseek"` 重合是“自研自营官方直连”的特例。常态下二者分离——同一 `deepseek-v4-flash` 从官方买时 provider=deepseek，从 OpenRouter 买时 vendor 仍是 deepseek、provider 是 openrouter，价格、限流、健康度全部不同。**vendor 挂在 Model 上，不挂在 Provider 上**：一个渠道（OpenRouter）可以卖几十个厂商的模型，渠道与厂商是多对多。
- **provider ↔ driver 协议**：协议是**端点**的属性，不是型号的属性——端点说什么协议，渠道就配什么适配器。源数据 `driver: { type: "pi-ai", provider: "deepseek", model: "..." } }` 拆解为：`type` 上移到 `Provider.driverType`（渠道说什么协议）；`model` 语义收窄进 `DriverConfig`（用户默认绑定，见 §4）。若同一厂商账号同时提供原生协议和 compat 两种端点，按两个 Provider 建模（不同 base URL 即不同渠道）。
- **offering 是“可购买单元”**：用户实际消费的从来不是抽象的 model，而是“某个渠道上的某个型号”。因此定价、健康探测、用量账本、能力偏差的挂靠点全部落在 offering 层。`(modelId, providerId)` 构成天然键，另设代理主键 `OfferingId`。
- **版本控制的锚定**：model id（`deepseek-v4-flash`）是**厂商目录的锚**——外来的、不可控的；`v4` / `v41` / `-exp` 是厂商命名的一部分，厂商换代的方式是“换一个新 id”，不是同一 id 上 version 自增（佐证：`deepseek-chat` 这类 id 会被厂商静默升级底层权重）。**版本控制的锚是我们围绕 offering 建的内部追加式实体**（PricingPlan 版本链、catalog epoch）。因此：不给 Model 加 `version` 字段；厂商换代 = 新 Model 行 + 旧行软删 + alias；需要版本化的事实全部挂在我们的追加式实体上。

## 3. 域划分（按生命周期归位，不按 JSON 嵌套）

| 域                                             | 内容                                      | 性质                               | 变更方式        |
| ---------------------------------------------- | ----------------------------------------- | ---------------------------------- | --------------- |
| **目录域**                               | Vendor / Provider / Model / Offering 身份 | 锚点（软删除，active 行可 upsert） | sync upsert     |
| **商业域**                               | 定价（挂 offering）                       | 不可变版本链，按时间区间生效       | 追加 + 回填过期 |
| **观测域**                               | 健康度（挂 offering）                     | 时序追加                           | 探测器追加      |
| **配置域**                               | DriverConfig 默认绑定与迁移链             | 活引用，可迁移                     | 用户/运维更新   |
| **账本域**                               | 用量与成本（挂 offering）                 | append-only 凭证                   | 请求结算时追加  |
| **审计域**                               | 目录变更事件                              | append-only                        | 随目录事务同写  |
| 原始 JSON 的三个结构性问题在本基线下直接消解： |                                           |                                    |                 |

1. pricing 挂 provider 层但语义粒度是模型级 → **挂 offering**（渠道×型号，粒度恰好）；
2. `driver.model` 是裸字符串弱引用 → **DriverConfig 引用 OfferingId**，强类型可校验；
3. health 只存单值 → **offering 级时序样本**，可回溯劣化曲线。

## 4. 完整数据结构（TS）

```ts
// ---------- 基础 ----------
/** 目录数据永不物理删除：下架 = 状态标记，身份保留作为历史引用的锚点 */
export type LifecycleStatus = 'active' | 'deprecated' | 'offline'
declare const brand: unique symbol
type Brand<T, B> = T & { readonly [brand]: B }
export type VendorId    = Brand<string, 'Vendor'>
export type ProviderId  = Brand<string, 'Provider'>
export type ModelId     = Brand<string, 'Model'>
export type OfferingId  = Brand<string, 'Offering'>
// branded 类型：四种 id 都是 string，但不可互换、不可裸写
// ---------- 目录域 ----------
export interface Vendor {
  id: VendorId            // 'deepseek'
  displayName: string
  status: LifecycleStatus
}
export interface Provider {
  id: ProviderId          // 渠道身份，如 'deepseek'（官方）、'openrouter'
  displayName: string
  /** 渠道端点使用的协议适配器 —— 承接源 JSON 的 driver.type */
  driverType: 'pi-ai' | 'openai-compat' | 'anthropic-native' | (string & {})
  /** 渠道性质，路由权重参考：官方直连 / 聚合商 / 代理 */
  kind?: 'official' | 'aggregator' | 'proxy'
  tags: readonly string[]  // 源 JSON provider.tags，粗粒度渠道标签
  status: LifecycleStatus
  // 注意：vendor 不在 Provider 上 —— 渠道与厂商多对多，归属由 Model 表达
}
export interface ModelCapabilities {
  contextWindow: number
  maxTokens: number
  supportsThinking: boolean
  supportsTools: boolean
  supportsVision: boolean
}
export interface Model {
  id: ModelId             // 厂商给定的 id，外来锚点，不设 version 字段（见 §2）
  vendorId: VendorId      // 谁开发的
  name: string
  /** 厂商规格：能力与型号同生共死，是唯一适合嵌入 Model 的部分 */
  capabilities: ModelCapabilities
  status: LifecycleStatus
  // 注意：没有 providerId —— model 与渠道的关系由 Offering 承载
}
/**
 * Offering：可购买单元 = model × provider。
 * 定价 / 健康 / 能力偏差 / 用量账本的统一挂靠点。
 * 天然键 (modelId, providerId) 唯一；id 可用 `${providerId}/${modelId}` 约定生成。
 */
export interface Offering {
  id: OfferingId
  modelId: ModelId
  providerId: ProviderId
  /** 渠道对厂商规格的偏差（如该渠道未开 vision 端点）；null = 完全遵循厂商规格 */
  capabilitiesOverride: Partial<ModelCapabilities> | null
  status: LifecycleStatus
}
/** 厂商改名/换代：旧 id 软删，新 id 插入，alias 保证历史记录可解析 */
export interface ModelAlias {
  id: string
  oldModelId: ModelId
  canonicalModelId: ModelId
  reason: 'vendor-rename' | 'operator-merge'
  mappedAt: Date
}
// ---------- 商业域：定价版本链（挂 offering） ----------
export interface PricingRates {
  inputPerMTok: number
  outputPerMTok: number
  cacheReadPerMTok: number
  cacheWritePerMTok: number
}
export interface PricingTier {
  thresholdTokens: number   // 如长上下文加价档
  rates: PricingRates
}
export interface PricingPlan {
  id: string
  offeringId: OfferingId          // ★ 渠道×型号级挂靠；同型号不同渠道各自成链
  currency: string
  base: PricingRates
  tiers: readonly PricingTier[]
  effectiveAt: Date               // 渠道口径的生效时刻
  expiresAt: Date | null          // null = 当前生效；新版本插入时回填
  observedAt: Date                // ★ 我们何时得知——与 effectiveAt 差值即"迟知成本"
  source: 'vendor-sync' | 'operator' | 'manual-import'
  version: string
}
// 查询语义：价格调整 = 插入新行 + 回填旧行，不 UPDATE，不 DELETE
// ---------- 观测域：健康时序（挂 offering） ----------
export interface HealthSample {
  id: string
  offeringId: OfferingId     // 探测目标：该渠道的该型号
  score: number
  source: 'probe' | 'manual-import'
  sampledAt: Date
}
// 渠道级健康（provider 整体故障）为派生聚合：对该 provider 全部 offering 样本求统计，不落库
// ---------- 配置域：默认绑定与迁移链 ----------
/**
 * DriverConfig：默认绑定与故障迁移链。
 * 语义收窄说明：协议选型（源 JSON driver.type）已上移至 Provider.driverType；
 * 此实体只保留"默认用哪份供给、坏了切到哪"。
 */
export interface DriverConfig {
  id: string
  /** 默认绑定：钉到具体 offering（渠道×型号），而非裸 model id */
  offeringId: OfferingId
  /** 迁移链，按优先级排序；约定：同型号换渠道优先，跨型号兜底 */
  fallbackOfferingIds: readonly OfferingId[]
}
// ---------- 账本域：长期凭证的落点（挂 offering） ----------
export interface UsageRecord {
  id: string
  offeringId: OfferingId    // ★ 结算主体：哪个渠道的哪个型号
  modelId: ModelId          // 冗余列：报表按型号聚合免 join
  providerId: ProviderId    // 冗余列：报表按渠道聚合
  pricingPlanId: string     // ★ 派发时刻钉死，结算依据（非实时价格）
  catalogEpoch: number      // ★ 由哪个快照版本路由，可追溯到变更审计
  inputTokens: number
  outputTokens: number
  cacheReadTokens: number
  cacheWriteTokens: number
  cost: number              // 冗余存结果，账务可审计
  occurredAt: Date
}
// ---------- 审计域：目录变更事件（与目录写入同事务） ----------
export type CatalogChangeKind =
  | 'vendor-added' | 'provider-added' | 'provider-deprecated'
  | 'model-added' | 'model-deprecated' | 'model-reactivated'
  | 'offering-added' | 'offering-deprecated' | 'offering-reactivated'
  | 'pricing-changed' | 'operator-override' | 'alias-created'
export interface CatalogChange {
  id: string
  epoch: number                     // 单调递增，快照版本号
  kind: CatalogChangeKind
  payload: Record<string, unknown>  // diff 形态，只存变化
  source: 'vendor-sync' | 'operator' | 'probe' | 'user'
  occurredAt: Date
}
// ---------- 运行时层：快照（内存结构，不落库） ----------
export interface CatalogSnapshot {
  epoch: number
  builtAt: Date
  offerings: readonly ActiveOfferingView[]   // 仅 status=active
}
export interface ActiveOfferingView {
  offering: Offering
  model: Model
  provider: Provider
  /** 合成后能力 = 厂商规格 ⊕ 渠道 override，路由判断只看这一个 */
  effectiveCapabilities: ModelCapabilities
  /** 当前生效价目；null = 目录可见但不可路由（无价不可结算） */
  pricing: PricingPlan | null
}
```

注意 `ActiveOfferingView` 中**没有** health——健康聚合是独立的易失结构，由探测器按自己的节奏刷新（见 §6），不参与 epoch 版本化，否则每分钟的健康波动会把快照版本刷爆。

## 5. 写入路径：动态更新机制

动态更新有四个来源，全部收敛到同一条管线：

| 来源                                  | 触发时机                                    | 落库动作                                                                                                    | 是否推动 epoch |
| ------------------------------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | -------------- |
| **渠道目录 sync**               | 定时（如每 6h）+ 手动触发 + webhook（若有） | diff 检出 → 事务内：upsert Vendor/Provider/Model/Offering、插入 PricingPlan、回填旧 plan、写 CatalogChange | ✅             |
| **健康探测**                    | 每 1–5 分钟 / offering                     | 追加 HealthSample                                                                                           | ❌（纯观测）   |
| **运维操作**                    | 人工调价、提前下架、改名 alias              | 与 sync 同构，source 标记 operator                                                                          | ✅             |
| **请求结算**                    | 每次请求完成                                | 追加 UsageRecord（钉死 plan 与 epoch）                                                                      | ❌（纯账本）   |
| **sync 管线的幂等与事务边界：** |                                             |                                                                                                             |                |

1. 拉取上游目录（厂商页 + 各渠道页），与库内 `active` 目录按 `(modelId, providerId)` 做 diff；
2. 同一事务内完成：新 vendor/provider/model/offering insert / 下架实体 status 翻转 / 新 PricingPlan 插入 + 旧版本回填 `expiresAt`；
3. 同事务写入 CatalogChange 并 `epoch + 1`（epoch 存在单行 `catalog_meta` 表中）；
4. 事务提交后发布 epoch 通知。
   幂等性由 diff 保证：重复拉到相同目录 → 无 diff → 无写入 → epoch 不动。
   **目录行 vs 事实行的更新纪律**：目录域（身份、能力）的 active 行允许 upsert（厂商改 context window 属于目录修正，随 change 事件留审计）；商业域（PricingPlan）与账本域（UsageRecord）严格追加，**永不 UPDATE、永不 DELETE**。
   **价格来源冲突政策**：operator 行与 vendor-sync 行区间重叠时，operator 优先（人工覆盖渠道）；由于均为追加，审计上永远可辨“这一个月价格是谁定的”。

## 6. 读取路径：快照构建、热替换与路由

```
epoch 通知（进程内事件 / Redis pub-sub / 轮询 catalog_meta）
        ▼
快照构建器：SELECT active offerings JOIN model JOIN provider JOIN 当前生效 PricingPlan
            → 合成 effectiveCapabilities → 构建 CatalogSnapshot
        ▼
原子指针交换（新快照整体构建完成后一次 swap，双缓冲）
        ▼
路由器读快照派发请求
```

要点：

- **整体交换，不做增量修补**。快照是小数据（几百 offering），整体重建的成本远低于维护增量一致性的复杂度。
- **在途请求不受影响**。每个请求在派发时刻从当时的快照钉死 `{offeringId, pricingPlanId, epoch}` 三元组，之后快照换代与本请求无关。
- **健康聚合旁路刷新**。`CurrentHealth = { score（滚动窗口聚合）, computedAt, windowSamples }` 存内存，探测器采样后异步重算，路由决策时与快照 join。
- **路由决策输入**：DriverConfig 默认绑定 → 快照中该 offering 的 `effectiveCapabilities`（能力过滤）→ `pricing`（无价不可路由）→ CurrentHealth（避开劣化渠道）→ 限流余量。fallback 沿 `fallbackOfferingIds` 逐级降级，同型号换渠道优先于跨型号。
- **缓存陈旧的正确性边界**：陈旧快照最坏情况是路由到一个刚下架的 offering → 请求失败 → 按新快照重试，损失的是可用性；账单钉的是 plan id 而非实时价格，**账务正确性永远不依赖缓存新鲜度**。
- **多实例一致性**：各实例收到 epoch 通知后各自重建，短暂不一致被可用性语义吸收。

## 7. 长期凭证 vs 运行时依赖（分界清单）

|                    | 长期落库的凭证（事实层）                                                                                                              | 运行时依赖（易失层）                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **判据**     | 丢失后无法重建、有审计/追责价值                                                                                                       | 丢失后可从凭证层完整重建                                                        |
| **内容**     | Vendor/Provider/Model/Offering 身份行（软删锚点）、PricingPlan 版本链、UsageRecord 账本、CatalogChange 审计、ModelAlias、DriverConfig | CatalogSnapshot、CurrentHealth 聚合、驱动实例、熔断/限流状态、fallback 决策缓存 |
| **变更方式** | 软删 / 追加 / 回填过期（商业与账本域永不改历史）                                                                                      | 随时可丢弃、重建、回滚                                                          |
| **存储介质** | Postgres（usage_records 按月分区）                                                                                                    | 进程内存（多实例可加 Redis 缓存视图，仍是易失缓存）                             |
| **崩溃恢复** | 天然安全（持久层）                                                                                                                    | 重启后从 DB 按 epoch 重建，秒级                                                 |

一句话：**凭证回答“过去发生了什么、凭什么这么算”；运行时回答“现在该往哪路由”。**  

`DriverConfig` 是中间态：它持久落库（用户配置不能丢），但它引用的 `offeringId` 是活引用——offering 下架时触发告警或沿迁移链自动切换。

---

## 8. 存储位置与写入时机（逐表）

| 表                                                       | 介质              | 写入时机                           | 写入者              | 保留策略                                          |
| -------------------------------------------------------- | ----------------- | ---------------------------------- | ------------------- | ------------------------------------------------- |
| `vendors` / `providers` / `models` / `offerings` | PG                | sync 检出 diff 时；运维下架/恢复时 | sync 管线 / 运维    | 永久（软删）                                      |
| `pricing_plans`                                        | PG                | sync 检出价格变化时；运维覆盖时    | sync 管线 / 运维    | 永久（append-only）                               |
| `model_aliases`                                        | PG                | 运维发现厂商改名时                 | 运维                | 永久                                              |
| `health_samples`                                       | PG（时序表/分区） | 每次探测 tick                      | 探测器              | 原始 30 天 → 小时降采样 1 年 → 天级永久（可选） |
| `catalog_changes`                                      | PG                | 每次目录变更，与变更同事务         | sync 管线 / 运维    | 永久（审计）                                      |
| `driver_configs`                                       | PG                | 用户/运维修改绑定与迁移链时        | 配置 API            | 永久                                              |
| `usage_records`                                        | PG（按月分区）    | **每次请求结算完成时**       | 运行时              | 永久                                              |
| `catalog_meta`（epoch）                                | PG 单行           | 每次目录事务提交时                 | sync 管线           | —                                                |
| `CatalogSnapshot` / `CurrentHealth`                  | 进程内存          | epoch 通知后 / 探测 tick 后        | 快照构建器 / 探测器 | 重建即覆盖                                        |

**结算写入的会计政策**：`pricingPlanId` 在**派发时刻**钉死而非结算时刻读取——请求飞行途中价格变动，本请求按起飞时的价目结算。账单不因迟到得知的信息回改。

## 9. 请求生命周期中的数据流

```
1. 请求进入
2. 路由器读 CatalogSnapshot（内存）+ CurrentHealth
   → 按 DriverConfig 默认绑定取 offering，能力/价格/健康过滤，必要时沿迁移链降级
3. 派发：钉住 { offeringId, pricingPlanId, epoch }
   → 取 Provider.driverType 对应的适配器实例，打到该渠道端点
4. 驱动执行（流式，可能跨越多次快照换代）
5. 完成：token 用量 × 钉住的 PricingPlan → 计算 cost
6. 追加 UsageRecord（含 offeringId + 冗余 modelId/providerId + epoch）→ 事实层
7. （旁路）探测器持续采样 → 健康聚合异步刷新
```

## 10. 动态更新场景走查（设计验证）

| 场景                           | 写路径动作                                                      | epoch | 运行时效果                                 | 历史影响                               |
| ------------------------------ | --------------------------------------------------------------- | ----- | ------------------------------------------ | -------------------------------------- |
| 厂商发布新模型（官方渠道）     | insert model + offering + plan v1 + change                      | +1    | 下个快照即可路由                           | 无                                     |
| **现有型号接入第二渠道** | **仅 insert offering + 该渠道 plan；model 不动**          | +1    | 路由可选新渠道（比价/分流）                | 原渠道历史不受扰动                     |
| 单渠道调价                     | 该 offering 插新 plan + 旧行回填 expiresAt                      | +1    | 新请求立即新价；在途请求旧价               | 账单各自按钉住版本                     |
| **厂商下架型号**         | model deprecated + 该型号**全部** offering deprecated     | +1    | 快照移除；DriverConfig 校验→告警/切迁移链 | 全链路可追溯，无孤儿                   |
| **单渠道下架某型号**     | **仅该 offering deprecated；model 仍 active（其他渠道）** | +1    | 迁移链优先切同型号其他渠道                 | 该渠道历史账单仍可解析                 |
| 渠道整体故障                   | 无目录写入，仅 health 样本劣化                                  | 不变  | 路由避开该渠道（健康过滤）                 | 无                                     |
| 厂商改名/换代                  | 旧 model 软删 + alias + 新 model + 新 offerings                 | +1    | 路由无感                                   | 旧 UsageRecord 经 alias 解析           |
| 运维覆盖定价                   | source=operator 的 plan 行                                      | +1    | 覆盖渠道价                                 | 审计可辨来源                           |
| 迟到得知调价                   | 新 plan 的 effectiveAt 在过去                                   | +1    | 立即生效                                   | **不回改历史账单**；重算仅报表层 |
| 实例崩溃                       | 无写动作                                                        | 不变  | 重启后按 DB 重建快照                       | 凭证零损失                             |

对比简化形态的关键增益在第二、五、六行：**渠道维度的变更被隔离在 offering 层，不再牵动 model 或其他渠道**——这正是 Offering 基线的存在理由。

## 11. 代价与取舍（诚实清单）

采用 Offering 基线不是免费的，明确记录代价：

1. **间接层加一**：单渠道厂商（如当前 DeepSeek 直连）每个型号也必须建 offering 行，查询多一层 join。缓解：运行时读快照（已物化 join 结果），成本只落在 sync 与构建侧；报表靠 UsageRecord 冗余列。
2. **引用链变长**：DriverConfig、账本、价目都指向 OfferingId，追到厂商要多跳。缓解：`offeringId` 采用 `${providerId}/${modelId}` 生成约定，肉眼可读。
3. **导入时数据不足**：源 JSON 的定价在 provider 层，无法精确到 offering（见 §12 的导入政策）。这是源数据本来的缺陷，本设计选择暴露它而非虚构数据。

## 12. Bootstrap：源 JSON → v1 映射

首次启动将原始 JSON 以 `source: 'manual-import'` 走一遍 sync 管线入库，字段映射如下：

| 源 JSON                         | v1 目标                                                                                | 说明                                                                                                                                                      |
| ------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `provider.id: "deepseek"`     | `Vendor('deepseek')` + `Provider('deepseek', driverType='pi-ai', kind='official')` | vendor 与 provider 恰好同名是直连特例，仍拆成两个实体                                                                                                     |
| `provider.tags`               | `Provider.tags`                                                                      | 原样保留                                                                                                                                                  |
| `provider.driver.type`        | `Provider.driverType`                                                                | 协议归渠道                                                                                                                                                |
| `provider.models[]`           | `Model(id, vendorId='deepseek', capabilities)`                                       | `supportsVision` 缺省 → `false`（显式归一）                                                                                                          |
| 每个`(provider, model)`       | `Offering(modelId, providerId, override=null)`                                       | 每型号建一份供给                                                                                                                                          |
| `provider.pricing`            | `PricingPlan` **仅挂 `driver.model` 对应的 offering**                        | 源数据定价本就只对默认型号有效；其余 offering`pricing=null`（目录可见、不可路由），待 sync 拉到渠道真实模型级价格后回填。**不为无价型号虚构价格** |
| `provider.driver.model`       | `DriverConfig.offeringId` 指向 `(deepseek × deepseek-v4-flash)` 的 offering       | 强类型引用取代裸字符串；fallback 链初始为空                                                                                                               |
| `provider.health: {score: 1}` | 丢弃或记一条`HealthSample(source='manual-import')`                                   | 无时间戳的占位值，建议丢弃，健康由探测器自建                                                                                                              |

此后该 JSON 格式仅作为快照导出格式存在（导出时是 offering 级精确数据，比源格式信息更完整）。

## 13. 边界政策与部署注意

- **回溯定价修正**：账本永不 UPDATE。迟到信息只影响未来请求；报表如需“修正后口径”，用 plan 链在查询时重算，与账本原始值并存两个口径。
- **回滚能力**：目录变更均有 CatalogChange 记录，可在审计层回答“epoch N 时系统认为的目录是什么”；如需完整时间旅行，可扩展 change 记录 before/after 快照。
- **多实例**：epoch 经 Redis pub-sub 或短周期轮询 `catalog_meta`（单行、极廉价）传播；各实例独立重建，短暂不一致被可用性语义吸收。
- **usage_records 分区**：按月分区，append-only；冷数据可归档到对象存储但保留可查询状态——凭证的归档 ≠ 删除。
- **目录行 upsert 纪律**：厂商静默改规格（同 id 换 context window）允许更新 active 行，但必须留 `model-*` change 事件；能力变更只影响新请求，历史账本钉住的是当时 plan 与 epoch，不受影响。

## 14. 收束

整个设计可压缩为四句话：

- **五层概念正交**：vendor 管出身，model 管型号，provider 管渠道与协议，offering 管具体供给，账本钉住 offering——model id 是厂商给的锚，版本控制的锚在我们自己的追加式实体上。
- **渠道变更被 offering 隔离**：单渠道上下架、调价、劣化都不牵动 model 与其他渠道；同型号多渠道天然支持比价、分流与渠道级 failover。
- **更新即时生效**：epoch 通知 → 快照原子热替换，无重启、无停机；健康旁路刷新不扰动版本。
- **凭证与缓存严格分层**：Postgres 里的账本、价目链、审计事件是唯一的“凭什么”；内存里的快照、聚合、驱动实例全部可弃可重建——丢掉任何运行时状态不构成事故，丢掉任何一行凭证才是。
  文件描述“现在”，数据库为“过去”负责——源 JSON 降级为 seed/导出格式的根本原因，正在于此。
