## 1. 设计原则

### 1.1 核心不变量

> **每一步的“判断”由模型做出，每一步的“事实”由 harness 记录。**
> 强化为**三方记录原则**：对任何一次真实动作，系统必须同时保留三份可对照的记录——
> **声明的**（TurnContract），**授权的**（Capacity），**实际发生的**（Step trace）。
> 三者齐备是审计、回放、复盘的前提。

### 1.2 工程原则

1. **契约先行**：跨包协作只通过 `packages/core` 中的纯类型契约，契约层零运行时依赖。
2. **策略可替换**：Goal-Plan-Execute-Observe-Reflect 闭环是 HarnessStrategy 的一种实现，不是硬编码流程。
3. **Provider 可替换**：所有模型调用经由 `packages/provider-llm`（pi-ai 适配），上层只面向契约编程。
4. **开关即架构**：每个流程节点都是带 FeatureFlag 的可插拔模块；**Flag 关闭 ≠ 数据不产生**——观测点持续 emit，且始终有一个不可关闭的持久化 sink 落盘，仅上层消费 sink 受控。
5. **契约层级化**：**GoalContract（声明要什么）→ TurnContract（声明子任务需要什么）→ Capacity（授权实际拿到什么）**。下层契约只能收窄上层约束，不能放宽。
6. **观测三层对齐执行三层**：Session-Turn-Step 与真实执行结构一一映射，任何 span 可定位到“哪次输入、哪个子任务、哪个最小动作”。
7. **统计双层原则**：厂商数据回答“账单怎么算”，Runtime 数据回答“资源怎么被用掉”；二者同挂 Step，缺一即数据不完整。
8. **韧性优先**：任务具备可恢复性。系统支持 Checkpoint 断点续传（应对进程/网络故障）、任务中断恢复（Turn 级重试/路由切换），以及事件流回放（调试与复盘）。所有外部调用（LLM/Tool）设计需考虑幂等性。
9. **用户为中心**：每个用户请求独立记录其原始输入与交互过程中的反馈，支撑用户画像成长与思维分析；记录内容遵循隐私合规要求，默认保存原始数据，但提供配置开关允许匿名化。

## 3. 核心契约定义

### 3.1 执行三层：Session / Turn / Step

```ts
// packages/core/src/session.ts
/** 用户的一次输入 = 一个 Session（聚合根） */
export interface Session {
  sessionId: string;                       // ULID
  userId?: string;
  rawIntent: string;
  /** 顶层契约（静态声明，生成后基本只读） */
  goal: GoalContract;
  strategyId: string;
  state: SessionState;
  /** Session 显式持有 Turn 实例（执行期由 Plan 层创建） */
  turns: Turn[];
  /** 聚合缓存：Turn 结束时由 usage aggregator 增量写入 */
  aggregate?: SessionAggregate;
  /** 会话级 Flag 快照（求值一次，全程冻结） */
  flagSnapshot: FlagSnapshot;
  createdAt: number;
  endedAt?: number;
  outcome?: 'success' | 'failed' | 'aborted' | 'timeout';
}
export interface SessionAggregate {
  totalTurns: number;
  succeededTurns: number;
  failedTurns: number;
  rolledBackTurns: number;
  totalSteps: number;
  totalTokens: TokenTotals;
  totalCostUsd: number;
  totalDurationMs: number;
  /** context 策略触发计数（效果观测） */
  contextStrategyInvocations: {
    truncate: number; summarize: number; retrieve: number;
    compressObservation: number; cachePromptPrefix: number;
  };
}
export interface TokenTotals {
  input: number; output: number;
  cacheWrite: number; cacheRead: number; reasoning: number;
}
/** 目标拆解出的一个子任务 = 一个 Turn */
export interface Turn {
  turnId: string;
  sessionId: string;
  /** 本 Turn 的任务契约（Plan 层产出，落盘持久化） */
  contract: TurnContract;
  /** 运行时由 Planner 从 contract 组装（请求 → 授权） */
  capacity?: Capacity;
  stepIds: string[];
  status: 'pending' | 'running' | 'succeeded' | 'failed' | 'rolled_back';
  attempt: number;
  /** 断点续传：执行到一半的 Turn 可从此恢复 */
  checkpoint?: TurnCheckpoint;
}
export interface TurnCheckpoint {
  lastCompletedStepSeq: number;
  pendingStepIds: string[];
  accumulatedUsage: TokenTotals;
  accumulatedCostUsd: number;
  savedAt: number;
}
/** 最小执行单元 = 一个 Step（thinking / tool_call / observation） */
export type StepKind = 'thinking' | 'tool_call' | 'observation';
export interface Step {
  stepId: string;
  turnId: string;
  sessionId: string;
  seq: number;
  kind: StepKind;
  payload: ThinkingPayload | ToolCallPayload | ObservationPayload;
  model?: ModelRef;
  /** 四段完整 Usage（见 3.5），thinking/tool_call step 均须挂载 */
  usage?: Usage;
  status: 'pending' | 'running' | 'ok' | 'error' | 'skipped' | 'blocked';
  error?: HarnessError;
  startedAt: number;
  endedAt?: number;
  decisionContext?: DecisionContext;   // 审计用：上下文摘要 + prompt 版本
}
```

**持久化视角**：Session 是聚合根，内存中 `turns` 持有引用；持久化层按 session(1)—turn(N)—step(N) 分表存储，Session 表存 `turnIds` 索引。兼顾对象图完整性（checkpoint/resume 直接重建现场）与查询性能（避免单文档过大）。

### 3.2 两级契约体系

**职责划分**：

| 维度      | GoalContract（Session 级）           | TurnContract（Turn 级）                |
| --------- | ------------------------------------ | -------------------------------------- |
| 目标      | 顶层目标陈述                         | 子任务目标陈述                         |
| 验收      | 整体完成定义（可含跨 Turn 聚合条件） | 本子任务的机械验收标准                 |
| 约束      | **全局硬约束**                 | 继承全局约束，可追加（只能更严）       |
| 工具      | **可用工具域**（上限）         | `requiredTools` ⊆ allowedTools      |
| 权限      | **权限天花板**                 | `maxPermission` ≤ permissionCeiling |
| 预算      | 全局预算 + 保留比例                  | 预算切片（守恒校验）                   |
| 路由      | ❌ 不携带路由信号                    | ✅`tags`（路由唯一信号源）           |
| 失败/回滚 | 整体回滚策略                         | 失败信号 + 子任务回滚方法              |
| 终止      | Session 终止条件                     | 子任务终止条件（防单点死循环）         |

#### 3.2.1 GoalContract

```ts
// packages/core/src/goal.ts
export interface GoalContract {
  goalId: string;
  sessionId: string;
  statement: string;
  /** 整体验收：可含跨 Turn 聚合条件 */
  success: AcceptanceSpec;
  /** 全局硬约束：机器可校验，Policy Engine 执行时强制 */
  constraints: Constraint[];
  /** 可用工具域：TurnContract.requiredTools 的合法上限 */
  allowedTools: string[] | 'all-registry';
  /** 权限天花板：任何 Turn 不得超越 */
  permissionCeiling: PermissionLevel;
  /** 全局预算（切片来源） */
  budget: GlobalBudget;
  termination: TerminationSpec;
  rollbackPolicy: RollbackPolicy;
  /** 策略选择提示（仅供 Strategy 选择，不参与 Provider 路由） */
  strategyHints?: StrategyHint[];
  metadata?: Record<string, unknown>;
}
export interface GlobalBudget {
  maxTurns?: number;
  maxSteps?: number;
  maxTokens?: number;
  maxCostUsd?: number;
  timeoutMs?: number;
  /** 切片时保留该比例的预算应对重规划/重试（默认 0.2） */
  reserveRatio?: number;
}
export interface Constraint {
  kind: 'forbidden-resource' | 'data-boundary' | 'compliance'
      | 'network' | 'spend' | 'custom';
  rule: string;                       // 机器可校验的条件表达式
  description?: string;
}
export type StrategyHint =
  | 'simple' | 'complex' | 'long-horizon' | 'realtime' | 'batch' | (string & {});
```

#### 3.2.2 TurnContract

```ts
// packages/core/src/turn-contract.ts
export interface TurnContract {
  turnContractId: string;
  parentGoalId: string;
  parentPlanNodeId: string;
  statement: string;
  /** 路由标签：Provider 选择的唯一信号源 */
  tags: TaskTag[];
  /** 机械可判定的子任务验收 */
  success: AcceptanceSpec;
  /** 失败信号：什么算失败 + 触发后的处理动作 */
  failureSignals: FailureSignal[];
  /** 工具需求（声明式；⊆ GoalContract.allowedTools） */
  requiredTools: ToolRequirement[];
  /** 本子任务权限上限（≤ permissionCeiling） */
  maxPermission: PermissionLevel;
  /** 预算切片 */
  budget: BudgetSlice;
  /** 预期可观察副作用（供 Observer 差异校验） */
  expectedSideEffects: SideEffectSpec[];
  rollback: RollbackSpec;
  termination: TerminationSpec;       // 防 Turn 级死循环
}
export type TaskTag =
  | SpecialtyTag                      // 业务专长（见 3.4）
  | CapabilityTag                     // 硬能力：'tools' | 'vision' | 'thinking' | 'long-context'
  | (string & {});
export interface ToolRequirement {
  nameOrCapability: string;           // 'fs.write' | 'code-execution' | ...
  /** required：装配缺失即 Turn 失败；optional：缺失时降级继续 */
  required: boolean;
}
export interface FailureSignal {
  kind: 'tool-error' | 'acceptance-failed' | 'budget-exceeded'
      | 'timeout' | 'schema-violation' | 'approval-denied' | (string & {});
  when?: Record<string, unknown>;     // 匹配条件，如 { tool:'browser', statusCode:429 }
  action: 'retry' | 'replan' | 'fallback-provider' | 'escalate-approval' | 'abort-turn';
  maxRetries?: number;
}
export interface BudgetSlice {
  maxSteps?: number;
  maxTokens?: number;
  maxCostUsd?: number;
  timeoutMs?: number;
}
export interface SideEffectSpec {
  scope: SideEffectScope;             // 'fs' | 'net' | 'process' | 'external-api'
  description?: string;
  reversible: boolean;
}
```

#### 3.2.3 三条派生规则（Plan 层强制校验）

Planner 生成 TurnContract 后逐条校验，**任一违反即拒绝出计划**，并 emit `plan.invalid` 事件：

1. **工具收窄**：`turnContract.requiredTools ⊆ goalContract.allowedTools`；
2. **权限收窄**：`turnContract.maxPermission ≤ goalContract.permissionCeiling`；
3. **预算守恒**：`Σ turnContract.budget.maxCostUsd ≤ goalContract.budget.maxCostUsd × (1 − reserveRatio)`（maxTokens 同理）。
   **防御纵深**：TurnContract 只是声明。即使 Planner 有 bug 生成越权契约，执行期 Policy Engine 仍按 **GoalContract 约束 ∩ TurnContract 声明 ∩ Capacity 授权** 三者交集放行——声明层收窄是第一道防线，策略层强制是最后一道。

### 3.3 Capacity 契约（运行时授权产物）

```ts
// packages/core/src/capacity.ts
export interface Capacity {
  /** 路由决策选中的模型 */
  model: ModelRef;
  /** 本次允许调用的工具白名单（schema 已校验、已解析） */
  tools: ToolSpec[];
  /** 本次允许的权限级别 = min(契约声明, 工具需求, 运行时限额) */

export interface ToolSpec {

  description: string;
  parameters: unknown;                // TypeBox schema，与 pi-ai Tool.parameters 对齐
  minPermission: PermissionLevel;
  irreversible?: boolean;             // 触发审批门
  sideEffects: SideEffectScope[];
}
```

### 3.4 Provider 扩展模型

Provider 不再只是“模型端点”，而是带**业务画像、实时性能、分时定价、经济性统计**的路由决策源。

```ts
// packages/core/src/provider.ts
export interface Provider {
  id: string;
  vendor: string;
  models: ModelDescriptor[];
  tags: ProviderTag[];                // 硬能力标签
  limits: { rpm?: number; tpm?: number; concurrency?: number };
  /* ── 业务专长标签（语义路由信号） ── */
  specialties: SpecialtyTag[];
  /* ── 性能画像（Runtime 滚动统计自动填充） ── */
  performance: PerformanceProfile;
  /* ── 分时定价 ── */
  pricing: PricingSchedule;
  /* ── 经济性画像（含 Tag 细分） ── */
  economics: EconomicsProfile;
  /** 兼容保留，逐步被 pricing/economics 取代 */
  costWeight: number;
  health: { score: number; lastErrorAt?: number };
}
export interface ModelDescriptor {
  id: string;
  contextWindow: number;
  supportsTools: boolean;
  supportsThinking: boolean;
  supportsVision: boolean;
}
export type SpecialtyTag =
  | 'frontend-ui-generation'    // 前端 UI / 组件生成
  | 'scenario-dialogue'         // 情景对话 / 角色扮演
  | 'scientific-research'       // 科研 / 学术写作
  | 'code-refactoring'          // 代码重构 / 大仓库理解
  | 'data-analysis'             // 数据分析 / SQL / 表格推理
  | 'creative-writing'
  | 'math-reasoning'
  | 'multimodal-understanding'
  | 'long-document-analysis'
  | 'tool-use-reliability'      // 工具调用可靠度高
  | 'fast-classification'       // 高速分类 / 抽取
  | 'summarization' | 'translation'
  | (string & {});              // 允许业务自定义扩展
export interface PerformanceProfile {
  tokensPerSecond: Percentile;
  ttftMs: Percentile;                 // 首 token 延迟
  e2eLatencyMs: Percentile;
  errorRate: number;                  // 滚动错误率 0-1
  /** 该模型生成 toolCall 的 schema 遵从率 */
  toolCallSchemaCompliance: number;
  /** 样本数（低于阈值时路由降权，新 Provider 进灰度桶） */
  sampleSize: number;
  windowMs: number;                   // 滚动窗口，如 3600_000
  lastUpdated: number;
}
export interface Percentile { p50: number; p90: number; p95: number; p99?: number; }
export interface PricingSchedule {
  currency: 'USD';
  base: {
    inputPerMTok: number;
    outputPerMTok: number;
    cacheWritePerMTok?: number;
    cacheReadPerMTok?: number;
    reasoningPerMTok?: number;
  };
  /** 时段档位：请求时刻命中的第一个 tier 生效 */
  tiers: PricingTier[];
  effectiveAt: number;                // 版本化，成本差异可审计
  version: string;
}
export interface PricingTier {
  name: string;                       // 'night-batch' | 'off-peak' | 'peak'
  /** UTC 小时区间，半开区间语义 [start, end)，如 [0,8) = UTC 00:00–08:00 */
  windowHoursUtc: [number, number];
  multiplier: number;                 // 0.5 = 半价，1.2 = 高峰加价
  appliesTo?: ('input' | 'output' | 'cache-write' | 'cache-read' | 'reasoning')[];
}
export interface EconomicsProfile {
  avgTaskCostUsd: number;
  avgTokensPerTurn: { input: number; output: number };
  costPerQualityScore: number;        // cost / 平均评估分，越低越好
  retryRate: number;
  sampleSize: number;
  /** 按 specialtyTag 细分的画像：路由评分优先消费此处 */
  perTag?: Record<string, TagEconomics>;
  lastUpdated: number;
}
export interface TagEconomics {
  avgTokensPerTurn: { input: number; output: number };
  avgTaskCostUsd: number;
  successRate: number;
  /** < 30 时该 tag 维度评分回退到 Provider 整体画像 */
  sampleSize: number;
}
```

### 3.5 Usage 双层统计

**设计原则**：厂商数据不可伪造（账单口径），Runtime 数据不可省略（策略优化口径）。

```ts
// packages/core/src/usage.ts
/* ── Part 1: 厂商层（LLM 响应返回，账单口径，与 OTel GenAI semconv 对齐） ── */
```

### 3.8 用户交互与思维记录（v1.2 调整）

**设计目标**：为每个用户请求（Session）建立独立的行为与思维记录，作为用户画像成长和思维分析的基础数据。记录内容包含用户原始输入、执行过程中的关键决策与反馈，以及最终结果。记录在用户输入完成后立即创建，并在 Session 生命周期内持续更新。

**与事件系统的集成**：

- 新增事件类型 `user.input.recorded`（创建记录时发出）和 `user.feedback.captured`（捕获到用户反馈时发出）。
- `user-profile` 模块作为事件消费者，其写入操作异步进行，不影响主流程性能。

## 4. Plan 层：从 GoalContract 到 Capacity 的流水线

### 4.1 总流程

```
GoalContract
  │
  ▼
Planner.plan(goal)
  ├─ 1. 分解：goal → PlanGraph，每节点生成 TurnContract 草稿
  ├─ 2. 派生校验：三条收窄规则（工具/权限/预算），违反 → emit plan.invalid，拒绝出计划
  ├─ 3. 预算切片（见 4.3）
  ├─ 4. TurnContract 落盘（与 goal.md 同级，作为 Turn 执行与事后审计的引用源）
  ▼
执行期（每个 Turn）
  │
Planner.assembleCapacity(turn)
  ├─ turn.contract.tags ──────────► ProviderRouter.select()（初期降级规则 / 后期六因子评分）
  ├─ turn.contract.requiredTools ─► registry 解析为 ToolSpec[]（schema 校验；
  │                                  optional 缺失 → 降级并 emit capacity.degraded）
  ├─ permission = min(contract.maxPermission,
  │                  tools 的 minPermission 最大值,
  │                  policy 引擎运行时限额)
  ├─ turn.contract.budget ────────► Capacity.budget
  └─ 沙箱配置（按 expectedSideEffects 推导）
  ▼
Capacity（授权产物，交付 Executor）
```

### 4.2 路由策略：初期降级与后期六因子

**初期（MVP）路由**：Provider 画像数据不足时采用**能力过滤 + 成本排序 + 健康检查**的简单规则：

- 硬性过滤：支持所需 CapabilityTag（如 tools/vision）且健康评分 > 0.5；
- 按当前时刻的有效单价（base × tier multiplier）排序，选择最低成本者；
- 若最低成本 Provider 不可用（连续失败），按成本递增顺序尝试下一个；
- 记录所有路由决策事件 `provider.selected`，供后续离线分析校准。
- 该模式由 Flag `planner.routing-mode` 控制，可选值为 `simple` 或 `full`。

**后期（数据积累后）启用六因子评分**（Flag `planner.routing-mode=full`）：

```
score = w1 × capabilityMatch      // 硬能力匹配，不满足直接出局
      + w2 × specialtyMatch       // turn.contract.tags ∩ provider.specialties
      + w3 × costEfficiency       // PricingSchedule 时段加权 + perTag 经济画像
      + w4 × latencyFit           // TTFT / tok/s 与任务 SLA 匹配
      + w5 × reliabilityScore     // errorRate + toolCallSchemaCompliance
      + w6 × healthScore
```

```
specialtyMatch = |turn.tags ∩ specialties| / max(1, |turn.tags|)
// 当前 UTC 时刻命中 tier 后的有效价格
tier = pricing.tiers.find(t => hourUtc ∈ [t.windowHoursUtc[0], t.windowHoursUtc[1]))
effIn  = base.inputPerMTok  × (tier?.multiplier ?? 1)
effOut = base.outputPerMTok × (tier?.multiplier ?? 1)
// token 消耗估计优先取 perTag 画像（sampleSize ≥ 30），否则回退整体画像
{avgIn, avgOut} = economics.perTag[specialtyTag]?.sampleSize >= 30
                  ? perTag[specialtyTag] : economics
costEfficiency = 1 / (effIn × avgIn + effOut × avgOut)
```

**CapabilityTag 参与硬性过滤（w1），SpecialtyTag 参与软性评分（w2）。**
**权重经 Flag 注入并支持 A/B**：

```json
{
  "key": "planner.route-weights",
  "type": "string",
  "defaultValue": "w1=0.3,w2=0.2,w3=0.2,w4=0.1,w5=0.1,w6=0.1",
  "rules": [
    { "match": { "goalTagIn": ["realtime"] },
      "value": "w1=0.3,w2=0.1,w3=0.1,w4=0.3,w5=0.1,w6=0.1",
      "source": "latency-sensitive-profile" }
  ]
}
```

**故障转移**：首选失败 → 按评分/成本顺序尝试次优（带退避），emit `provider.fallback`。

### 4.3 预算切片算法

```
可分配预算 = goal.budget.maxCostUsd × (1 − reserveRatio)     // reserveRatio 默认 0.2
1. 加权：weight_i 由 estimatedSteps 与所需 tag 下模型价位估算
2. 切片：slice_i = 可分配预算 × weight_i / Σweight
3. 下限保护：每片不低于该 tag 下最便宜可用模型的最小任务成本
   （参考 economics.perTag[tag].avgTaskCostUsd，避免切片小到必然失败）
4. 归还：Turn 成功后未用尽的 slice 预算归还全局池，供重规划使用
```

**静态兜底（冷启动）**：当 `economics.perTag` 样本量不足（<30）或不存在时，采用**均分策略**：每个 Turn 均分可分配预算，并设置绝对下限 `MIN_TURN_BUDGET_USD`（默认 $0.01）。随着数据积累，自动切换到加权切片。该行为由 Flag `planner.budget-slicing-mode` 控制（`simple`/`weighted`）。

**超支路径**：Turn 级超支 → 按 `contract.failureSignals` 中 `budget-exceeded` 的 action 处理；retry 需从全局保留池追加，追加经 Policy Engine 校验并 emit `budget.reallocation`；Session 级超支 → 触发 GoalContract.termination。

### 4.4 策略选择的三级信号

tags 下沉后，`strategy.score()` 的信号源改为：

1. **显式提示**：`goalContract.strategyHints`（意图分类层产出）；
2. **结构评分**：`PlanEstimate`——estimatedTurns、hasIrreversibleActions、constraintCount、estimatedCostUsd，由 Planner 轻量预估；
3. **动态升降级**：flag `strategy.auto-escalate` 允许 plan-execute 在观察到连续失败信号时热切换 full-loop，切换事件（`strategy.switched`）落 trace 保证可审计。

## 5. Token 统计与成本核算体系

### 5.1 三个采集点

```
┌─ 采集点 A：Context 组装阶段（Executor，请求发出前）
│    TokenizerRegistry 对各段分别精确计数 → RuntimeContextBreakdown
│    ├─ systemPrompt / history / toolSchema / newInput / observation / retrieved / example
│    └─ 求和得 totalContextTokens；与 window 比值得 utilization
│
├─ 采集点 B：LLM 流结束（provider-llm Driver，stream final 事件）
│    捕获厂商原生 usage → VendorUsage；捕获 TTFT/totalMs → UsageTiming
│    emit 'llm.response'
│
└─ 采集点 C：成本计算与回填（usage 包 Aggregator，消费 llm.response）
    查 ProviderRegistry 取 PricingSchedule → 按当前 tier 计价 → CostBreakdown
    回填 estimationDriftTokens；将完整 Usage 挂到对应 Step
```

**TokenizerRegistry**：按 `ModelRef.vendor` 路由——OpenAI 用 tiktoken；Anthropic 用官方 tokenizer；其他厂商用保守估算（字符数 × 0.25 加安全余量）。估算漂移通过 `estimationDriftTokens` 透出，超阈值（5%）告警并切换更精确实现。

### 5.2 聚合规则

```
Step.usage        ← 直接记录（四段完整）
Turn.aggregate    ← Σ step.usage.vendor + Σ step.usage.cost
                    + steps 间 contextDelta 曲线（context 膨胀轨迹）
Session.aggregate ← Σ turn.aggregate + contextStrategyInvocations 计数
```

### 5.3 聚合视图与反馈路径

| 视图                   | 聚合键                                   | 回答的问题                     | 反馈去向                  |
| ---------------------- | ---------------------------------------- | ------------------------------ | ------------------------- |
| Token 蒸发曲线         | session × stepSeq × contextDelta       | context 是否持续膨胀、何时失控 | Context 策略              |
| System Prompt 占比分布 | provider × systemPromptRatio 直方图     | 系统提示是否冗长               | Prompt 瘦身 → 失败分类账 |
| 缓存命中率             | provider × (cacheRead/input)            | 前缀是否稳定、缓存策略是否生效 | 启用 cache-prompt-prefix  |
| Reasoning 占比         | model × (reasoning/output)              | thinking 预算是否过度          | thinking budget 调整      |
| 单任务成本分布         | strategy × provider × totalCostUsd     | 哪种策略×模型组合性价比最优   | 路由权重 / 预算切片       |
| 模型切换点             | session × stepSeq × provider（变更处） | 是否频繁换模型、一致性是否受损 | 路由稳定性                |

**四条反馈主路径**（规则外置为 Context 策略配置，由策略模块加载执行）：

1. **→ Context 策略**（闭环最短）：
   - 触发条件与动作定义在 `context-policy.config.json` 中，例如：
     ```json
     {
       "rules": [
         {
           "id": "auto-summarize-on-high-util",
           "condition": "contextWindowUtilization > 0.9 for 3 consecutive steps",
           "action": "summarize-history"
         },
         {
           "id": "suggest-prompt-slim",
           "condition": "systemPromptRatio > 0.4",
           "action": "log-to-failure-ledger"
         },
         {
           "id": "enable-cache-prefix",
           "condition": "cacheRead/input < 0.3 and systemPromptTokens > 2000",
           "action": "cache-prompt-prefix"
         },
         {
           "id": "compress-large-observations",
           "condition": "observationTokens/total > 0.5",
           "action": "compress-observation"
         }
       ]
     }
     ```
   - 策略模块定期（或事件驱动）评估条件并执行动作，所有动作记录 `context.strategy.applied`。
2. **→ Provider 路由**：
   - 某任务类型的 token 效率持续低于同类均值 → 降低该 Provider 在该 tag 的 specialty 权重
   - `costPerQualityScore` 劣于替代 Provider → 路由权重自动调整（写 perTag 画像）
3. **→ 成本与预算**：
   - Plan 层预算切片参考 `economics.perTag.avgTaskCostUsd`，而非拍脑袋
   - 非实时任务可延迟到 off-peak tier 执行（价格档位感知调度）
4. **→ 训练与评估**（治理回路）：
   - Step 级 Usage + Outcome 成对样本进评估集，支撑“context 组成 ↔ 成功率”回归分析
   - 高成本失败案例（cost > P95 且 outcome=failed）自动入失败分类账

### 6.2 事件持久化默认策略

- **不可关闭的持久化 sink**：EventBus 内置一个 `FileSink`（或 `QueueSink`），该 sink **不受任何业务 Flag 控制**，仅受基础设施配置（如环境变量 `EVENT_LOG_DIR`）控制。所有事件异步写入 JSONL 文件（按 sessionId 分文件或按时间滚动），保证审计数据永不丢失。
- 业务 Flag（如 `observe.enabled`）只控制是否将事件推送给**额外消费者**（指标聚合、实时告警、看板），不影响落盘。
- 该设计确保 `Flag 关闭 ≠ 数据不产生` 且 `Flag 关闭 ≠ 数据不持久化`。

### 6.3 回放语义：事件流回放 vs 任务中断恢复

| 维度                   | 事件流回放（Event Replay）                               | 任务中断恢复（Task Recovery）                                     |
| ---------------------- | -------------------------------------------------------- | ----------------------------------------------------------------- |
| **目的**         | 调试、审计、复盘、指标重建                               | 从故障（进程崩溃、网络中断、Provider 不可用）中继续执行           |
| **依赖**         | 已持久化的事件日志（包含完整输入输出、版本信息、决策链） | Checkpoint（Turn 级状态、已完成 Step 序列、预算使用）             |
| **是否调用模型** | 否，不重新调用任何 Provider；仅重放记录的事件流          | 是，可能调用 Provider 继续未完成的 Step，或触发路由重选           |
| **产出**         | 可视化决策链、指标重算、失败分析                         | 任务最终完成或明确失败                                            |
| **实现方式**     | `EventBus.replay(sessionId)` 重放事件，不改变任何状态  | Recovery 模块读取 TurnCheckpoint，恢复 Session 状态，注入缺失事件 |
| **幂等性要求**   | 无（只读）                                               | 高：已完成的 Step 不可重复执行；重试必须安全                      |

**事件流回放示例**：给定 sessionId，返回该会话的全部 `HarnessEvent` 列表（包含当时的模型请求、响应、工具调用结果、路由决策、策略触发等），开发者可在本地重现完整决策过程，无需访问外部服务。

**任务中断恢复示例**：假设 Turn 执行到 Step 5（共 10 步）时进程崩溃。重启后，Recovery 模块从持久化存储加载 TurnCheckpoint（已完成的 Step 1-4 的结果与 Usage），重建内存中的 Turn 状态，并从中断点继续执行 Step 5。若 Provider 不可用，则触发 `provider.fallback` 选择备用模型。恢复过程会补齐缺失的事件（如 `turn.resumed`），保证事件流连续。

在 5.3 的 Token/成本视图之上，叠加 Tag 维度、治理视图与用户行为视图：

| 视图                | 聚合键                                               | 回答的问题                         | 反馈去向                             |
| ------------------- | ---------------------------------------------------- | ---------------------------------- | ------------------------------------ |
| Tag 成本分布        | turn.tags × avgCost / avgTokensPerTurn              | 前端任务 vs 科研任务成本结构差异   | 预算切片权重校准                     |

## 7. 反馈与校准回路

```
Step 级 Usage + Outcome + UserInteractionRecord（含用户反馈）
        │
        ▼
  聚合视图（§5.3 / §6.4）
        │
   ┌────┼──────────┬─────────────┬──────────────┐
   ▼    ▼          ▼             ▼              ▼
Context   Provider   预算/调度     训练管线      用户画像/思维分析
策略      路由/画像   （tier 感知）  （可验证奖励） （个性化与改进）
   │    │          │             │              │
   └────┴──────────┴─────────────┴──────────────┘
                 │
                 ▼
          失败分类账（每条规则可追溯一次具体失败）
                 │
                 ▼
        Harness 迭代（prompt 修订 / schema 调整 / hook 增加 / 指标新增）
          同时警惕过度工程：模型升级后旧脚手架敢于删除
```

校准体系自身成环：评估结果反馈给模型（反思层）、反馈给 harness（失败账本）、反馈给训练（可验证奖励）、反馈给用户画像（个性化体验）。**最可靠的 agent 不是模型最强，而是“模型—harness—评估—用户”耦合度最高。**

### 7.1 失败分类账最小实现

- **存储**：数据库表 `failure_ledger`，记录字段：
  - `sessionId`, `turnId`, `stepId`, `failureSignalKind`, `costUsd`, `providerId`, `tags`, `summary`, `createdAt`
- **写入时机**：
  - 当 Turn 失败且处理动作为 `abort-turn` 或最终失败时；
  - 当某 Step 产生高成本失败（cost > P95 且 outcome=failed）时。
- **消费方式**：人工定期 review，或通过脚本生成报告，识别高频失败模式，驱动 Harness 改进（新增 hook、调整 prompt、增加校验等）。
- 分类账本身不自动触发代码变更，只作为改进依据。

### 7.2 用户画像成长与思维分析回路

- **数据源**：`UserInteractionRecord` 表（按用户 ID 聚合，包含原始输入与反馈）。
- **画像维度**：
  - 使用频率、活跃时段；
  - 偏好任务类型（intent.category 分布）；
  - 思考模式（planning vs reactive，基于 thoughtTrace.category 比例）；
  - 对延迟/成本的敏感度（基于历史交互中用户反馈与任务时长的相关性）；
  - 满意度趋势（基于 feedback 类型分布与评分）。
- **更新机制**：每日离线批处理，聚合新写入或更新完成的 `UserInteractionRecord`，更新用户画像快照。
- **应用场景**：
  - **个性化策略选择**：根据用户历史偏好（如喜欢详细规划），调整 StrategyHints 的默认权重。
  - **个性化路由**：若用户对成本敏感，优先选择经济型 Provider（结合分时定价）。
  - **主动干预**：若检测到用户连续多次给出负面反馈，可触发更保守的策略或建议用户调整需求。
- **隐私保护**：默认保留原始输入以便分析，但可通过 Flag 启用匿名化；所有分析遵循数据治理政策。

## 8. Feature Flag 与 A/B 实验

**核心机制**：Flag 静态声明 + 运行时按 Session 上下文求值 + 快照冻结到 Session；**关闭 ≠ 数据不产生**——emit 不受控，且默认持久化 sink 始终落盘，仅额外 sink 消费受控。

```ts
// A/B 示例：对比路由算法 v2（六因子含 specialty/分时定价）
const flags: FeatureFlagDefinition[] = [
  {
    key: 'ab.planner.route-v2',
    description: '六因子路由 v2 vs 规则路由 v1',
    type: 'boolean',
    defaultValue: false,
    rules: [
      { match: { bucketRange: [0, 49] },  value: true,  source: 'exp-route-v2-2026-09' },
      { match: { bucketRange: [50, 99] }, value: false, source: 'exp-route-v2-2026-09' },
    ],
  },
]
```

**A/B 无需旁路系统**：实验分组由 `flagSnapshot.trace` 自动携带，观测层按 flag 值分组聚合各指标即得对照结论。Turn 级 flag（匹配 `turnTagIn`）可对特定任务类型做精细化实验。

**默认 Flag 集**：

| Flag                            | 影响范围      | 关闭后行为                                 |
| ------------------------------- | ------------- | ------------------------------------------ |
| `observe.enabled`             | Observer 模块 | 不消费事件，但事件仍 emit 且持久化落盘     |

## 10. Policy Engine 拦截时序（以 tool_call 为例）

```
模型输出 tool_call 请求
        │
        ▼
[Executor] 构建 ToolCallPayload（含参数、目标工具、预期副作用）
        │
        ▼
[Policy Engine] 同步校验（阻塞执行）
        ├─ 1. 工具是否在 Capacity.tools 白名单内？          否 → tool.blocked
        ├─ 2. 所需权限 ≤ Capacity.permission？            否 → tool.blocked
        ├─ 3. 参数 schema 是否通过校验？                   否 → tool.blocked
        ├─ 4. 是否满足 GoalContract.constraints 全部规则？ 否 → policy.denied
        ├─ 5. 若工具 irreversible=true 或权限 ≥ draft，
        │     是否满足审批门要求？（approval.gate）        否 → approval.requested
        │         └─ 审批通过 → 继续；审批拒绝 → tool.blocked
        └─ 6. 预算检查：当前 Turn 累计成本 + 预估成本 ≤ Capacity.budget？ 否 → budget.exceeded
        │
        ▼
[Executor] 执行工具调用（沙箱内）→ tool.invoke → tool.result
        │
        ▼
[Observer/Reflector] 对比结果与预期副作用，更新 Turn 状态
```

- **同步校验**：1-6 均为阻塞式，确保越权或超预算的工具调用不会发生。
- **审计记录**：每一步校验结果均 emit 对应事件（`policy.check`/`policy.denied`/`tool.blocked`/`budget.exceeded`），并附加在 Step trace 中。
- **性能考虑**：校验逻辑轻量，规则表达式预编译，预计单次校验 < 1ms（不含审批等待）。

## 11. 端到端执行流程（full-loop 策略）

```
用户输入
  ▼
[Runtime] 创建 Session：求值 FlagSnapshot 并冻结 → session.flagSnapshot
  │
  ├─ [User Profile] 立即创建 UserInteractionRecord（保存 rawInput，状态 recording）
  │     emit user.input.recorded
  ▼
[Goal 层] 生成 GoalContract（落盘 goal.md：success/failure/constraints/
          allowedTools/permissionCeiling/budget+reserveRatio/termination）
  ▼
[Strategy 选择] strategyHints + PlanEstimate 结构评分 → 选出 FullLoopStrategy（emit strategy.selected）
  ▼
[Planner.plan]
  ├─ 分解 → PlanGraph（每节点生成 TurnContract 草稿）
  ├─ 三条派生校验（失败 → emit plan.invalid，终止）
  ├─ 预算切片（加权 + 下限保护 + 保留比例；冷启动均分兜底）
  └─ TurnContract 落盘（emit plan.created）
  ▼
[Executor：对每个 Turn]
  ├─ Planner.assembleCapacity：tags→路由（初期简单规则 / 后期六因子）（emit provider.selected）
  │   ├─ requiredTools 解析（optional 缺失 → emit capacity.degraded）
  │   ├─ permission = min(声明, 工具需求, 运行时限额)
  │   └─ budget 切片注入（emit capacity.assembled）
  ├─ 逐 Step 执行：
  │   ├─ 采集点A：context 分段计数 → RuntimeContextBreakdown
  │   ├─ PiAiDriver.stream（采集点B：final 时捕获 VendorUsage + Timing，emit llm.response）
  │   ├─ 采集点C：Aggregator 计价（CostBreakdown，emit 后回填 estimationDrift）
  │   ├─ tool_call 命中 Policy Engine 校验（见 §10）
  │   │   ├─ 通过 → tool.invoke → tool.result
  │   │   ├─ 需审批 → approval.requested → approval.granted（用户可能给出反馈）
  │   │   └─ 拒绝 → tool.blocked → 反思层介入
  │   └─ context 压力触发策略 → context.strategy.applied
  ├─ 观察层（若启用）：结构化回注，锚定 contract.expectedSideEffects
  │
  ├─ [User Profile] 根据事件流更新 UserInteractionRecord：
  │     - 补充 thoughtTrace / actionTrace
  │     - 捕获用户反馈（如 approval 决策、输出评分）
  ▼
[Reflector（若启用）] 对照 turn.contract.success 独立评估
  ├─ 通过 → Turn 完成，slice 剩余预算归还全局池
  ├─ 失败 → 按 contract.failureSignals 处理（retry / fallback-provider /
  │         replan / escalate-approval / abort-turn）
  │         retry 追加预算 → policy 校验 → emit budget.reallocation
  └─ 连续失败 + strategy.auto-escalate → strategy.switched → 升级 full-loop
  ▼
[Session.ended] 聚合指标上报 + 失败分类账更新
  │
  └─ [User Profile] 完成 UserInteractionRecord：写入 outcome 和 metrics，状态置 completed
        emit user.interaction.updated
```

**中断恢复流程（穿插在 Executor 内部）**：每个 Step 成功后立即更新 TurnCheckpoint（持久化）。若进程崩溃，恢复时加载最新 Checkpoint，跳过已完成 Step，从中断点继续；若 Provider 不可用，则触发故障转移（见 §4.2）。恢复期间，`UserInteractionRecord` 保持 `recording` 状态，继续更新。

## 12. 验收标准

| #  | 验收项                     | 标准                                                                                                                                 |
| -- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 1  | 三层观测完整性             | 任意事件可通过 sessionId/turnId/stepId 定位；缺必填 ID 即报错                                                                        |
| 2  | 两级契约校验               | 构造`requiredTools ⊄ allowedTools` 或 `maxPermission > ceiling` 的 TurnContract，Planner 必须拒绝出计划并 emit `plan.invalid` |
| 3  | 预算守恒                   | Σ 切片 ≤ 全局 × (1−reserveRatio)；Turn 成功后剩余 slice 可归还全局池；冷启动均分时满足同一守恒条件                               |
| 4  | 路由信号下沉               | Provider 选择只读取 turn.contract.tags；GoalContract 上无任何路由字段                                                                |
| 5  | Usage 双层完整             | 每个含 LLM 调用的 Step，usage.vendor 与 usage.runtime 字段齐备；runtime 段须含 systemPromptRatio / contextDelta / strategyApplied    |

| 7  | 估算漂移受控               | estimationDriftTokens 超阈值（5%）时告警；切换 tokenizer 后漂移下降                                                                  |
| 8  | 策略可替换                 | 新增 HarnessStrategy 实现无需改 runtime；策略切换/升级落 trace（strategy.selected / strategy.switched）                              |
| 9  | Provider 可替换            | pi-ai 仅存在于 provider-llm 包；grep 验证其他包无引用                                                                                |
| 10 | Flag 关闭 ≠ 数据丢失      | 关闭 observe.enabled 后，JSONL trace 仍含完整 llm.request / tool.invoke / usage 流水                                                 |
| 11 | A/B 对照                   | 同一 flag 不同 bucket 的 Session 在成本/成功率/Turn 数指标上可自动分组对比                                                           |
| 12 | 契约零依赖                 | packages/core 的 dependencies 为空，可独立编译发布                                                                                   |
| 13 | 三方记录可对照             | 任意动作可取回 TurnContract（声明）、Capacity（授权）、Step trace（实际）三方记录并 diff                                             |
| 14 | 审计可重建                 | 凭事件日志离线重放任意 Session 完整决策链（事件流回放）                                                                              |
| 15 | 任务可恢复                 | 模拟进程崩溃后能从 TurnCheckpoint 恢复，跳过已完成 Step，不重复执行；Provider 不可用时能故障转移                                     |
| 16 | Tag 画像反馈               | Provider-Tag 适配度视图数据可回写 economics.perTag，且 sampleSize < 30 时路由回退整体画像                                            |
| 17 | 失败可追溯                 | 每个 harness 组件能说清“因哪次具体失败而存在”，说不清即冗余；失败分类账记录必要字段可供查询                                        |
| 18 | **用户记录即时创建** | Session 创建后立即生成 UserInteractionRecord，包含完整原始输入，状态为 recording                                                     |
| 19 | **反馈完整捕获**     | 用户在会话期间的决策更改、授权操作、输出结果评价均被记录在 feedback 数组中，并有事件发出                                             |
| 20 | **画像更新及时**     | 用户画像快照在每日批处理后反映前一天的用户行为；查询接口延迟 < 100ms                                                                 |

## 13. 演进路线

| 阶段         | 目标                   | 关键交付                                                                                                                                                                         | 依赖条件            |
| ------------ | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| M1           | **MVP 核心闭环** | 基础 Session/Turn/Step 模型，Goal/Turn 契约，简单路由（能力+成本），Policy 基础拦截，Usage 双层采集，事件持久化，Checkpoint 恢复，**UserInteractionRecord 基础写入与更新** | 无                  |
| M2           | 沙箱与审批             | policy 包：PermissionEngine + ApprovalGate + 进程级隔离                                                                                                                          | M1                  |
| M3           | 持久化 Memory          | checkpoint/resume（增强）、检索、跨 Session 记忆                                                                                                                                 | M1                  |
| M4           | 独立 Reflector         | LLM-as-judge + 校准集（Platt/isotonic），替换规则评估                                                                                                                            | M1 + 数据积累       |
| M5           | 六因子路由             | 启用画像数据，加权评分；时段感知调度；故障转移；灰度桶                                                                                                                           | 积累 >10k Turn 数据 |
| M6           | A/B 实验平台           | experiment 管理 API + 自动聚合报表                                                                                                                                               | M1 + 观测体系完整   |
| M7           | 策略生态               | 开放 HarnessStrategy 插件协议，第三方包注册策略                                                                                                                                  | M1 + 稳定性验证     |
| **M8** | **用户画像深化** | 基于 UserInteractionRecord 的用户画像分析平台，个性化策略与路由建议                                                                                                              | M1 数据积累         |

**MVP 范围界定**：M1 必须完成，M2 推荐包含（生产安全），M3-M8 可逐步引入。初期路由使用简单规则，预算切片使用均分兜底，用户画像仅做基础记录和简单统计，待数据量足够后再升级。

## 附录：文档变更要点总结（v1.1 → v1.2）

- 调整 `UserInteractionRecord` 契约：移除强制脱敏要求，新增 `rawInput` 字段保存原始输入，`inputTimestamp` 记录输入时间。
- 写入时机改为**用户输入完成后立即创建**，后续通过事件流持续更新，最终在 Session 结束时标记完成。
- 新增 `UserFeedback` 接口，支持决策更改、授权操作、输出评分、文本反馈等多种类型。
- 事件类型新增 `user.input.recorded`、`user.feedback.captured`、`user.interaction.updated`。
- Flag 调整：移除 `user-profile.full-content`（不再需要，默认保存原始内容），新增 `user-profile.anonymize` 控制匿名化。
- 更新流程描述，使 `user-profile` 模块在 Session 生命周期内持续运行，而非只在结束时生成。
- 验收标准相应修改，强调即时创建和反馈捕获。
