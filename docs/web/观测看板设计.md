# 观测看板设计（右侧边栏审计面板）

> **版本**：v2
> **定位**：WebUI 右侧边栏的「审计」页。点击主对话区的 Task / Step 时，面板展示该执行单元的
> Vendor 实际用量、Runtime 输入估算（breakdown）、输出估算、成本双口径与漂移，落实
> docs/webui.md §1.1「透明即信任 / 实时可观测」。
> **依赖契约**：packages/libs StepUsage（第 2 节）。

---

## 1. 目标

- 点击任意 Step / Task，右侧边栏切到「审计」页展示其可观测事实。
- **以 Conversation 为单位**：同一 Conversation 内所有 Session（run）共享上下文，审计的
  context diff 是贯穿全部 run / task / step 的一条连续线。
- **Vendor 实际用量**与 **Runtime 估算**分开展示，并给出两者漂移与漂移率。
- Runtime breakdown 只描述 **input（上下文）** 的估算；输出侧单独估算。
- Context 占比用环形饼图呈现（按显示段归一化并保底最小扇区），点击分段可查看该段原文。
- 展示与上一轮相比**新增的上下文内容**（diff 文本），以及逐步骤 Context Diff。
- 审计只展示用量/成本/上下文事实，**不展示工具与模型输出正文**；步骤明细仅在 Task/Run 目标展示。
- 成本分「vendor 实际」与「breakdown 估算」两个口径，并给出漂移率。
- 数据实时：执行中点击正在运行的 Step，随 SSE 增量刷新。

### 1.1 非目标

- 不做跨会话趋势、成本对账、配额、定价管理。
- 不新增 API 端点：复用 GET /api/sessions/:id/timeline 快照与 SSE step 事件的 usage 载荷。

## 2. 术语与口径

### 2.1 Vendor 实际（厂商上报，权威口径）

| 字段 | 含义 |
| --- | --- |
| input tokens | 本轮请求输入（含 cache read）|
| output tokens | 本轮模型输出（含 reasoning）|
| cached input tokens | 命中缓存的输入（⊆ input）|
| reasoning output tokens | 思考输出（⊆ output）|
| total | input + output |

### 2.2 Runtime 输入估算（breakdown，只描述 input）

用真实 tokenizer 对「本轮请求的完整上下文」分段落估算，各段之和 = totalContextTokens：

| 段落 | 含义 |
| --- | --- |
| system prompt | 系统提示词 |
| user history | 历史用户消息 |
| assistant thinking | 历史 assistant 内容（思考 + 正文）|
| tool-call args | 历史 assistant 工具调用参数（JSON）|
| tool schema | 工具定义（JSON Schema）|
| new input | 本轮新增输入（最后一条 user 消息）|
| observation | 工具结果（role=tool，回注上下文）|
| retrieved / examples | 检索/示例（可选，缺省 0）|

说明：observation 是工具结果，属于下一轮请求的 **input context**（ReAct 语义）；assistant 生成的
思考与工具调用参数分别计入 assistant thinking 与 tool-call args。

每段同时保留**原文**（contents，按段截断，供 UI 点击查看）；并保留相对上一轮**新增内容**
（diffContent，按消息边界取增量，首轮为 newInput）。原文与 diff 只用于审计展示，不参与计量。

**Conversation 共享上下文**：同一 Conversation 续聊时，新 Session 的请求前置此前轮次
（用户输入 + 助手最终回答，最多 10 轮，回答截断 4000 字符），因此 history 段包含跨 Session 的
对话历史。diffContent 按「本 Task 内消息边界」取增量，首个 round 只含本轮新输入，不含前置历史。

### 2.3 输出估算

- estimate.output：用同一 tokenizer 对「本轮非 reasoning 输出文本」估算的 token。
- 与 vendor 对比口径为 **vendor.output − vendor.reasoning**（不含 reasoning）。

### 2.4 漂移与漂移率

| 指标 | 定义 |
| --- | --- |
| inputDrift | totalContextTokens − vendor.input（有符号）|
| inputDriftRate | inputDrift / vendor.input |
| outputDrift | estimate.output − (vendor.output − vendor.reasoning)（有符号）|
| outputDriftRate | outputDrift / (vendor.output − vendor.reasoning) |
| costDriftRate | (estimatedCost.total − vendorCost.total) / vendorCost.total |

估算总量参照：estimatedTotal = totalContextTokens + estimate.output，对比 vendor.total。

### 2.5 Tokenizer

- 使用 js-tiktoken（默认 o200k_base，可用 RuntimeConfig.tokenizerEncoding 覆盖）。
- 这是对厂商（DeepSeek 等）私有 tokenizer 的**近似**：用于暴露估算与实际的偏离，不作为计费依据。
- 编码器进程内缓存；文本为空 → 0。

## 3. 数据契约（packages/libs StepUsage）

    interface StepUsage {
      roundId?: string;                    // 同轮 thinking/intent 共享；聚合按它去重
      vendor?: {
        inputTokens: number;
        outputTokens: number;
        cacheCreationInputTokens?: number;
        cacheReadInputTokens?: number;
        reasoningOutputTokens?: number;
        totalTokens: number;               // input + output
        reportedByVendor?: boolean;
      };
      runtime?: {                          // input 估算（breakdown）
        totalContextTokens: number;
        systemPromptTokens: number;
        historyTokens: number;             // 聚合 = 下面三个之和
        historyUserTokens?: number;
        historyAssistantTokens?: number;
        toolCallTokens?: number;
        toolSchemaTokens: number;
        newInputTokens: number;
        observationTokens: number;
        retrievedTokens?: number;
        exampleTokens?: number;
        systemPromptRatio?: number;
        contextWindowUtilization?: number;
        contextDeltaFromPrev?: number;
        strategyApplied?: string[];
        budgetPressureAction?: string;
        estimationDriftTokens?: number;    // 有符号：totalContextTokens − vendor.input
        estimationDriftRate?: number;
        contents?: {                       // 各段原文（截断，供点击查看）
          systemPrompt: string; historyUser: string; historyAssistant: string;
          toolCalls: string; toolSchema: string; newInput: string;
          observation: string; retrieved: string; examples: string;
        };
        diffContent?: string;              // 相对上一轮新增内容（截断）
      };
      estimate?: {                         // 输出估算
        outputTokens: number;
        outputDriftTokens?: number;
        outputDriftRate?: number;
      };
      cost?: StepCostUsage;                // vendor token 口径
      estimatedCost?: StepCostUsage;       // 估算 token 口径（breakdown）
      timing?: { ttftMs: number; totalMs: number; tokensPerSecond: number };
    }

**来源**：measureContext 产 runtime 段（requestRound 内回填 input 漂移）；requestRound 产 estimate /
estimatedCost；provider 层 computeCostBreakdown 产 cost / estimatedCost；RoundExecutor 产 timing。

**轮次归属与去重（roundId）**：一轮模型调用可能产生 thinking 与 intent 两个 step，二者挂载**同一份** usage
（携带同一 `roundId`）。会话/任务/底部统计按 `roundId` 去重，一轮只计一次；单步面板仍显示完整 usage，
因此「首步 thinking」也有统计。旧数据无 roundId 时按 step 各自计入（历史每轮仅一个 step 带 usage，不受影响）。

**input 全量口径**：`vendor.inputTokens` = 全部输入 = `cachedInputTokens + cachedWriteInputTokens + 新输入(miss)`；
`outputTokens` 已含 `reasoningOutputTokens`；`totalTokens = inputTokens + outputTokens`。pi-ai 桥接层负责把其
「未命中缓存」的 `input` 与 `cacheRead/cacheWrite` 相加归一（`normalizePiUsage`）。

**工具调用展示**：`StepView` 额外投影 `toolArguments` 与 `toolOutput`；对话流工具行标题显示命令/参数
（`shell.run` 取 command，其余取单值或 JSON），可展开查看完整输出，行尾显示用时与失败状态。

**工具审计 view**：选中 `tool_call` step 时，右侧审计面板渲染**工具专用视图**（命令 / 参数 JSON / 输出 / 耗时 / 状态），
不再展示 vendor token / 估算 / cost / timing 这些对工具步无意义的区块（`AuditView.tool`）。

**intent 内联于 thinking（中间轮）**：同一 `roundId` 的**中间轮** intent（模型输出）内联展示在其 thinking 的
reasoning 下方，**不单独成步、不用代码框**，正文颜色比 thinking 的灰更深（`--fg` vs `--fg-secondary`）。
**整条 run 的最后一个 intent（最终模型输出）不进入执行树**，由底部独立的 **Summary 区块**展示
（正文 + 该轮 token，可点击查看审计；与该轮 thinking 同轮，故审计数据一致）。无 thinking 的孤立 intent
（纯文本轮）单独成行（旧数据无 `roundId` 时按 `thinking → intent` 邻接回退配对，最终输出同样排除）。

### 5.1 Vendor 用量
- 五项分行：input / output / cached input（附占 input 命中率）/ reasoning output / total。

### 5.2 Input 估算（breakdown）
- 环形饼图（SVG 扇区，每段一个 path）按段占比着色，中心显示估算 input。
- **hover 交互**：悬停扇区向外突出、其余变暗，并冒气泡展示段名 / tokens / 占比；图例行与扇区双向联动。
- **归一化与保底**：饼图按「显示段 token 之和」归一化，非零段保底最小扇区（缺省 3%），
  否则占比过小的段不可见；图例仍显示相对 totalContextTokens 的真实占比。
- 图例逐段列出 token 与占比，**点击分段展开该段原文**（contents，截断）；旧数据缺细分字段时退化为单段 history。
- 窗口利用率进度条 + contextDeltaFromPrev（>0 绿 / <0 橙）。
- inputDrift 与 inputDriftRate（有符号，警示色）。
- 展示与上一轮**新增内容**（diffContent）供对照。

### 5.3 输出估算
- estimate.output、vendor 非 reasoning 输出、outputDrift/Rate。
- estimatedTotal 与 vendor.total 对照。

### 5.4 Cost
- vendor 成本与 estimated（breakdown 估算）成本并列，附 costDriftRate 与成分拆分。

### 5.5 Timing
- TTFT / total / tok/s。

### 5.6 展示范围与边界
- 不展示工具与模型的输出正文（正文属对话流，不属审计）。
- **context diff 以 Conversation 为范围**：步骤按会话流全局排序（跨 run/task/step），
  某一步的 diff = 本步 context 总量 − 会话流中上一步总量。
- **步骤编号统一为 `R#1·T#1·S#1`**（中点分隔，`R#运行·T#任务·S#task 内步骤序号`），三者是
  **一个整体单元格**（不再各自一列）：审计面板底部的步骤明细、Context 追踪、工具折叠行都使用该整体格式。
  会话步骤表顶部渲染一行**表头**（`位置 / 类型 / 上下文 / Δ / tokens`）标明每列含义。
- 步骤明细：Task 目标只列本任务步骤；未选目标时展示整条会话步骤线；单步骤目标不列明细。

### 5.7 Context 追踪（独立 Tab）

- 侧栏新增「Context」页：以 Conversation 为单位，从第一个 run 到最后一步，按会话流顺序
  列出全部 step 的估算 input 总量（`R#/T#/S#` 整体）与相对上一步的 context delta。
- **折叠 icon hover 才显示**：每个 step（含工具组）行首的 `+`/`−` 默认隐藏，鼠标悬停才显现；
  **单击该 icon** 折叠/展开，**双击该行**定位到主页面会话流对应 step（`data-step-id` + `scrollIntoView`），
  且**保留在 Context 面板**、不跳转到审计面板。
- 每步可展开查看**按段拆分的新增内容**（diffContents，截断）：system prompt / user history /
  assistant / tool-call args / tool schema / user input / observation 各段分别展示相对上一步的增量。
  首个 round 的 system prompt 与 tool schema 以全量呈现；后续轮只列真正新增的消息。
- 可视化：顶部为**峰值 / 最新 context + 窗口利用率**与**分段图例**；每步一行，
  行内是**分段堆叠增长条**（system prompt / user history / assistant / tool-call args /
  tool schema / user input / observation 按比例堆叠，长度按会话峰值归一），右侧为总量与 delta。
- **过滤对 context 无影响的工具调用**：工具步没有自己的 context，不进入增长条图表；
  它们**折叠在对应模型轮（thinking）那一行之下**（不是单独面板）——每个模型轮一组，
  组内「工具调用（N）」可展开。工具行展示完整工作路径 + 命令：`<cwd> <命令/参数>`（如 `~/.mazi ls .`），
  `cwd` 为 tool_call 入库的 `payload.cwd`（home 缩短为 `~`），非 `shell.run` 会在命令前带上工具名。
- 列表不随 Step/Task 选择变化，始终是整条会话流。

## 6. 计算规则

### 6.1 原始事实入库与派生（不把展示逻辑写进凭证）

- `Step.usage` 除写入时的展示派生值（`vendor` / `timing` / `cost` / `estimate` / `runtime`）外，
  还入库**原始轮次事实** `raw`：`providerId` / `modelId` / `inputTokens` / `outputTokens` /
  `cachedInputTokens` / `cachedWriteInputTokens` / `reasoningTokens` / `totalTokens` / `ttftMs` / `totalMs`；
  以及派发钉死的 `pin`（`offeringId` / `pricingPlanId` / `catalogEpoch`）。
- 读取时 `usageViewOf` **优先由 `raw` 重算** `vendor`/`timing`；无 `raw` 的旧数据回退到写入时的派生字段。
- 目标：即使 UI 或算法演进，也能从原始事实重算，而不是依赖当时算出的派生值（"数据对不上"）。

- **估算**：tokenizer 对文本 encode().length；requestRound 汇总 runtime 段并回填漂移。
- **estimatedCost**：以 TokenUsage{ input=估算input, output=估算output, cached=0, reasoning=0 }
  走 computeCostBreakdown。
- **聚合**（Task / Conversation）：vendor/cost/estimate 求和；runtime 取时间最新一轮；漂移按聚合后的
  input/vendor 重算（inputDrift = Σ估算input − Σvendor.input）。
- **会话线 delta**：按 Conversation 内 run 顺序拼接全部 step，contextDelta_i =
  totalContextTokens_i − totalContextTokens_{i-1}（首个为 null）；Task 明细同样使用该全局 delta。
- **占比**：segmentTokens / totalContextTokens；total 为 0 → 全 0；环形按各段 ratio 归一。
- **格式化**：token K/M；成本 6 位小数；百分比 1 位小数；漂移带符号。

## 8. 日志与事件面板（系统级 vs 会话级）

审计 / Context 面向**单条会话的用量与上下文**；「日志 / 事件」承担**系统级**观测，避免与会话流重复。

### 8.1 日志（系统）
- 服务端进程内维护最近日志环（`apps/api` `log.ts`，上限 1000 条：level/module/time/message），
  所有 `Logger.log/warn/error` 写入缓冲；debug 仅在 dev 记录。
- `GET /api/logs?level=&limit=` 返回最近日志。
- UI「日志」页：级别过滤（全部/错误/告警/信息）+ 刷新；**只展示系统日志**，不再重复会话步骤看板
  （步骤/用量请看审计与对话流）。
- 行内固定 时间 / 级别 / module 列宽避免重叠；内容省略号截断，**鼠标 hover 弹窗显示完整内容**（宽度不足时也能看全）。

### 8.2 事件面板（暂时下线）
- 在「系统 / 会话流」梳理清楚之前，右侧栏**去掉「事件」页签**；只保留 审计 / Context / 日志。
- 事件数据管线（Harness 事件、SSE）仍保留，便于后续以更清晰的形态重新引入。
- 历史尝试：事件行曾把 `step.started`/`step.ended` 合并为一行、按来源区分系统/会话；因与系统日志职责重叠而暂时下线。

### 8.3 面板宽度与最大化适配
- 右侧栏默认宽度 440px（可拖拽，280–960px）。
- **最大化 = 内容适配而非拉伸**：`.drawer-body` 居中限宽（≤1280px）；≥1180px 时审计页改为双栏网格，
  「步骤明细」跨整行；Context / 日志 / 事件保持单列限宽，长行不会横跨整屏。
